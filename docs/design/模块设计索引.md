# 模块设计集 · 索引与系统级设计

- **定位**：本集是 [architecture.md](../architecture/architecture.md)（唯一架构图，v0.9）的**模块级细化层**——
  每个执行单元一份设计，落到"格 / 件 / 句柄 / 主题 / 参数 / 时序 / 降级 / 红线"八面。
- **证明方法（本集的写作规矩）**：每一句现状断言都回指一个文件（`module.toml`、`atoms/*/atom.toml`、
  `src/composite.rs`、`rr-hal` 选择函数、`config.toml`、`contracts/*`），符号名锚定不写行号
  （[conventions.md](../process/conventions.md) §5）；**未取到证据的一律标"待证"或"无实测"**，
  不写推测值。设计意图与现状事实分节写，绝不混排——这是本集与旧版文档最大的差别。
- **冲突裁决序**：ADR > architecture > 本集 > 模块 README。本集若与上三者矛盾，以上三者为准并回改本集。

## 1 系统切分总表（六执行单元）

| 单元 | 执行单元形态 | 件（格） | 对外面（RPC / 发布） | 句柄来源 | 心跳/看门狗 |
|---|---|---|---|---|---|
| `rr3-sense` | 进程（host）/ 待 rtos 复用 | capture(`audio.capture`) · vad(`audio.vad`) · env(`sensor.env` 占位) · imu(`sensor.imu` 占位) | `capture/dump` · `audio/pcm` + `audio/vad_start` **两流实发**（`env/temperature`、`imu/state` 申报在册但**无生产者**） | `rr3_hal_audio_source` | 1000 / 5000 ms |
| `rr3-act` | 进程（host） | servo(`act.servo`) · led(`act.led`) · relay(`act.relay`) | 三 RPC + servo/state(限速流) · relay/state · motor/reflex | `rr3_hal_servo` · `rr3_hal_gpio_out(role)` | 1000 / 5000 ms |

## 2 跨单元契约实然图（`⊙` 的当前真相）

下表左列是**申报面**（六份 `module.toml` 的 `[events]`），右列是**实现面**（各 `composite` 里的发布/
订阅/点名常量）。两列不一致的地方就是设计要处理的债。

| 通道 | 申报 | 实现 | 判定 |
|---|---|---|---|
| `sense → brain` `audio/pcm`、`audio/vad_start` | **brain 的 `subscribes` 未列**（只列 `asr/text`、`net/link`） | 真实消费：`rr3-brain/rr3_brain/composite.py` 的 `TOPIC_PCM` / `TOPIC_VAD` | **申报缺口（阻塞裁剪与降级判定）**：语音主链的实际入口不在契约面上 |
| `interact → brain` `rr3-interact/asr/text` | brain 订阅、interact 申报发布 | interact 全模块**零 `rr3_publish` 调用**（发布只存在于 `tools/sim`） | **悬空边**：设计上的 ASR 文本上行链在生产侧不存在；首个 retired 候选（C14） |
| `interact` `rr3-interact/dialog/turn` | interact 申报发布 | **全仓零生产点**——`tools/sim` 也只发 `asr/text`，没有任何代码路径发 `dialog/turn` | **纯幽灵边**（比上一条更彻底：连演练脚本都不产它），C14 首例应包含它 |
| `brain → act/interact` `rr3-brain/intent/result` | act + interact 订阅，brain 发布 | 三侧一致（act `intent.rs` 两道归属门；interact 主循环消费） | 成立 |
| `act → brain` `rr3-brain/llm/completion` 等点名 | brain `exposes` 一条；act/interact 无申报需求 | brain 调 `interact/tts/text` 是**点名调用**（`rr3.call`），不占订阅面 | 成立（形状需在 §7.2 写清） |
| `env/temperature`、`imu/state` | 件与 module 均申报发布 | 占位件无机制、无发布代码 | **申报超前于实现**；格标记位应记"占位"（ADR-0019 修订 2 ③） |
| `power → 全体` 降级传播 | `net.online`/`power.battery` 为 base 层恒在位 | rrd `rr3_state_frame` + 依赖环（`registry.rs` 的 `rr3_reg_*`） | 成立，但**探测恒真**使"缺格降级"环不转（`rrd/src/probe.rs`） |

> **结论**：语音闭环的**申报拓扑与运行拓扑不是同一张图**。第 III 轮批I–K 之前，`architecture §7.2`
> 必须按实然图画（见本集 §4）。这条差异不修，任何"裁剪掉某个单元看谁降级"的推演都是假的。

## 3 窄缝在各单元的落点（谁被哪条缝卡住；前三条 = 第 III 轮，第四条 = v0.11 增补轮六）

| 单元 | 能力面（`rr-hal-api`，批I） | 总线（`Rr3ByteStream`，批J） | 注入面（`handles`/`ops`，批J） |
|---|---|---|---|
| sense | 音频源 + `Rr3PcmStream`/`Rr3AudioCfg` 值类型去 `Vec` | 采集环在板上要有 conn 通路 | capture 的 `sample_rate/channels/frame_ms` → ops 槽 |
| act | 舵机 + GPIO 两 trait；led/relay 去 `rr3_block_on` | 反射环**永不进 `⊙`**（ADR-0007），仅需本地 | 行程/时限/限速 → ops；**LED 白名单是策略**（待迁） |
| interact | 显示帧 `Rr3FaceFrame` + 音频 sink | panel HTTP 属 host 档专属（rtos 无面板） | 音量/预缓冲/表情默认值 → ops（现 config 未被读，见该册） |
| power | 电源读数 trait + `Rr3BatteryState` | 心跳 2s 档 | 阈值三条（sample/low/cutoff） → ops；**cutoff 只解析不动作** |
| connect | 链路读数 trait + `Rr3LinkState.ssid` 去 `String` | UART 桥对端的主要用户 | 上报周期/漫游探测 → ops；配网 8 位规则属策略 |
| brain | 不接能力面（云 HTTP） | 宿主档专属，不进 rtos/bare | 模型名/超时/静音尾 → 策略配置（L4，本就该在 brain） |

**v0.11 补第四条（资源与语义缝，architecture §12.8）**：上表三列之外，每个单元还欠同一件事——
它依赖的**物理资源（角色 / 槽位 / 能源域）在契约里没有对象**。逐单元看：sense 欠 I2S 与音频格式的绑定键、
act 欠轴执行件档案（行程/极性/速率/激磁/电流上限）与数字输入面、interact 欠显示面板句柄与亮度阶梯参数、
power 欠轨压与能源域（= 本集 §11 新增 L-11 的另一面）、connect 欠 UART 环大小/波特率与板侧凭据存储、
brain 不接物理面但欠模型 ops 的面板可见性。工单落点 = 各册批N 单号（power P-9/P-10、act A-13/A-14、
sense S-9/S-10、interact I-15/I-16、connect N-10、brain B-12），施工编排见
[增补轮六全案](../process/dev/0.0.5增补轮六——底座资源模型与能力面抽象补课全案.md)。

**同批订正一行**：上表 interact 行原写"panel HTTP 属 host 档专属（rtos 无面板）"。随
[ADR-0021](../process/adr/ADR-0021-三独立形态与资源供给面-能力原子化补课.md) 裁定 1 的三形态独立改判，
**rtos 形态必须有自己的配置面**（观测面责任不可经链路转让给宿主），面板不再是 host 专属；
待裁面因此收窄为"写通道走 WiFi 还是先 BLE"（本集 §8 的 D11/D12），而不是"rtos 要不要面板"。

## 4 对话主闭环的实然序（本集按此重写，`architecture §7.2` 同批对齐）

```
mic → sense.capture（自 pacing，frame_ms 拍）→ audio/pcm(stream) ┐
                                  vad（**两沿**：Onset/Offset）→ audio/vad_start ─┤→ brain.dialog 状态机
                                                                                  │   （Onset 起轮 / Offset 收轮
                                                                                  │     / 采集段上限 8s 封轮）
云 ASR(brain.asr) → 文本 → brain.llm → 回复 → brain.tts → PCM
   → rr3.call 点名 interact/tts/text → interact.player 播放 → interact.face 表情
   → brain 用**用户原话**（不是回复）匹配关键词 → 发 intent/result → act（servo/relay 执行，两道归属门）
```
**与申报拓扑的四处不同**：① 入口是 sense 直连 brain（不是 interact 转发 asr 文本）；② brain 到 interact 是
**点名调用**（`rr3.call`）不是订阅；③ **判停在 sense**（`silence_tail_ms` 是 sense 的参数，brain 侧同名键
无读者）——旧版把它画进 brain 的状态机是错的；④ 意图映射读的是**用户原话**，schema 还明禁拿回复匹配。
另有一条"应有而无"：链路 down 不起新轮在 brain 里没实现（B-7）。写方案时以本序为准。

## 7 框架与填写纪律

所有单元册照 [模块设计框架 v1.3](模块设计框架.md) 的**十五节**填写（§0 身份证 → §14 基线对表）。
三条硬规矩：① 签名照抄仓内现物、目标签名以 `→` 标注并说明为何改，且要分清**件面导出**与**只在 `mech` 内
`pub`**（后者一律立工单，不留在中间态）；② 时序数字必须来自代码常量或 `config.toml`，未实测的一律写
"名义"并把实测项推给 §11；③ **推测值**只准出现在 §11，但 §4/§6 的"未实测/后端未实装"是**必须写的缺口
标记**，每条指回 §11 的编号——v1 把这条写成"待证只准在 §11"，结果六册自己在 §4/§6 各破了一次，v1.1 收口。
**§8 两腿对拍用例设计**是这版与上一版的分水岭——没有它，件就不能进 ADR-0019 修订 1/2 的门禁。
本轮全量复核（六册逐符号对代码）另立一条纪律：**用例存在性必须点着用例如名**，"需补"之前先 grep 一遍
tests 面——六册里有六条"缺用例"的登记其实是错的（用例早已在册）。

## 10 形态裁剪闭环（总目标的机械化：一套机制核，裁出多种微型形态）

主形态是**具身机器人**（六单元全启用），裁剪出来的微型形态是同一套件在不同承载档上的**子集 + 不同放置**。
本节的作用是把 architecture §12.7 的"谱系"落到**具体格位集合**——因为"裁剪 = 只改装配单"这句口号，
只有写出至少一个真能裁剪出来的第二形态才算数。格名一律取 `contracts/slots.toml` 与 `profiles/default.toml`
的实然集合，不造新格。

| 形态 | 承载档 | `enabled_slots`（模块 → 格） | 失去什么（诚实面） | 板侧必须自己守住什么 | 证的命题 |
|---|---|---|---|---|---|
| **F-A 全承载具身主形态**（rock3 今天） | host | 实然 17 项：`act 3 / connect 2 / interact 2 / sense 4 / power 2 / brain 4`（+ base 5 恒在） | 无（基准） | 全部安全核在板侧件 + rrd 监督 | 具身主形态成立 |
| **F-B 桥接微型形态**（`profiles/esp32-mini.toml`，0.0.5 R3-D6 的第二形态样例） | rtos | `rr3-sense = [audio.capture, audio.vad]`、`rr3-act = [act.servo]`（可选 `act.led`）；**不启用** `net.*`（桥就是它的链路）、**不启用** `cognition.*`（认知在 host）、**不启用** `ui.face`/`audio.playback`（无屏无喇叭） | `audio/pcm`+`audio/vad_start` 只上灌不本地下发；`tts` 产出丢弃（interact §6 "意图与声音解耦"成立）；`relay` 缺席 = 意图里带通电动作的动作被拒执行（act §6 已定行为） | **限位 / 时限 / 饱和通告必须在板侧跑**（`rr-core::control` 已可达，act §12 判定 reflex 今天就能 bare）。理由：桥一断，舵机不能失去守护——这是"经桥不等于把安全托付给网络"的硬要求 | "裁剪 = 改数据"成立；一枚 MCU + 桥 = 会听会点头的微型机器人 |
| **F-C 自足微型形态**（bare，无桥无主承载层） | bare | 目标集 `rr3-act = [act.servo, act.led]`；`⊗` 只在单元内，`⊙` **不宣称**（ADR-0018 修订 2 ①） | **今天不成立**：base 层"恒在位"这一条在 bare 档是假的（见 §11 审计 L-10）——`bus.publish/subscribe/rpc` 与 `net.online` 都靠主承载层供数，bare 档无 rrd 即无这些格。另失去全部远程可观测面 | 本地安全核 + **平台看门狗**（缺口 L-2）+ 本地守护输出（缺口 L-1） | 远期"一枚 MCU 自成整机"（architecture §12.7）——**本版不主张**，只把成立条件写清 |

**填给点验矩阵的三行（architecture §12.6 七列）**：F-A = 0.0.6 全承载档首行（①②⑤⑥⑦ 行为证据 + ③④ 装载门）；
F-B = 0.0.7 轻承载档行，硬项 ①②③⑤⑦，**⑥ 生命周期按"经桥注册态"跑，不是"不适用"**（详见 §11 L-9）；
F-C = 无承载档空行，⑥ 列写"平台复位"，触发条件 = 一块真无 OS 的板 + L-1/L-2/L-10 三缺口关闭。

**裁剪自检三问**（每次新增微型形态都要答，答不出就不许进 profiles）：
① 被裁掉的格里有没有**别人依赖它作为依赖边**？（例：裁 `net.wifi` 后 `cloud/session` 的"链路未就绪"文案还成立吗？）
② 失去生产者/处理者的主题，申报面是否同步 retired？（否则依赖仲裁当它是活边——R-3 同型问题）
③ 该档安全核是否仍在板侧？（把限位/低电托付给桥或云 = 违规形态）
**v0.11 读法改判（承 [ADR-0021](../process/adr/ADR-0021-三独立形态与资源供给面-能力原子化补课.md) 裁定 1）**：
上表 `F-A/F-B/F-C` 是"**承载档 × 链路**"的组合名，不是三台机器的身份。三台独立形态——RK3566 桌面具身、
树莓派、ESP32 微型——**两两零关系**（不共享进程、不共享总线、不共享供电），"ESP32 是 RK3566 的协处理器"
这一定性作废（施工事实保留：显示/舵机/拾音/播放四件确实挂在 ESP32 上做完并实测）。
"经桥"是一种链路选项而不是形态定义，所以第③问"该档安全核是否仍在板侧"的答案与是否经桥无关；
更强的一句是：**观测面的责任不能经由链路转让**——形态自己欠压、自己标定、自己记外设失败数。
本节表格按历史保留，逐格得失在批N1 起改用"形态 × 档"两轴表述。

我自己 grep/读码复核，撤回与收窄项单列在
[增补轮六全案](../process/dev/0.0.5增补轮六——底座资源模型与能力面抽象补课全案.md) §16.2）。
它与第三类的区别在**位置**：命中点不在模块里，而在机制核、契约层、门禁脚本与装配单里——
纲领一直被用来量别人，这一轮量回自己最严的那一层，五条全中。
**L-22…L-24 是第五类**：来源是 **2026-10-15 同日再一轮的逐项证伪审查**——不问"文档写全了没有"，
只逐条问"**什么观测能推翻这条设计**"，并把反例构造到"不改任何硬件形状、只改装机档或一句话就让门变绿"
的粒度（32 条命中、其中 **14 条打在 ADR-0021/0022 与全案自己写的裁定与编排上**，撤回 7 处单列全案 §18.8，
审过成立 10 条单列 §18.7）。它与第四类的区别在**对象**：第四类量的是**代码**，第五类量的是**设计本身**——
包括上一轮刚立的那些判据。三类失败形态各有名字，因为它们要**分别执法**：
L-22 **自愿填写的字段**（不填即不判 ⇒ 注释搬了家）、L-23 **新加一层没迁旧一层**（同一事实四套语法、门只判一套，
所以它会**绿着发生**）、L-24 **判据恒真**（"并发窗口内""落在空段上""`ps` 看不到编译期常量"——
它交出的不是宽松而是**绿色的确定性**，人从此不再看这道门）。
五类都算审计，但证据强度与修法不同：第一类可被"设计还没做"解释，第二类已被硬件账单证实，
第三类只能靠**把门禁当被测对象**查出来（本集 §12 的三条硬尺正是为此而设），
第四类只能靠**把纲领当被测对象的自检**查出来——它最贵，因为它推翻的是"我们已经做到了"这句话；
第五类只能靠**给每条设计配一条反例**查出来，它推翻的不是宣称而是**判据**，所以它的产出多半是改写门而不是补码。
**L-26…L-27 是第六类**：来源是第六轮把设计**当运行期跑一遍**（掉电 / 重启 / 生效路径、端到端流与失败传播）。
它与前五类的区别在**时间轴**：前五类问"静态上闭不闭"，第六类问"跑起来之后这个值什么时候生效、失败了谁知道"——
所以它查出的东西在静态审里全都"写着"（`RAIL_MILD_MV` 是常量、`println!` 是留痕），只是**没有读者或没有通路**。
**L-25 / L-28…L-31 是第七类**：对象是**上一轮刚立的判据、分母、编号与门本身**，即审计的自指层。
第五轮机械数引用查出 L-25（同一份文档两套口径），第七轮闭合五问查出 L-28（判据的前件对象不存在）/
L-29（基座轨无号可引）/ L-30（序列没有唯一登记处），第八轮拿代码实测查出 L-31（门的入口条件可被省略参数绕过）。
这一类最容易被跳过，因为它要求**把刚写下的纪律当被测对象**；它的修法多半是**给纪律加一条登记义务**
（conventions §6 命名空间总表、§2 "判据登记时必须写出入口条件"），而不是补码。
七类都算审计；第七类是这七类里唯一会**随每一轮产物增长**的，所以它的执法位必须写在纪律里而不是写在某一轮的结论里。
这也是本集新增的收口判据：**每个坑必须升格为①供给位 ②能力面 trait ③描述符键 ④格或主题 ⑤门禁判据
之一**，否则只算一次现场处置，不算收口（判据原文见 [ADR-0021](../process/adr/ADR-0021-三独立形态与资源供给面-能力原子化补课.md)）。
这也是六册 §12/§13 存在的理由：那两件工件就是逼每一格、每一串都回答一次。
