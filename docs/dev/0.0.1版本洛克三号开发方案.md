## 1. 版本目标与范围

### 1.1 目标（一句话）

rock3 仓库完成结构化改造：legacy 冻结归位、新目录骨架建立、模块四件套规约可机械化生成、契约目录成为字节级唯一事实源、CI 守住规约。

### 1.2 范围内

| # | 交付物 | 说明 |
|---|---|---|
| D1 | legacy 冻结迁移 | `core/`、`firmware-c/`、`firmware-rs/`、`rust/` → `legacy/`（git mv 保历史） |
| D2 | 顶层目录骨架 | `base/`、`modules/`、`contracts/`、`tools/` 全量空结构 + 各级 README |
| D3 | 模块四件套 schema | `base/runtime/rr-registry/src/module.schema.toml` + 说明 |
| D4 | 契约初始版 | `contracts/envelope.schema.json`（A-IPC 128B）、`contracts/topics.toml`、`contracts/events/` 模板 |
| D5 | rr3-mkmod 脚手架 | 输入模块名 → 生成四件套 + manifest 骨架，产出物自动过 schema 校验 |
| D6 | Rust workspace 空壳 | `base/runtime/` 下 rr-ipc/rr-bus/rr-registry/rr-hal/rr-ota/rrd 六 crate 可 `cargo check` 通过（不含业务逻辑） |
| D7 | 规约 CI | GitHub Actions：① workspace 编译 ② manifest schema 校验 ③ 主题前缀归属校验（topics.toml vs manifest.name） |
| D8 | 开发规约文档 | 本文档 §5：分支/commit/评审/ADR/DoD |

### 1.3 范围外（明确不做）

- rrd 业务逻辑（注册/心跳/总线运行时）→ M2
- 任何模块的业务实现 → M3+
- Buildroot/OS 层 → M1
- Python 侧 rr3_brain 包 → M4

## 3. 任务分解（WBS）

依赖关系：T1 → T2 →（T3、T4、T5 并行）→ T6 → T7 → T8。工作量档位：S（半天内）/ M（1~2 天）/ L（3 天+）。

| # | 任务 | 产出 | 依赖 | 量 | 验收标准 |
|---|---|---|---|---|---|
| T1 | legacy 冻结迁移 | legacy/ 四目录 + 冻结 README | 无 | S | `git log --follow` 历史可溯；根目录只剩新结构 |
| T2 | 顶层骨架 | D2 全部目录与占位 README | T1 | S | 目录树与 §2 完全一致 |
| T3 | module.schema.toml | D3 schema + 注释化字段说明 | T2 | M | 用 schema 手工校验一份样例 manifest 通过 |
| T4 | contracts 初始版 | D4 三个文件 | T2 | M | envelope.schema.json 字段与 ADR-0006 的 128B 布局逐字节对应（偏移表） |
| T5 | rr3-mkmod | D5 脚手架 | T3 | M | `rr3-mkmod rr3-sense` 生成四件套；生成物过 schema 校验；名称不合 naming.md 规约时报错 |
| T6 | Rust workspace 空壳 | D6 六 crate | T2 | S | `cargo check --workspace` 全绿；rrd 可运行打印版本 |
| T7 | CI 流水线 | D7 workflow | T5、T6 | M | PR 上三检查全触发；故意提交错前缀 manifest 时 CI 红 |
| T8 | 开发规约 | 本文档 §5 定稿 + README 链接更新 | 全部 | S | README_zh 的文档索引增加本方案 |

关键设计点：

- **T4 的 envelope.schema.json 是全项目第一个"真"契约**——把 ADR-0006 的 C 结构转写为 JSON Schema（字段、偏移、LE 序），并附偏移对照表。M2 时 Rust/Python 编解码用它做 golden test
- **T5 的 mkmod 是规约的执行器**：四件套模板、manifest.name 与目录名一致性、事件前缀规则都在生成器里强制，而不是靠人记住 naming.md
- **T7 的主题前缀校验**是最早的"架构守护"自动化：topics.toml 中每条主题的前缀必须等于某个已注册 manifest.name，CI 直接拒绝越权

## 4. 模块 manifest schema 要点（T3 交付物定义）

字段集与约束（完整 schema 见交付物）：

| 段 | 字段 | 约束 |
|---|---|---|
| [manifest] | schema_version / name / version / type / lang / entry | name 必须匹配 `^rr3-[a-z]+$`；type ∈ module/brain；lang ∈ rust/python |
| [provides] | capabilities | 每项 `^[a-z]+(\.[a-z_]+)+$`（如 audio.capture） |
| [depends] | required / optional | 引用的 capability 必须存在于已注册模块或 base 内建 |
| [events] | publishes / subscribes | 每条以 `[manifest.name]/` 为前缀 |
| [rpc] | exposes | 同上 |
| [resources] | restart_policy / mem_limit_mb / start_priority | restart_policy ∈ always/on-failure/never |
| [health] | heartbeat_ms / watchdog_timeout_ms | heartbeat < watchdog |
| [upgrades] | semver 约束 / staging 开关 | ADR-0007 预留字段，v0.0.1 允许缺省 |

## 5. 开发规约（D8，从 v0.0.1 起生效）

### 5.1 分支与提交

- 分支：`main` 受保护；功能分支 `feat/<topic>`、修复 `fix/<topic>`、文档 `docs/<topic>`
- Commit：遵循 Conventional Commits（`feat:`/`fix:`/`docs:`/`chore:`/`refactor:`）；涉及决策的提交必须在 body 引用 ADR 编号
- 重大决策流程：先写 ADR（状态：提案）→ 评审通过改"已接受" → 关联 PR 合入

### 5.2 代码规约

- 命名：唯一权威是 [naming.md](../naming.md)；CI 层面只强制机器可查项（crate 名、manifest 校验），其余靠评审
- 模块代码不允许直接依赖其他模块的 crate——只能经 rr-ipc/rr-bus（架构守护，评审一票否决项）
- 每个模块四件套齐全是合入 `modules/` 的前提

### 5.3 Definition of Done

- [ ] `cargo check --workspace`（及 CI 全检查）通过
- [ ] 涉及 contracts/ 的变更附带 schema 演进说明（只增不改 / major 升级）
- [ ] 涉及架构语义的变更已更新对应 ADR 或新增 ADR
- [ ] 新模块由 rr3-mkmod 生成并通过 schema 校验

### 5.4 文档纪律

- architecture.md 是唯一总览，改结构必改它的 §3 目录树
- ADR 只增不改实质内容——被修订时在状态行注明（ADR-0003 先例）
