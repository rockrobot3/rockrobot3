# ADR-0009：依赖仲裁 —— 启动序、降级传播与不做清单

- **状态**：已接受
- **日期**：2026-10-01
- **关联**：[ADR-0002](ADR-0002-模块模型-5加1-进程隔离.md)（§2 模块只依赖能力名）· [ADR-0007](ADR-0007-控制面分层与模块级升级.md)（重启预算）· [architecture.md §4.1](../../architecture/architecture.md) · status.md"依赖仲裁"行

## 背景

`depends.required` / `depends.optional` 两个 manifest 字段自 D3 起就在字段字典里（形状：
capability 列表），但语义只落地了一半——单件校验把每一项硬性限在 `base_capabilities`
白名单内（`module.schema.toml` 自注"v0.0.1 只有 base 内建能力可被依赖；跨模块能力仲裁随
rrd 注册表（M2）落地"，M2/M3 已过而仲裁未落地），status.md 因此记"依赖仲裁＝未设计
（连类型都未定义）"；rrd 侧 supervisor.rs 文件头已知边界④写明"depends / degraded 两条
不做"——启动序只按 `start_priority` 排，`Rr3Phase::Degraded` 是"有 enum 变体、无写入方"
的死相位（`rr3_reg_beat` 对它的"只续命、不升级"兜底已实装）。F 系列框架收口要接通这两条。

## 决策

### 裁定 1：依赖对象永远是能力名；可满足者 = base 内建 ∪ 本次 boot 全集 provides

ADR-0002 §2 口径不变：manifest 不依赖模块名，只依赖能力名（能力名依赖 = 模块可替换的
泛化核心）。一个 required 能力的满足者只有两个来源：`base_capabilities`（基座内建，
永远在位）∪ **本次 boot 装载全集**里各 manifest `provides.capabilities` 的声明。

由此，校验分两层、各管一段：

- **单件校验**（rr-registry 既有入口）看不到全集，"未知能力"检查从单件层**迁出**——
  单件层对该段只保语法（`capability` 形状规则）。这不是放宽：原"必须命中 base 白名单"
  是"跨模块能力登记面定型之前的过渡约束"（architecture.md §4.1 原话），定型后继续
  留在单件层反而挡死一切跨模块依赖。
- **跨 manifest 仲裁**（rr-registry 新增纯函数，`depends.rs`）：输入全部 manifest 的事实
  （名字 / provides / depends.required / start_priority），输出拓扑启动序或逐条错误。
  CI 全集检查与 rrd boot 共用同一实现，不允许第二处真值。

### 裁定 2：启动序 = 拓扑序为主键、start_priority 降为层内次键

- **边**：消费者模块 → 它 required 能力的**全部**提供者。多提供者并存时"任一存活即满足"
  是运行期语义；启动期不做择一——把任选一个提供者排前面会随集合变动翻转，全部排前
  保守且确定。
- **层内排序**：同一批入度为零的模块按 `start_priority` **稳定升序**，同 priority 按名字
  典序——确定性裁定，杜绝结果随装载顺序漂移。既有的"start_priority 稳定升序"全局规则
  从主键降级为次键，语义收窄但不作废。
- **环 → 拒整个 boot**（fail-closed）：环是 manifest 集合的自相矛盾，环内能力永远无人在
  位，挑牺牲品是任意裁定；rrd 打逐条点名后拒绝进入 boot 阶段。
- **能力不可满足（base 没有、全集无人 provides）→ 只拒该模块**：沿用既有 boot 拒绝口径
  （打"拒绝启动"、不吃重启预算），其余模块照常。环与不可满足分开裁定，因为前者无解、
  后者有局部解。
- 模块依赖自己 provides 且 base 也没有的能力 = 自环，落进"拒整个 boot"。

### 裁定 3：降级传播 —— 提供者全灭 → 下游置 Degraded；任一恢复 → 解除

- **触发**：某 required 能力的全部提供者都离开 `Running`（判死 `Failed` / 退出 / 注销）
  → 依赖它的在册模块置 `Degraded`（死相位的 setter 由此接通，写入方在 rrd 记账侧）。
  多提供者时任一存活即满足，不降级。
- **Degraded 语义 = 既有兜底**：模块保持注册、心跳只续命不升级（`rr3_reg_beat` 已实装，
  一颗心跳不会把降级标注抹平）；rrd **不杀**下游进程——是否自降功能由模块自己决定。
- **恢复**：任一提供者回到 `Running`（`Promoted` 那一拍）→ 重算，下游解除 `Degraded`
  回 `Running`。
- **optional 不参与**：不进启动序、不触发降级。v0.0.1 的 `depends.optional` 只是文档性
  声明（architecture.md §4.1 示例注释"缺席 → 降级运行"随之订正）。

### 裁定 4：重启联动边界

- 降级不是崩溃：下游置 `Degraded` **不吃重启预算、不产重启计划、不经 supervisor**——
  下游进程没病，重启治不了依赖缺失，还白烧 ADR-0007 的预算。
- 提供者自身崩溃照旧走既有三条死亡路记账（conn EOF / watchdog 到期 / 子进程退出码）；
  提供者反复崩达上限停止重启后，下游**稳定处于** `Degraded`——这才是"运行时降级"的
  落点，取代 supervisor.rs 那句只打日志的"停止重启……运行时降级"。

## 明确不做（本轮裁定边界，任何"依赖仲裁已完成"的措辞不许盖过）

1. **跨机依赖**：仲裁只在单机单 rrd 的 boot 全集内做。
2. **运行期动态重仲裁**：启动序只在 boot 时算一次；运行期新注册 / 注销不重排任何
   已在跑的模块。
3. **optional 依赖的传播**：见裁定 3，v0.0.1 不做。
4. **依赖触发的下游自动重启**：降级 ≠ 重启（裁定 4）。
5. **能力级权限仲裁**：谁**能用**一个能力（发布归属 / 越权拒绝）仍是 registry 发布四道门
   的范围；本 ADR 只裁"谁**提供**、先起谁、死了怎么办"。

## 备选方案否决理由

- **depends 直接写模块名**：破坏 ADR-0002"能力名依赖 = 模块可替换"的泛化核心。
- **环只拒环内模块**：依赖环内能力的下游同样不可满足，局部拒绝产出"半死集合"且报错面
  更难解释；整批拒最简单也最诚实。
- **单件层保留 base 白名单检查**：见裁定 1——它把跨模块依赖永久挡死，与字段字典自注
  的演进方向矛盾。
- **Degraded 时杀下游重启**：见裁定 4。
- **多提供者择一排序**：见裁定 2。

## 后果

- 正面：`Degraded` 死相位接通（supervisor 边界④解除）；启动序确定性可复现（同输入同序）；
  manifest 集合级错误（环 / 不可满足）在 boot 前被拒，不等注册握手才暴露。
- 负面：单件校验对"未知能力"的报错时机推迟到全集层——CI 必须跑全集仲裁补位（contract
  用例 `every_module_dependency_set_is_satisfiable_and_acyclic` 钉住）；原单件用例
  `manifest_unknown_dependency_rejected` 的断言随之迁移。
- 校验项：`cargo test -p rr-registry`（新增 `depends.rs` 单元用例与 contract 仲裁用例，
  条数登记 conventions §2）；rrd 侧接线（boot 拒环 / `Degraded` setter / 线级用例：链式
  启动序、环拒绝、依赖崩溃降级）另起 F2，本 ADR 不声称运行期已接线。
