# ADR-0010：控制通道与查询面 —— rr3.ctl.* 与 rr3-ctl 实装

- **状态**：已接受
- **日期**：2026-10-01
- **关联**：[ADR-0007](ADR-0007-控制面分层与模块级升级.md)（事务面 = UDS + JSON-RPC）· [ADR-0006](ADR-0006-采用AiryIPC线格式与rr-ipc分层.md)（线格式）· [ADR-0002](ADR-0002-模块模型-5加1-进程隔离.md) · architecture.md §3（rr3-ctl 规划能力）

## 背景

rr3-ctl（总线侧运维 CLI）自 M0 起只有命令面骨架：`commands.rs` 只回显"它将问谁、问什么"，
真正的 UDS 往返原计划随 M2。rrd 的 UDS 事务面（注册 / 心跳 / 发布 / rr3.call）已上线，但
它面向**模块**：首帧必须是 `rr3.register`，不注册的连接只会被读超时收掉。运维查询（查
在册模块、看健康、取日志）没有承载面。F3 把这条通道接通。

## 决策

### 裁定 1：同一套接字、同一线格式，控制通道是事务面的只读旁支

rr3-ctl 连接的仍是 `cfg.socket` 那一个 UDS（不另开管理端口），帧格式仍是 ADR-0006 的
128B 头 + 2B payload 前缀，请求体仍是 JSON-RPC 2.0。不引入第二条通道、第二套编解码。

### 裁定 2：ctl 连接不注册、不进在册表、不受 watchdog 管

控制连接是**一次性查询连接**：一问一答即断（rr3-ctl 每个子命令独立进程，天然一问一答）。
它不调 `rr3.register`、不在册表里占槽、不分配 task 号、不喂狗、不参与广播收发——在册表
是"活的业务模块"的账本，运维探针进来记账反而污染快照与容量门。

### 裁定 3：握手放宽只放 rr3.ctl.*，模块路径一字不动

`conn.rs` 的 `rr3_handshake` 增加一条旁支：首帧若为 `Request` + 方法 ∈ `rr3.ctl.*`，
**不注册、即答即断**——rrd 应答该请求后直接结束这条连接（`Rr3Flow` 语义上等价于干净收尾，
不记崩溃账）。首帧为 `rr3.register` 的模块路径与全部拒绝门保持原样；`rr3.ctl.*` 旁支的
畸形（非 Request / 非 ctl 方法 / RPC 畸形）仍按既有口径回错误帧后断开。

### 裁定 4：四个查询方法，全部落在"已有数据源"上，不新增状态

| 方法 | 数据源 | result 形状 |
|---|---|---|
| `rr3.ctl.status` | `rr3_reg_snapshot()`（在册表快照，按 task 升序） | `{"modules": [{"name","task","phase"}], "denied_publish": n}` |
| `rr3.ctl.health` | 快照 + 各条目 `heartbeat_ms` / `watchdog_ms` / `now - last_beat_ms` | `{"modules": [{"name","task","phase","heartbeat_ms","watchdog_ms","since_beat_ms"}]}` |
| `rr3.ctl.logs` | rrd 自身日志环（裁定 5） | `{"lines": ["...", ...]}` |
| `rr3.ctl.ota` | 无——恒拒（见下） | — |

- `status` 与 `health` 的数据全部来自在册表既有字段，**不新增任何守护状态**；快照按
  task 升序与 `rr3_reg_snapshot` 既有口径一致。
- `ota` **恒拒**：方法名进白名单（协议面定型、rr3-ctl 的命令面不再改），但语义随 M6
  （ADR-0007 决策二的模块级更新轨道）。错误码用契约冻结集里的 `AIRY_EPERM`（`Permission`）
  ——契约状态码子集是冻结面（envelope.schema.json `x-adopted-by`），不新增 `NotSupported`
  码，与 `rr3-ota-ctl switch` 的"恒拒 + 文案点 M6"先例同构。

### 裁定 5：日志环在 `rr3_log` 单点落环——stdout 照旧、内存环形追加

`rr3_log` 是全 daemon 唯一日志出口（既有事实，集成测试的可观察面全靠它）。在此单点加一个
**固定容量环形缓冲**（`Mutex<VecDeque<String>>`，512 行，满了丢最旧）：写 stdout 的行为
一字不动，追加一份进环。`rr3.ctl.logs` 返回环的**尾部副本**。不落盘、不写文件——持久化
日志属系统层（journald / syslog）职责，守护进程不重复做。

### 裁定 6：rr3-ctl 输出人类可读表，协议细节不漏到 stdout

rr3-ctl 负责 UDS 连接、发 `rr3.ctl.*` 请求、解析 JSON 应答，并渲染成人读的表（status =
对齐列的模块表；health 同表加心跳列；logs = 逐行原文；ota = 错误文案 + 非 0 退出）。JSON
形状是协议面（rrd ↔ rr3-ctl 的内部契约），不作为 CLI 的输出格式承诺。

## 明确不做（本轮裁定边界）

1. **日志持久化**：环是内存的、随进程消失；落盘归系统层。
2. **鉴权**：单机可信模型（与总线其余部分一致）；套接字文件权限就是访问控制。
3. **watch/订阅式查询**：ctl 连接一问一答即断，不订阅、不长连。
4. **ota 的任何执行语义**：随 M6。
5. **跨机查询**：ctl 只问本机这一个 rrd。

## 备选方案否决理由

- **rr3-ctl 走假注册（注册成特殊模块再查询）**：占在册槽、进 watchdog、污染快照，
  违反裁定 2 的账本语义；为绕开握手而伪造身份是协议面的歪路。
- **新增 `NotSupported` 状态码**：契约状态码子集是冻结面（envelope.schema.json），
  为一个恒拒方法动冻结契约不划算；`Permission` + 文案点 M6 表意足够。
- **日志环落在 daemon 广播面**（让 ctl 连接收 state 广播）：ctl 连接不进在册表就没有
  Sender，为它造一条特殊广播路是新增并发形状；一问一答读环副本最简单。
- **rr3-ctl 输出 JSON**：CLI 的用户是人；要机器可读，后续加 `--json` 时再说（本轮不做，
  免得两种输出形状都要测试钉）。

## 后果

- 正面：F3 打通"查在册 / 看健康 / 取日志"的运维闭环，M2 遗留的 rr3-ctl"实现随 M2"
  兑现；查询不触碰模块路径的任何拒绝门（握手放宽只在首帧方法分支上）。
- 负面：`rr3_handshake` 多一条旁支（分支复杂度 +1）；`rr3_log` 每行多一次入环拷贝
  （512 行上限，成本有界）。
- 校验项：rrd 侧线级用例（四方法各一条，夹具复用 tests/support）+ rrctl 单元用例，
  条数登记 conventions §2；`docs/reference/rrd-rpc.md` 的方法面同批更新。
