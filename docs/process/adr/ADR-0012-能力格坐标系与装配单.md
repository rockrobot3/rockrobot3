## 背景

ADR-0002 定下"模块只依赖能力名"的泛化核心，ADR-0009 把能力可满足性仲裁做了实装，但
**能力名本身至今没有坐标系**：`base_capabilities` 是代码里的白名单，跨模块能力（如
`audio.capture` 由谁提供、`tts` 可以有几家）只存在于各 manifest 的自由书写里。由此产生
三个泛化欠账：

1. **能力名无总表**——manifest 里写什么能力全凭作者，换一块板、换一个模块组合时
   没有"这台机器人有哪些格位"的单一事实源；
2. **装配信息无落点**——哪块板用哪些件、以什么形态起（模块→能力格的绑定关系）目前
   硬编码在 boot 流程与 rrd 参数里，"快速部署到另一台机器人"意味着改代码；
3. **机制与策略无边界**——模块里混着"怎么做"（PCM 采集、舵机协议）与"给谁用、
   何时用"（对话策略、装配关系），通用化的最后一步是把它拆开。

Airymax 0.1.19 对同类问题给出的工程思想是：**Slot**（能力格，固定不变）、**Atom**
（原子件，只含机制）、**Facade**（形态面）、机制与策略极致分离、⊗装配（进程内）与
⊙编排（跨进程）分界、格格双达标。本 ADR 采纳该思想，但 rock3 是 Rust 多进程架构
（模块即独立进程即 Facade），**不引入进程内 Composite 层**——见裁定 6 的形态差异声明。

## 决策

### 裁定 1：立格 —— `contracts/slots.toml` 是能力格坐标系唯一事实源

能力格（slot）= 一个**固定命名的能力位**，只描述"这里需要/可以有什么"，不描述"谁来填"。
全项目的格位总表落在 `contracts/slots.toml`（与 topics.toml 同级、同纪律：只增不改，
破坏性变更升版本走 review），分三层：

| 层 | 格位（示例） | 归属 |
|---|---|---|
| 基础层 | `bus` · `ipc` · `registry` · `arbitration` · `watchdog` · `ota` · `log` · `time` | 基座内建（`base_capabilities` 的表内化），永远在位 |
| 身体层 | `audio.capture` · `audio.play` · `audio.vad` · `motion.servo` · `motion.relay` · `power` · `net` · `sense.imu` · `sense.env` · `face.display` | 模块提供，按装配单绑定 |
| 认知层 | `dialog.brain` · `dialog.asr` · `dialog.llm` · `dialog.tts` | 模块提供，按装配单绑定 |

- 格位命名两段式 `<域>.<格>`（基础层单段，因其为横切设施）；与主题命名
  `rr3-<模块>/<域>/<事件>`（ADR-0003）不同轴，互不混写。
  **对账注记（2026-10-03）**：上表格名列与裁定 3 示例骨架是**设计期记法，不是事实源**——
  落盘的 `contracts/slots.toml` 全部为两段式（基础层格名随 `base_capabilities` 原名，
  "基础层单段"作废），且身体/认知层定名有出入（`motion.servo→act.servo`、
  `motion.relay→未立格`、`audio.play→audio.playback`、`power→power.battery/power.charger`、
  `net→net.online/net.wifi/net.bt`、`face.display→ui.face`、`dialog.*→cognition.*`）。
  格位全集与定名一律以 slots.toml 为准，本 ADR 正文不回改（ADR 只增不改先例）。
- **base 格的"永远在位"语义（2026-10-03 注记，B2 裁定）**：基础层格承诺的是
  **通道在位**——总线管道随 rrd 启动即存在、无进程提供者、按 ADR-0009 恒不降级；
  **不是"状态永远为真"**。`net.online`/`power.battery` 的状态语义是**事件负载**
  （在线/离线、电量读数），由基座转发，**反应归策略层**（ADR-0014 对话状态机即
  消费方）——这是裁定 2 机制/策略分离在 base 格上的推论，不是例外。slots.toml
  相应 note 措辞已按"通道 boot 即在位、状态运行期发布"订正。
- manifest 的 `provides.capabilities` 与 `depends.*` **只许引用表内格位**——单件校验
  只保语法，"是否在册"由 CI 全集层对 `slots.toml` 判（ADR-0009 裁定 1 的校验分层
  在此闭合：未知能力从"单件白名单"迁到"格位表查册"）。
- 格位表 ≥20 格起步，**只增不改**：新增格位 append 即可；格位语义变更 = 破坏性
  变更 = 升 schema_version。**不留空格**——进表的都是有明确供给方或明确需求的格，
  "先占位以后再说"的格不进表。

### 裁定 2：造件 —— 模块 = 只含机制的原子件 + 对外能力格面

模块（Atom）只含机制：怎么采 PCM、怎么驱动舵机、怎么跑 VAD。**策略不进模块**：
何时说、说什么（对话策略）归 `dialog.brain`；哪块板装哪些件（装配关系）归装配单
（裁定 3）；提供者选择归 rrd 仲裁（ADR-0009）。模块对外的身份不是"我是一个程序"，
而是"我 provides 哪些格位"——这与 ADR-0002 §2 一致，本裁定把"机制/策略分离"从
口号落成**可扫描的门禁口径**（裁定 5③）。

### 裁定 3：装配单 —— `profiles/*.toml` 纯数据，机器人装配的声明式描述

一台机器人的全部"选型与绑定"收敛为一份 profile，纯数据文件、零代码、零逻辑。
下面骨架的**格名与模块归属均为设计期示意**——格名对账见裁定 1 注记（如 `motion.servo→
act.servo`、`dialog.*→cognition.*`），模块归属以落盘 `profiles/default.toml` 与各
`module.toml` 的 `provides` 为准（如 `cognition.tts` 属 `rr3-brain`，非示例里的 `rr3-interact`）：

```toml
# profiles/<机型>.toml（示例骨架，schema 细节随实体落盘登记）
[os]
route = "distro"          # distro | buildroot（双轨见 ADR-0013）

[bindings]                # 格位 → 件（谁提供这个格）
"audio.capture" = "rr3-sense"
"motion.servo"  = "rr3-act"
"dialog.tts"    = "rr3-interact"

[enabled_slots]           # 模块 → 本形态启用的格位集合（原名 [faces]，2026-10-08 消歧改名）
rr3-sense    = ["audio.capture", "sense.imu", "sense.env"]
rr3-interact = ["audio.play", "dialog.tts", "face.display"]
```

- **rrd 启动装配链**：读 profile + 硬件探测（`/proc/device-tree`、`/sys`、ALSA 枚举）
  → 匹配（bindings 声明的格位与探测到的硬件能力对账）→ ADR-0009 仲裁出启动序
  → **缺格置 Degraded**（fail-closed：声明了格位但无人提供/硬件不在，模块降级
  而非带病启动）。
- profile 不写"怎么启动"（那是 rrd 的机制），不写"启动序"（那是 ADR-0009 拓扑仲裁
  的输出）——装配单只声明**什么格位、由谁、给哪个形态**。
- **`[os] route` 的消费者（2026-10-03 注记，B3 裁定）**：`[os]` 节归**装机与运维**
  消费（打包器按 route 选 deb/镜像、人读机型意图），**rrd 运行期不读**——轨无关性由
  ADR-0013 裁定 6 保证，route 不进装配匹配、不参与仲裁。v0.0.1 无代码消费者，
  属声明性元数据（与 `[bindings]`/`[enabled_slots]` 的"运行期必读"相对，`[os]` 是"装机期读"）。

### 裁定 4：装配 ⊗ / 编排 ⊙ 分界

- **⊗ 装配**：跨格位的静态绑定关系（谁提供 audio.capture、本形态启用哪些模块），
  发生在 boot 前，落在 profile + rrd 启动链。
- **⊙ 编排**：运行期的动态协调（对话轮转、事件流），发生在 boot 后，落在
  `dialog.brain`（ADR-0002 原则 3"brain 是唯一编排者"）。
- **F⊗F 非法**：Facade 不得做装配的事——rr3-brain 不许在运行期动态决定"哪个模块
  提供哪个能力"；rrd 不许在运行期重排装配（ADR-0009"运行期动态重仲裁"不做清单
  同款边界）。两者越界即门禁 ③ 的扫描对象。

### 裁定 5：门禁三项（fail-closed，CI 与 rrd 各管一段）

1. **模块互依赖成环 → 拒**：ADR-0009 已裁（环拒整个 boot），本 ADR 将其纳入
   装配门禁总清单，不另立语义。
2. **格位引用越表 → 拒**：manifest 引用的每个 capability 必须命中
   `contracts/slots.toml`；profile `[bindings]` 的每格必须同样是表内格位。
   CI 全集层判（与 ADR-0009 的 `plan_boot` 共用同一真值实现，不允许第二处）。
3. **机制/策略越界 → 扫描点**：模块 crate 之间互不依赖（既有 §3 结构纪律一票
   否决项）+ 装配关系不出现在模块代码里（F⊗F）。v0.0.1 为评审项 + lint 后置，
   逐条点名不静默放行。

### 裁定 6：格格双达标 + 与 Airymax 0.1.19 的思想映射与形态差异

**双达标**（格位成活的判据，两条缺一不可）：

- **有效扇入 ≥3**：一个格位要有 ≥3 个真实或潜在的依赖者才值得立格——扇入不足的
  "格"是单件私有配置，不配占坐标系；
- **测试接线 CI**：格位的提供者必须在 CI 里有契约级接线用例（manifest provides
  过格位表校验 + 仲裁用例可达），没有接线的格是纸面格。

  **口径修订（2026-10-03 注记，B1 裁定）**：双达标是**新格立格时的评审判据**，
  不是对存量格回溯执法的 CI 硬门——落盘 20 格按落盘日（2026-10-01）**grandfather
  豁免**，不因其扇入不足而拆格。原"有效扇入 ≥3"的数字是从 Airymax（数百模块生态）
  借来的标定，对 v0.0.1 六模块规模在数学上不可满足（连 `bus.rpc`/`power.battery`
  都过不了），若接成 CI 门第一版即红掉自己的格位表。新格立格判据据此收敛为：
  **≥1 个真实依赖者，或评审记录中明确的 ≥3 潜在场景**；"潜在"须落到评审文字，
  不接受口头占位（与"不留空格"同纪律）。扇入数**不进 CI**（CI 只执法测试接线那条），
  扇入判据留在 review。

**思想映射**（Airymax 0.1.19 → rock3）：

| Airymax 概念 | rock3 对应 | 差异 |
|---|---|---|
| Slot 能力格 | slots.toml 格位 | rock3 跨进程，格位由独立进程提供 |
| Atom 原子件（机制） | rr3 模块 crate 本体 | 同构 |
| Composite（进程内装配） | **不引入** | rock3 模块即进程，无进程内装配层 |
| Facade 形态面 | 模块进程对外能力面 + profile [enabled_slots] | rock3 的"形态"是装配单而非进程内包装 |
| ⊗装配 / ⊙编排 | rrd 启动链 / rr3-brain 对话策略 | 同构，分界判据见裁定 4 |

**形态差异声明**：rock3 是 Rust 多进程底座，模块 = 进程 = Facade，机制/策略分离
由**进程边界天然承载**，不需要 Airymax 的进程内 Composite 装配层。取其
"立格—造件—装配三分离 + 门禁执法"的思想，不套其运行时形状。

## 明确不做（本轮裁定边界）

1. **进程内 Composite 层**：见裁定 6，rock3 形态不需要。
2. **运行期动态改装配**：profile 只在 boot 读一次；换 profile = 重启，不做热切换。
3. **格位级权限仲裁**：谁*能用*一个能力仍归 registry 发布四道门（ADR-0009 不做
   清单第 5 条同款）；本 ADR 只裁"格位有哪些、谁提供、怎么装配"。
4. **profile 层级/继承**：v0.0.1 一机型一文件，不做 include/继承机制。
5. **硬件探测的抽象层**：探测逻辑（device-tree/sys/ALSA 归属哪个 crate）随实体
   落盘另行登记，本 ADR 只定"探测结果用于装配匹配"这一语义。

## 备选方案否决理由

- **能力名继续自由书写（维持现状）**：三个泛化欠账（裁定 1 背景条）无解，换板
  即改码，与"快速部署"目标直接冲突。
- **格位表放 base_capabilities 白名单里扩**：白名单是代码常量，加格要改代码再发版；
  格位坐标系必须是**数据**（toml），与 topics.toml 同纪律。
- **装配关系写在 manifest 里**：manifest 是**件**的声明，装配是**台**的声明；
  混写后同一模块在不同机型上无法复用，且多提供者择一必须有人裁——那是 rrd 仲裁
  的活，不是件的自述。
- **profile 写启动序**：与 ADR-0009"拓扑序为主键"冲突——序是仲裁输出，手写序
  与拓扑序必然漂移。
- **引入进程内 Composite**：见裁定 6 形态差异声明。

## 后果

- 正面：能力名有了唯一坐标系（`slots.toml`），"未知能力"检查有了全集真值；
  换板/换机型 = 写一份 profile，不改代码——"快速部署"从口号变成数据文件；
  机制/策略分离有了可扫描的门禁口径。
- 负面：manifest 能力引用受格位表约束（新能力先立格再用，多一道 review）；
  rrd 启动链增加"读 profile + 硬件探测 + 匹配"一段（缺格走既有 Degraded 语义，
  不新增相位）。
- 落点登记：`contracts/slots.toml`（20 格 = base 5 + body 11 + cognition 4，基础层格名随
  `base_capabilities` 原名——查册门把两份名单逐条钉死等价，正文"基础层单段"为示例记法）、
  `profiles/default.toml`（RK3566 参考机）、查册门（rr-registry `slots.rs` + contract 全集
  用例）已于 2026-10-01 落盘；rrd 装配链（读 profile + 硬件探测 + 匹配）仍未落盘，归后续
  批次（实况唯一落在 status.md）。

## 增补注记（2026-10-09，承 ADR-0018 修订 1 三档 + 索引 §11 审计 L-10）：base 层的"恒在位"要按档分族

本 ADR 裁定 1 给基础层格写的语义是"**通道 boot 即在位、恒不降级**"，`contracts/slots.toml` 五枚 base 格的
`note` 逐字承此。用微型形态推演时这条语义暴露出一处不闭合：**五枚格里有四枚的"在位"是靠主承载层供数的**——
`bus.publish`/`bus.subscribe`/`bus.rpc` 由 `rr-bus` + rrd 承载，`net.online` 由基座内建；在 bare（自足、无 rrd）
档里它们**没有供数方**。于是"恒在位"在该档要么假（依赖仲裁永远缺格），要么被迫装假（正是本 ADR 裁定 5②
门禁要防的"假在位"）。这不是 slots.toml 的数据错误，是本 ADR 的语义缺了一个维度：**在位性与承载档绑定**。

现补一条分层，不改任何既有格名、不改号位、不改查册门（只增语义注记，随批J 落 `slots.toml` 注释与查册面）：

| 族 | 成员 | 在位条件 | 供数方 |
|---|---|---|---|
| **base-supply**（真跨档恒在） | 时基 / 内存 / 事件循环 / 传输（`[supplies]` 四类，含 ADR-0018 修订 4 新增的看门狗位） | 只要该档有 port 就恒在 | 平台 port |
| **base-bus**（仅在有主承载层的档在位） | `bus.publish` · `bus.subscribe` · `bus.rpc` · `net.online` | **host / rtos(经桥) 档在位；bare 自足档不适用** | rrd + rr-bus（桥对端仍是 host 的 rrd，故经桥档仍在位） |
| 通道型 body 格 | `power.battery`（本 ADR 裁定 1 的通道语义样例） | 通道在位、读数可缺 | rr3-power；**纯 USB 供电形态下"通道"该不该存在 = 索引 D3 待裁**，本注记不预判 |

推论三条（写进 architecture §4.3 与 §12.1 的口径）：
① 微型形态的依赖仲裁**不许**要求 `bus.*` 在 bare 档满足——要求了就是永不可成立，裁到那儿就停；
② `net.online` 的"恒不降级"经桥档仍成立（对端 rrd 判在线），但**自足档不适用**，面板/状态面须写成
   "不适用"而非"离线"（architecture §12.7 形态身份那一条的同源问题）；
③ 三态标记（正常/占位/retired，ADR-0019 修订 2 ③）与"不适用"是**两个轴**：三态说这张格有没有件，
   适用性说这档要不要这张格。批J 的门只能各判各的，混判就会把"这形态本就没有总线"误报成"缺件"。

另记一处口径订正：本 ADR 落点登记段写"20 格 = base 5 + body 11 + cognition 4"，实况
`contracts/slots.toml` 是 **21 格 = base 5 + body 12 + cognition 4**（body 侧补入 `audio.playback` 后未回抄此数）。
数字以文件为唯一真值，本注记只订正正文计数。
