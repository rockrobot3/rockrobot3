## 背景

rock3 现有架构文档与代码都建立在"底座跑在 Linux 上"这一默认之上：架构文档把交付物定义为
"Linux 起来之后的 payload"（ADR-0013），`rrd` 在非 Unix 平台直接以 `RRD_UNSUPPORTED`
退出，HAL 后端、打包、brain 全部默认有操作系统。

本项目的核心价值是**跨平台快速部署**：同一套底座机制，要能快速部署到各种板卡上——既有带
Linux 的板卡（RK3566、树莓派这类应用处理器），也有**不带 Linux 的板卡（ESP32 这类微控制器）**。
"跨操作系统"不是附带好处，而是这套底座成立的理由：换一次平台省下的，是重做一遍的时间和成本。

一旦把"不带 Linux 的板"列为一等部署目标，"同一份 payload 装到任何地方"这句就站不住了——
微控制器上没有"操作系统起来"这一步，也就没有 rrd 的跨进程监督、没有 systemd、没有 ALSA、
跑不了 Python brain。硬套只会得到"ESP32 只能当被牵着的验证节点"，那等于没兑现核心价值。

因此必须把底座重新切成两层：一层与操作系统无关、能下沉到裸机、且冻结稳定；另一层只有具备
操作系统的平台才叠加。本裁定就是这条切线，以及"一个新平台要满足什么才算把 rock3 部署上去了"
的边界。它把 ADR-0017 的"机制与策略分离"从模块维度抬到操作系统维度：机制 = 所有平台共享的
不变内核；策略与承载 = 按平台叠加的可变量。

## 决策

### 裁定 1：底座切分为机制核与主承载层

- **机制核（与操作系统无关，`no_std` 可达，契约级冻结，所有平台共享）**：
  字节契约（128B 消息头 + payload 类型）· 传输抽象（transport trait）· 消息语义
  （发布/订阅/调用/广播的 topic、寻址、task 号、trace_id 规则）· 模块运行时（连接→
  注册→心跳→分发→节拍的执行环）· 控制原语（速度曲线、位置环、限位/过流保护等闭合
  原语）· 安全核（急停、限位、低电兜底）。
- **主承载层（有操作系统的平台才叠加，可增不可依赖）**：`rrd` 的跨进程监听与扇出、
  进程监督/重启/退避、完整 HAL 后端、cloud brain、deb/OCI 打包与 OTA 写侧。

一个机器人形态落在某块板上 = 机制核在其上运行 + 该板能否承载主承载层决定它跑多少。
带 Linux 的板跑全部；不带 Linux 的板跑机制核的一个切片（可为完整自足的极小机器人，
也可为经桥接使用主承载层能力的节点——二者都由同一套边界表达，差别只在"这块板提供了
多少承载"）。

### 裁定 2：模块的一般化——从"操作系统进程"到"平台执行单元"

修订 [ADR-0002](ADR-0002-模块模型-5加1-进程隔离.md) 的隐含前提：模块不再必须是一个
操作系统进程。模块 = **由平台提供一个执行单元**，落地形态随平台：

- 带操作系统的平台：独立进程（崩溃隔离由进程提供，沿用 ADR-0002 语义）；
- RTOS 平台：一个任务；
- 裸机平台：一个内联子系统（编译期装配进同一固件）。

模块对外的可见面（manifest 声明的 provides / subscribes / exposes、能力格绑定、
128B 消息语义）**不因落地形态改变**——变的只是"谁来给它调度的执行单元"。这一条是本裁定
最需要后续实施验证的地方：它要求机制核的模块运行时不把 `fork/exec`、进程间 socket 当成
唯一装配手段。

### 裁定 3：平台移植边界固定为四类供给 + 能力格部分实现

把 rock3 带到一个新平台，平台需要提供且仅需要提供四类东西：

1. **时间基准**：一个单调时钟（供心跳到期、控制节拍、注入时钟使用），不要求墙上时间；
2. **内存策略**：有堆则用堆，无堆则用静态/定长区——机制核不得假设全局分配器；
3. **事件循环**：一个能驱动"收帧→分发→节拍"的调度形态（Linux 是线程 + 阻塞 socket，
   裸机可以是主循环 + 中断，RTOS 可以是任务 + 队列），由机制核的运行环消费；
4. **传输实现**：对 transport trait 的一个实现，落到该平台的物理链路（Linux 本地为
   UDS；跨片或裸机可为 UART/SPI/I²C/BLE 等）。

能力格允许**部分实现**：一块板只提供它物理上具备的格（例如只有 PWM、GPIO 没有音频），
缺的格按现有纪律置 `Degraded`/`Unsupported`、显式回错、fail-closed，不影响底座在该板上
起来。立平台不为凑齐格而写假实现。

### 裁定 4：描述符是"这块板/平台是什么"的唯一数据事实源

把一台机器人在某块板上的全部平台特定信息——能力格到执行单元的绑定、每个格对应的物理
参数（引脚、控制器编号、总线、设备名）、内存与时基供给的取值——收进一份声明式描述符
（扩展 `profiles/<机型>.toml`，见 ADR-0012）。运行期由 rrd（或裸机上的机制核装配段）
读描述符、探测硬件、据此实例化 HAL 后端并把就绪句柄注入模块。

本裁定要求收口现状的一处泛化欠账：当前 `rr-hal` 把板特定值散落在环境变量与代码缺省里
（例如 I²C 总线缺省为树莓派那条、GPIO/PWM 缺省为树莓派引脚），使"换板不改代码"只在格位
层成立、在驱动缺省层不成立。收口方向：物理绑定来自描述符，环境变量降为应急覆盖，代码
缺省改为"描述符没给就 fail-closed"，而不是回落到某块具体板的引脚。

### 裁定 5：控制与安全核是纯函数 + 注入时钟；控制是组合出来的策略

承 ADR-0017、ADR-0007 裁定 1：反射环与高频闭环不进总线、留在本地。本裁定进一步约束其
可移植性——控制原语与安全核必须是**不读墙上时钟、不睡眠、时钟与输入由外部注入**的纯计算。
这样同一张控制图在 Linux 的实时环里跑、在裸机的定时器里跑，行为逐拍一致。开发者编排的是
"用一组稳定原语连成的控制图"（数据 + 参数），控制因此是**策略**；而执行这张图的定长、
确定性调度属于**机制**。执行局部性是机制，行为图是策略——这条线是"跨操作系统仍同底座"的
关键。

安全核（急停、限位、过流、低电兜底）不可被策略改写，永远包住任何控制图；它在带操作系统的
平台落在 rrd/基座，在不带操作系统的平台落在机制核内的同一段纯逻辑。

### 裁定 6：部署到新平台 = 实现移植边界 + 交描述符 + 过点验矩阵

"把 rock3 部署到一块新板"定义为三个动作，Linux 与非 Linux 一致：

1. 实现裁定 3 的四类供给 + 该平台提供的能力格后端；
2. 交一份该平台/形态的描述符（裁定 4）；
3. 过一遍**点验矩阵**——一套机械检查，确认：底座按描述符起来了、能力协商与降级正确、
   字节契约对得上 golden 向量、安全核生效、（若有主承载层）模块生命周期正常。

点验矩阵是"跨平台快速部署"这件事的机械下限：它把"新增一块板的验证成本"从人肉 bespoke
检查，压成"跑同一套矩阵"。跨平台持续集成（例如把门禁与跨架构用例接在能真正执行的流水线
上）是承载这套矩阵的地方；本机跑不到、需要实板或实芯的项，作为带触发条件的敞口显式登记，
不以"设计已覆盖"充当"已验证"。

## 备选与否决

- **备选 A：只支持带 Linux 的板，微控制器仅当验证/外设**——否决：等于放弃"跨操作系统"，
  核心价值不成立，"各种大小的机器人"里的最小端落空。
- **备选 B：为每种平台各写一套实现（Linux 一套、ESP32 一套）**——否决：那是两个底座，不
  是"一个底座跨平台"，回到换平台要重做的成本原点，也违背机制核冻结。
- **备选 C：把整份 rrd/全 HAL/Python brain 都塞进微控制器**——否决：裸机没有承载它们的
  前提（进程、文件系统、CPython），强行下沉只会得到一个跑不动的臃肿核；正确的切法是主承载层
  按能力叠加，不是全量下放。

## 后果

- 正面：跨平台成为"实现边界 + 交描述符 + 过矩阵"的可复现动作；同一份机制核可在有 Linux
  与无 Linux 的板上成立；形态与平台正交，裁剪全落在数据与策略上。
- 代价与敞口：
  - 需要把 `no_std` 可达线**从当前的字节协议层（`rr-ipc`，0.0.7 批B 已下沉）向上画过
    总线语义、模块运行时、控制与安全核**——这是一次真正的架构手术，不是改状态口径能替代的；
  - 裁定 2 一般化"模块 = 执行单元"，会牵动 ADR-0002 的进程隔离表述与 rrd 监督模型；
  - 裁定 4 收口 `rr-hal` 板特定缺省，触及现有 HAL 后端与描述符 schema（ADR-0012）；
  - 控制原语集合要覆盖不同大小的机器人所需的执行器与反馈类型，又必须克制膨胀以守住
    "非常稳定"——这条张力留给实施批定标尺。
- 迁移成本的地板：机制核已覆盖的能力，换平台近乎零改动；覆盖不到的（新执行器种类、缺的
  硬件），成本有界且有明确归属，不假装为零。
- 实施批排期：本裁定只落设计边界；下沉到哪个版本、与 0.0.6 树莓派真件批 / 0.0.7 ESP32 批 /
  0.0.8 模块分层批如何衔接，由后续版本方案排，本裁定不锁实施时点。

## 不做清单

- 不引入 async 运行时进传输/机制核执行环（沿用 ADR-0008 裁定 1：传输同步阻塞，async 只进
  模块侧）；
- 不把"跨平台"表述成"同一份 payload 到处装"——是机制核跨、主承载层按能力叠加；
- 不为本裁定预先创建任何 crate/目录结构或改 `contracts/` 字节布局（结构落点见 architecture.md
  §3 的规划落点注记，实体进度见 status.md）。

## 修订记录

### 修订 1（2026-10-09，0.0.5 第 III 轮立项）：切线改按"四类供给齐备度"，三处窄缝立为跨 OS 的实施前提

第 II 轮（0.0.5 批A–E）真的把机制核切片下沉了一遍，也对表出原裁定在三处口径上的欠账。本修订
不改裁定意图，只把口径收到代码事实与可施工的形状上。

- **① 承载切线：二分 → 三档。** 裁定 1 用"要不要操作系统"画线，裁定 2/3 却按"线程 / 任务 /
  内联子系统"枚举执行单元——后者才是真判据。0.0.7 已裁 ESP32 走 esp-rs **std** + FreeRTOS
  （[ADR-0018 落地方案 0.0.7 §3 Q2](../dev/0.0.7版本洛克三号ESP32系统级验证方案.md)），那是
  一块**有操作系统**（RTOS 即 OS）、却没有主承载层（无 rrd 跨进程监督、无富文件系统、无
  ALSA/CPython）的板；二分线在这里无档可归。现固定三档，判据取裁定 3 四类供给的齐备度：

  | 档 | 判据 | 承载内容 | 现役实例 |
  |---|---|---|---|
  | **全承载档 host** | 四类供给齐 + 进程模型 + 富文件系统 | 机制核 + 全部主承载层 | RK3566 参考机、树莓派（0.0.6 实装） |
  | **轻承载档 rtos** | 四类供给齐，无进程监督 / 无富文件系统 | 机制核 + 主承载层按需（经 `⊙` 桥接取云端能力） | ESP32 + FreeRTOS（0.0.7） |
  | **无承载档 bare** | 仅时基 + 事件循环，无 OS | 机制核切片：单固件自足 或 经桥上灌 | 尚无（真机批触发，见本条末敞口） |

  连带订正：0.0.7 的定位行原写"无 OS 端第一个一等承载平台"，按本表应归**轻承载档**——那半句
  是 0.0.5 第 II 轮改写 0.0.7 时写错的，随本修订改正，0.0.7 §1 同批改。

- **② 机制核外延定名。** 裁定 1 给的是组件清单，没给 crate 级外延，于是第 II 轮之后出现两份读法
  （[ADR-0019](ADR-0019-原子功能模块模型-格件面与组合代数.md) 裁定 7 把原子件与组合件也算进
  机制核）。现定名：机制核 = `rr-ipc::protocol`（字节契约）+ `rr-core`（消息语义 · 模块运行时 ·
  控制原语 · 安全核）+ **待建 `rr-hal-api`**（能力面契约，见本条 ③）。`modules/**/atoms/**`
  定性为**承载层内的机制件**：第 II 轮交付的原子层带 std 形状（`std::thread`、
  `std::sync::mpsc`、`std::env::var`、async HAL 经 `rr3_block_on`），不在 no_std 可达面内——
  把它们算进"机制核"是名义，把它们改到 no_std 可达才是事实。ADR-0019 的求和公式随该 ADR
  修订 1 改写。

- **③ 三处窄缝立为跨 OS 的实施前提。** 裁定 3 说"平台只需提供四类供给"，但按今天的接缝形状平台
  **提供不了**——三条接缝的签名全是 std 的。本修订把这三条列为第 III 轮强制内容：

  | 接缝 | 今天的形状 | 阻塞了什么 | 定形 |
  |---|---|---|---|
  | **能力面**（件 ↔ 硬件） | `rr-hal` 七 trait 全挂 `#[async_trait]` + `Send + Sync`，件侧经 `rr3_block_on`（`yield_now` 自旋） | 件把 std 的调度形状当成机制；一次调用 = 一个装箱 future | `rr-hal-api`：同步签名 · 去 `Send + Sync` · 值类型去 `String`；async 留模块侧（与 ADR-0008 裁定 1 同线） |
  | **总线**（单元 ↔ 单元，即 `⊙`） | `Rr3TransportConn` 唯一实现路径是 `impl<T: std::io::Read + Write>`；`uart` 整模块 `cfg(any(linux, macos))` = 宿主侧开串口，不是板侧 | **无 std 的板接不进总线**——本 ADR 核心价值唯一的结构性阻塞点 | 机制核内两方法窄缝 `Rr3ByteStream`；conn 面在其上 blanket impl 一次，`std::io` 走 adapter，**三实现的行为与线上字节零改动**（签名面要加适配——见本条 ①/修订 3 ①，勿按"零改动"字面理解） |
  | **注入**（策略 → 件） | 17 份 `assemble.toml` 全 `handles=[]` / `ops=[]`，无读者、无校验 | 缺格降级环空转、裁剪无法表达、裁定 4 的"就绪句柄注入"停在文字 | `handles` / `ops` 定形并被装配段校验，缺项即该格 `Degraded`（同一处即 ADR-0019 的 L3） |

- **④ 描述符分七段（补强裁定 4）。** 裁定 4 要描述符收"绑定 + 物理参数 + 内存与时基供给的取值"；
  批D④ 只落了 `[hardware]` 九个物理绑定键，四类供给的取值**无处表达**（传输后端走
  `RR3_HAL_BACKEND` 环境变量，游离在描述符之外）。现定形**七段**（v0.9 修订 3 订正段数——含既有 `[os]`，此前写"六段"漏计）：`[platform]`（芯片平台档——决定后端族
  与供给）、`[supplies]`（四类供给的取值）、`[slots]`（`present` = 本板物理在位集，缺格从此是
  声明而非反推）、`[bindings]`（格→件）、`[enabled_slots]`（本形态启用集）、`[hardware]`（底板
  走线）。分段的目的是让"换底板 / 换芯片 / 裁剪形态"各只改一段——这也是"板 = 数据"成立的确切
  条件：**硬件是芯片平台，不是具体底板**，`[platform]` 与 `[hardware]` 必须在数据面上分开。

- **⑤ 零堆降为敞口（收窄裁定 3 第 2 项）。** 裁定 3 写"有堆则用堆，无堆则用静态/定长区"。实况是
  `rr-core` 以 `core + alloc` 达成（帧组装产 `Vec<u8>`、`Rr3FrameBuf` 分配），**no_std 可达 ≠
  无堆可达**。口径改为：core + alloc 是已达成面也是目标面；静态/定长区路径列**显式敞口**，等一块
  真无堆的板再裁。architecture §12.1 的"no_std 可达"一栏不再隐含"无堆"。

- **⑥ 点验矩阵定形（补强裁定 6）。** 裁定 6 把矩阵定为"部署完成"的定义，但第 II 轮结束时它只有
  名字没有内容（architecture/ADR/conventions 共 13 处引用、零行列，0.0.6 与 0.0.7 两份实机方案
  都不引用它）。现定形六列：① 字节契约对 golden 逐字节 · ② 机制核编译面（目标三元组 + 无 std
  逃逸与无全局分配器 tripwire）· ③ **供给自证**（port 交时基分辨率与单调性、内存模型、事件循环
  形态、传输是否保消息边界，与 `[supplies]` 逐键核对，不一致即红）· ④ 描述符装载（全键落位、
  未知键与坏值当场点名、缺格显式降级）· ⑤ 安全核逐拍一致（在目标上**真跑**，不只是编译过）·
  ⑥ 生命周期（注册→心跳→分发→节拍→断开→重启；无承载档只跑单固件环）。每块新板填一行，跑不到的
  格按裁定 6 原文登敞口。**0.0.6 作为全承载档首行实录、0.0.7 作为轻承载档首行实录，两版改用它
  收口**——"新增一块板要花多少"第一次成为可估的数，而这个数就是本项目成立的理由。

- **本修订不假装结清的敞口**：无承载档（bare）至今没有实现路径。0.0.7 的
  `tools/esp32-uart-echo` 只复用 `rr-ipc` 字节面、绕过 transport trait，机制核的运行时与消息
  语义从未在一枚 MCU 上跑起来过。把三处窄缝立为实施前提，正是为了让这一档从"设计里存在"变成
  "可施工"。实施载体 = 0.0.5 第 III 轮：批I 能力面契约 / 批J 总线窄缝 + 描述符七段（修订 3 ② 订正段数） / 批K 件级
  对拍门 + 点验矩阵 + 第二形态。

### 修订 2（2026-10-09，第 III 轮开工前收口）：无主承载层形态的寻址 · 能力面契约的增长律 · 时序预算位

修订 1 把三处窄缝立为实施前提之后，二次压力测试查出本裁定自身留下的三处空白——不补，批I/J/K
开工当周就会卡住。三条都**不改既有裁定的意图**，补的是"意图之下缺少的落地条件"。

- **① 无主承载层形态的寻址与生命周期（补裁定 1 / 裁定 2）。** 裁定 1 说无 OS 的板"可为完整自足的
  极小机器人"，裁定 2 说模块对外可见面不因落地形态改变。两句合起来今天**不成立**：机制核的模块运行时
  第一步是注册，而 `task` 号由 rrd 分配（`0` 广播 / `1` rrd / `≥2` 模块三段是 `rr-core` 的常量真值，
  `RR3_TRACE_ID_DIRECT = 0` 的"非代理"语义也以基座在场为前提）。没有 rrd 的自足固件里，task 没有分配者、
  目的地 `1` 不存在、代理路由无处可谈。现定三条：

  1. **寻址随平台供给**：无主承载层形态的 task 号由**描述符静态分配**（`[platform]` 增任务号位或等价的
     构建期常量表）。三段号空间的**语义不变、分配者变**——`rr3_task_kind` 判定照旧成立，"谁来发号"从
     rrd 换成装配段。这正是裁定 2"可见面不变、执行单元由平台供给"的应有之义，不是新增例外。
  2. **运行环有两个合法入口**：`Rr3ModuleRuntime` 的 `Registering → Online { task } → Down` 面向"有基座"
     形态；自足形态走**同一状态机的退化用法**——由装配段直接给 `Online` 态与静态 task，不经注册握手。
     机制核**不为自足形态新增第二套状态机**（预置 task 的构造入口归实施批，不在本修订定形状）。
     关键口径：`Down` 在无基座形态下的处置不是"交 supervisor 重启"，而是"交平台复位"——裁定 2 原文
     "裸机面 = 运行环复位"已含此意，此处把它与生命周期表对齐。
  3. **`⊙` 的两种拓扑**：经桥接（对端有 rrd，注册/心跳/前缀归属全按现有语义）与自足（无 rrd，只跑
     单元内 `⊗` + 本地安全核）。**自足形态不宣称能发布主题**——它可以产帧、可以经桥上灌，但在没有
     注册中心的固件里"发布"无处投递。architecture §12.7 的谱系按此重述，§14 自检句"这块没 Linux 的板
     跑的是什么"由此才有完整答案。

- **② 能力面契约的增长律与对象形状（补裁定 1 新成员 `rr-hal-api`）。** 它要"契约级冻结、只增不改"，
  又要"覆盖不同大小的机器人所需的执行器与反馈类型"（本档"后果"段自己点出的张力）。现定三条规则，
  批I 的验收以此为准：
  1. **增长只走"新增 trait / 新增值类型"，不走"既有 trait 加方法"**——后者要求所有实现者与消费者同批改，
     等于变更契约语义。新执行器种类（步进、电调、气阀、多轴）= 新 trait + 新格（走 ADR-0012 立格判据）；
     既有 trait 的方法集是冻结面。
  2. **对象形状分档**：`bare` 档**禁用 trait 对象**（`dyn` 的 vtable 与潜在分配在单固件里不可预算），
     该档只允许泛型单态化或编译期常量分派；`rtos` / `host` 档允许 `dyn` 句柄（跨线程移交的现实需要）。
     因此 `rr-hal-api` 的签名必须**两种用法都写得出来**——这条不定，批I 会在第一个裸机后端上返工。
  3. **堆依赖显式化**：能力面值类型一律定长或借用（`&[i16]`、定长数组 + 长度），堆只出现在承载层。
     这与"core + alloc 为已达成面"不矛盾：**机制核允许 alloc，但能力面契约不许把 alloc 写进签名**。

- **③ 时序预算位（补裁定 5 的"定长、确定性调度"）。** 裁定 5 用"执行这张图的定长、确定性调度属于机制"
  来定义控制环归属，但全设计从未对它提出**可测要求**：无周期上界、无抖动预算、无安全核最坏执行时间与
  心跳/看门狗的时序关系。于是"同一张控制图在裸机定时器里跑、行为逐拍一致"只在**数值语义层**成立
  （对拍用例所证），在**时序层**无证据。现补：描述符 `[supplies]` 增时序位（名义周期与允许偏差、
  安全核调用间隔上界），点验矩阵增"时序达标"一项——实测法随 0.0.7 真板批取得（板上取周期直方图），
  本机只能取"声明与代码常量一致"这一半。**在拿到真板时序证据之前，§12.5 那句必须带条件读**：
  逐拍一致 = 数值一致，不含实时性保证。

### 修订 3（2026-10-09，批I 开工前最后一道对表）：窄缝落点 · 段数订正 · 禁词作用域 · 执行宿主前置

修订 1/2 定形之后再压一遍，查出四处"写下来了但按仓库现状做不到"的地方。本修订把它们当场收口，
不留给实施批去"边做边猜"。

- **① 窄缝落点定名（补修订 1 ③ 第二条）。** `Rr3ByteStream` 落 `rr-ipc` 的 `transport` 面内一个
  **no_std 可达的子模块**（帧层已在那儿），而不是新 crate。但必须先解除一件既存障碍：`rr-ipc/src/lib.rs`
  把整层写成 `#[cfg(not(target_os = "none"))] pub mod transport`——**裸机目标今天连 transport 模块都不编译**，
  窄缝若放在该层内而不拆门，就等于不存在。裁定：把 `std::io` 依赖隔离到 impl/adapter 侧，让窄缝本身在
  `target_os = "none"` 下可编译。连带订正 v0.8 §12.8 那句"uds/shm/uart 三实现零改动"——准确说法是
  **三实现的行为与线上字节零改动**，签名面必然要加适配（blanket impl 换底不可能不触碰实现声明）。
- **② 描述符段数订正：是七段，不是六段。** 修订 1 ④ 列了 `platform/supplies/slots/bindings/enabled_slots/hardware`
  六段，但 `rrd/src/profile.rs` 与查册门测试都**硬要 `[os].route`**（`expect("profile 缺 [os] route")`）。
  写"六段"会让批J 第一步就撞门或去删 `[os]`（那就是改既有契约）。定形为**七段**：`[os]` + 上面六段。
- **③ 板无关禁词的执法作用域。** `rr-registry/src/atom.rs` 的 `RR3_BOARD_TOKENS` 禁
  `gpio/i2c/pwm/uart/ina219…`，而 `rr-hal/src/descriptor.rs` 的在册键恰恰是
  `gpio_led_line/pwm_chip/i2c_bus/ina219_addr`——**同一个断言不能同时作用这两面**，否则注入面一写真值就全红。
  现定：禁词面 = **件声明面（`atom.toml`）**，那里永远不许出现板词汇；**描述符 / `handles` 键名是板数据面**，
  板词汇出现在那儿正是它的职责。另明确：扩 `[hardware]` 键仍走 `descriptor.rs` 自己声明的契约级评审
  （R11），**该评审排进批J 产出**，不是"到时候再说"的隐含前提。
- **④ 执行宿主前置（本裁定的验收依赖它）。** 点验矩阵的 ②⑤⑦ 三列需要目标 runner。当前开发机的实况：
  `rustup toolchain list` 只有 `stable-x86_64-pc-windows-msvc`，无 xtensa 目标、无 aarch64-musl target、
  无 ESP-IDF、树莓派离线、外设未采购——`tools/ci/rr-core-xtensa-check.sh` 在这台机器上**恒走 SKIP**，
  而该脚本既不在 `check.sh` 也不在 `ci.yml` 的 job 里。故规定：**矩阵与一切"真跑"判据必须在写名的执行宿主上跑**
  （首选：WSL2 补 xtensa/musl target + qemu；或指定那台已装 esp 工具链的宿主），宿主清单落 0.0.6/0.0.7 的
  "执行前置"节；宿主未就位时，相关格一律记 **"无载体"**，不得记 SKIP 通过、更不得记 PASS。
  这条是本 ADR"不以设计已覆盖充当已验证"纪律的具体化——没有它，修订 1 ⑥ 的矩阵就是一张填不满的表。
