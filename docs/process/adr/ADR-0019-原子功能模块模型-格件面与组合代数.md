## 背景

ADR-0018 把底座切成机制核与主承载层，并确立"跨操作系统快速部署"为核心价值。要让这个价值可施工，还需要一条**模块内部**的
组织法则：把"一个机器人形态"拆到可复用、可裁剪、可门禁的最小单元。现状是五个粗粒度模块（`rr3-sense/act/interact/power/connect`）
各是一坨手写 `main.rs` + 若干机制文件，粒度太粗、裁剪只能整进整出、机制与策略混在同一文件——不满足"每个原子功能一个文件夹、
足够抽象、便于维护"。

0.0.8 已尝试给模块内部做五层拆分（boot/rpc/dispatch + 机制文件原位），但它仍是"以模块为单位"的手术，没有把**原子**立成一等单元。
本裁定把这套意图升级为 rock3 的模块组织模型：**格（固定坐标）→ 件（可换原子）→ 组合件（装配出来的执行单元载体）→ 面（职责视图）**，
并用一组代数（`⊗` 装配 / `⊙` 编排）规定谁能和谁拼、拼成什么。ADR-0017 的机制/策略分离、ADR-0007 的控制面分层、ADR-0018 的
机制核，都在这套语言里各归其位。

## 决策

### 裁定 1：架构语言四层（格 / 件 / 组合件 / 面）

| 中文 | 英文 | 定义 | 落点 |
|---|---|---|---|
| **能力格** | **Slot** | 机器人能力的最小归类坐标，**固定不变、只增不改** | `contracts/slots.toml`（现 21 格：base 5 / body 12 / cognition 4） |
| **原子件** | **Atom** | 填一个格、不可再分、只含机制的最小实现件；每个原子一个目录，板无关、经描述符注入句柄 | 源码目录（0.0.5 重铺） |
| **组合件** | **Composite** | 两个及以上原子件按 `⊗` 装配得到的组件，是**执行单元的承载** | 运行期落为一个执行单元（进程/任务/内联子系统） |
| **形态面** | **Facade** | 按**职责面**暴露的组合件集合；= 声明(`.manifest`) + 生成(样板，`rr3-mkmod` 产出) + 组合件装配(Composite 承载) | 见裁定 4 的固定四面 |

核心关系式（全文统一，不得改写语义）：

```
面 Facade = 声明（.manifest）+ 生成（样板）+ 组合件装配（Composite 承载）
格 Slot   ←固定→   件 Atom   ←可变→
功能 = 原子件 ⊗ 装配 → 组合件 ⊗ 再装配 → 形态面
```

统一自检句：`ServoAngleSet 是 act.servo 格上的原子件，由 actuation 组合件 ⊗ 装配承载，经运行面暴露。`

**术语消歧**：现 `profiles/<机型>.toml` 的 `[faces]` 语义是"某模块在本形态启用哪些格"，与本裁定的职责面 Facade 不是一回事。
本裁定把 profile 里的 `[faces]` 改名 **`enabled_slots`**（连带改 ADR-0012 裁定 3、architecture.md 装配单节、`rr-registry` 查册门字段名），
腾出"面/Facade"专指职责视图。

### 裁定 2：组合代数 `⊗` 与 `⊙`（`⊙` 按 ADR-0018 跨 OS 化）

| 算子 | 时相 | 边界 | 类型 | 通道 |
|---|---|---|---|---|
| `⊗` 装配 | 装配期 | 执行单元内 | `A×A→C/F`、`C×A→C/F` | 函数调用 |
| `⊙` 编排 | 运行期 | 跨执行单元 | `F×F→F_sys` | **经 transport 抽象**：Linux = UDS，无 Linux 平台 = UART/SPI/BLE 等（承 ADR-0008、ADR-0018 裁定 3） |

- **`⊗` 五性质**：类型律、闭合律、结合律、幂等律，以及**地位律——`F⊗F` 非法**：面是与执行单元边界绑定的职责视图，面之间只能 `⊙` 编排；
  允许面直接装配就等于"一个执行单元装下所有功能"，机制核分层即失效。**`F⊗F` 违反即 fail-closed 拒绝**（门禁，非警告）。
- **`⊙` 的通道不写死 IPC/syscall**：这是与外部模板的必要分歧——rock3 的价值是同一机制核要跑到没有进程/系统调用的 MCU，
  故 `⊙` 定义为"跨执行单元经 transport trait"，落什么链路按平台 port 决定。
- **组合一律经组合件承载，禁薄胶水串联**：薄胶水（散落的 if/转发调用直接串原子、无组合件实体）无契约、无测试、复杂度散落、无问责，
  使系统不稳定；装配契约（输入/输出/生命周期/错误传播）必须落在组合件代码内，组合件自身要有 tests 且接线 CI，`main` 只启动组合件不直连散原子。

### 裁定 3：每格一件 + 不留空格 + 格格双达标（rock3 化，非全盘照搬）

- **每格一件**：每个能力格落一个原子件，同类件塌缩归一。格是架构承诺，**不留空格**——空格意味着该能力靠各处私搭乱建维持。
- **格格双达标**（两判据都要满足）：① 落点件**有 tests 且接线 CI**（承 `conventions.md` §2 七步门，"有测试未接线 = 未达标"）；
  ② 落点件**非死件**（有有效扇入：真实跨单元消费者，`#include`/伞形引用只作初筛不计扇入）。
- **扇入口径按 rock3 分档（不套用外部模板的"全格无豁免 ≥3"）**：`N ≥ 3` 作为**新建/收编跨形态复用机制原子**的准入杠杆；
  但 rock3 有天然的单消费者能力格（如 `power.battery`、`sensor.imu` 在某形态只有一处消费），硬套 ≥3 会把合理单件判成违例。
  故沿用 **ADR-0012 裁定 6 的成格判据**（≥1 真实依赖者或 ≥3 潜在场景、落盘格 grandfather 豁免）作为**格**的门槛，
  `N≥3` 只加在**原子件复用**上。二者分档，不互相覆盖。**（此为 rock3 化判断，若你要求全盘 ≥3 可改。）**

### 裁定 4：形态面 = rock3 固定四职责面（不照搬外部面名）

rock3 采"每个组合件横跨固定职责面、四面是视图不可拆成独立执行单元"这条结构。**四面用 rock3 具身语义命名**：

| 面 | 职责 | 典型 |
|---|---|---|
| **接入面 intake** | 对硬件/对外的入口：RPC 请求、传感器与事件入、下行指令入 | 收 `servo/command` |
| **运行面 operate** | 机制执行：采集、控制环、渲染、播放、编排原子 | 跑 servo 控制图 |
| **状态面 state** | 可观测：状态流、回读、计数、配置摘要 | 发 `servo/state` |
| **守护面 guard** | 治理：安全核、降级、看门狗、越权拒 | 限位/过流/低电兜底 |

**关键后果**：一个组合件天然横跨这四面，四面不是四个可独立拆出的执行单元。原 `rr3-sense/act/interact/power/connect` **不再是"模块"这一等概念，
而降为"组合件按能力域的一种分组"**；组织的主轴变成"格→原子→组合件→面"，能力域（感知/执行/…）与运行时职责面（四）两条轴正交。
**（四面命名与"是否就用这四张面"是 rock3 化判断，可改；但"面=运行时职责视图、非功能域"这一刀建议保留，否则形态与平台无法正交。）**

### 裁定 5：机制与策略分离四层 + 零策略载荷

自内向外：

- **L1 机制**：不含任何策略的原子件（代码）。
- **L2 契约**：接口与数据结构（公开头/公开 trait，承 §5）。
- **L3 注入**：策略经 `ops` 函数表 + `.manifest` **数据化注入**——原子件只见 ops 指针与描述符给的绑定句柄，不见厂商、不见产品决策。
- **L4 策略**：具体决策（阈值、编排、人格、对话规则），落 brain 或形态配置/生态层。

**两条硬规（静态断言、fail-closed）**：
1. 策略只经 `ops` 函数表 + `.manifest` 注入，不得在机制件内 `include` 具体策略、不得 `if vendor == …` / `if product == …`；
2. **机制核零策略载荷**——机制件里出现厂商名、产品名、业务阈值即门禁失败。这把 ADR-0017 的"策略不进模块"从人工评审升级为可扫断言。

### 裁定 6：原子件准入三问

任何拟新增/保留的件，三问全过才算原子件：① 是机制吗（不含业务策略/厂商/产品决策）？② 是收敛型抽象吗（收编后总行数下降，抽象带语义而非仅签名，非伪抽象）？
③ 复用达标吗（按裁定 3 的扇入分档）？不是机制 → 归策略、迁生态层；不是收敛型 → 禁止；复用不达标 → 就地内联，不建件。

### 裁定 7：与既有 ADR 的衔接与取代

- **取代 ADR-0017 的实施定位**：0.0.8 的"每模块拆 boot/rpc/dispatch + 机制文件原位"被本模型吸收——机制文件即"原子件"，boot/rpc 层即组合件对四面（接入/运行/状态）的分装。0.0.8 不再作为独立施工批，其规格并入 0.0.5 原子重铺。
- **修订 ADR-0002**：`rr3-sense/act/…` 从"进程模块"降为"组合件的域分组"；执行单元粒度由组合件决定，与原子数解耦（原 `RR3_REG_MAX_MODULES=16` 约束的是运行时执行单元，不再限制原子数）。
- **对齐 ADR-0018**：机制核 = 本模型的"原子件 + 组合件 + 安全核（守护面）"之和，`no_std` 可达；主承载层 = 经 `⊙` 编排进来的更重组合件与 brain。
- **对齐 ADR-0007**：反射环与高频控制图落运行面、永不进 `⊙` 跨单元通道；`ops` 注入的正是控制图的参数与选择。

### 裁定 8：门禁子集（取可静态执法的，不引入体积总账）

采纳能机器执法的几条接进 `check.sh`：机制核零策略载荷（grep 厂商/产品/阈值）、每格一件、准入三问留痕、`F⊗F` fail-closed、
组合经组合件承载禁薄胶水、五件套计数（`.manifest`+入口+实现+装配清单+唯一私有头）、`main` 入口行数上限（沿用 0.0.8 的 ≤80 行雏形）、
格格双达标的"有 tests 接线 CI"。**不引入外部模板的"体积 <N 行 + 迁出账 + 三账分立 + 阶梯门禁"**——rock3 代码量未到临界，过早设总账是负收益（可改）。

## 备选与否决

- **备选 A：维持 5 粗模块 + 0.0.8 内部分层，不立原子为一等单元**——否决：裁剪粒度仍锁在模块级，做不到"每原子一文件夹、跨形态复用、按格塌缩"，"足够抽象"落空。
- **备选 B：把外部模板的格表/四面英文名/体积账整套搬进 rock3**——否决：那是搬内容非搬方法，与 rock3 机器人域和现有 `slots.toml`/`naming.md` 冲突。
- **备选 C：面 = 功能域（把 sense/act 当 Facade）**——否决：那等于没换组织法，仍无法让"形态、平台、职责"三轴正交；域降为组合件分组、面取运行时职责，才成立。

## 后果

- 正面：模块组织有单一法则（立格→造件→成面），裁剪与复用落到原子粒度且可门禁；机制/策略分离从纪律升级为静态断言；与 ADR-0018 跨 OS 自然拼接。
- 代价与敞口：
  - **这是一次全仓源码结构重铺**（五模块 + brain 拆成原子目录并生成面），体量接近一次大重构，须由 0.0.5 分批施工、每批带验收，不能一把梭；
  - 能力格若为原子化再细分一层，`slots.toml`/`topics.toml` 要同批改（契约只增不改纪律）；
  - `[faces]`→`enabled_slots` 改名触及 profile、`rr-registry` 查册门、若干 dev 方案，须连带修；
  - 四面（裁定 4）与扇入分档（裁定 3）是本 ADR 的 rock3 化判断，实施前你可一句话改写。

## 不做清单

- 不引入外部模板的具体模块命名、格表、编号体系、体积硬线、禁词表；
- 不在本 ADR 落 `.rs`、不改 `contracts/` 字节布局、不建原子目录（结构落点见 architecture.md 与 0.0.5 施工批）；
- 不删除 ADR-0017（其设计裁定保留，实施定位由本 ADR 承接改写其"后果"）。

## 修订记录

### 修订 1（2026-10-09，0.0.5 第 III 轮立项）

第 II 轮把"格 → 件 → 组合件"真的铺进了源码（17 个原子目录、21 格唯一覆盖、六单元入口 16–18 行），
也照出四层语言与门禁子集里四处定得过满的地方。本修订把口径收到"能施工、能门禁"的形状上。

- **① 第四层 Facade 降为职责视图，不建第四份 manifest（改判裁定 1）。** 裁定 1 把"面"写成
  `= 声明（.manifest）+ 生成（样板）+ 组合件装配（Composite 承载）`。第 II 轮只交付了前两层声明物
  （Atom `atom.toml` + Composite `composite.toml`），全仓无 facade manifest、`rr-registry` 无
  Facade schema——**因为面没有需要独立声明的内容**：一个组合件的接入/运行/状态/守护四段职责，
  全部可由它的 `composite.toml`（装了哪些件）+ 各件的 `atom.toml`（占哪个格、发哪些主题）推出。
  再加一份 facade.toml 就是第四真值，四处可漂移。现改判：
  - 关系式右半改为 `面 Facade = 组合件的职责视图（由 Composite 声明 + 件的归属推导，无独立声明物）`；
  - 四张面（接入 / 运行 / 状态 / 守护）**保留**——它仍是读图与评审的好用切分，§12.2 的"组合件跨
    四面不可拆"原句不动；
  - `architecture` §13"五件套齐全"一行的"每个组合件/**面** `.manifest`"改为**只按组合件计数**；
  - 生成侧（`rr3-mkmod`）不再为面产出样板。

- **② 双达标判据②改判为"件级逐拍对拍"（改判裁定 3）。** 原判据②"落点件非死件：有有效扇入、
  真实跨单元消费者"在第 II 轮**零执法**——扇入要全链接图加人工判断，⑥ 只断"工程有 ≥1 测试且接线"，
  ⑦ 完全不查。于是 `sensor.env` / `sensor.imu` 两格由 2 行纯注释件（无机制、无发布、无消费者）
  名义占住，"每格一件 + 双达标"与"不留空格"同时空转。现把判据②换成机器可判的三条：

  | 判据 | 内容 | 执法形态 |
  |---|---|---|
  | **件级逐拍对拍** | 件的公开面必须能构造一条"合成输入序列 → 输出序列"的确定性用例：无 IO、无线程、无墙上时钟、同输入两跑逐拍相等（范式已在 `rr-core/src/control.rs` 的 `same_control_graph_beat_for_beat_identical` 立住） | 新增静态可数门：每件的 `#[cfg(test)]` 面须含一条命名过 `beat_for_beat` 的用例，⑥/⑦ 接线 |
  | **依赖闭包** | 件的外部依赖 ⊆ {`core`, `alloc`, `rr-ipc` protocol, `rr-core`, `rr-hal-api`}；出现 `use std::` / `use rr_hal::` 即红 | 新增 grep 门，扫 `modules/**/atoms/**`（brain 两件式豁免沿用） |
  | **字面量位点清单** | 件内不得留业务阈值与厂商/产品名；已有位点列清单逐条迁出（DoA 30° 分档阈、wifi 密码 8 位、sim 假 SSID 三行、`RR3_HAL_SIM_BT_UP`） | 清单登记 + 评审（**不再宣称 grep 命中即红**，见本条 ④） |

  扇入降为**评审项**（准入三问第③问仍按它判）。这一换的额外收益是关键性的：写不出对拍用例的件，
  必然是里面藏了时钟、线程或 std 形状——**第 II 轮 `atoms/led`（自持线程 + `mpsc` +
  `recv_timeout`）与 `atoms/bt`（件内读 env）这两件病，正是这条判据天然会当场拒绝的形状**。
  占位件（env/imu/charger 三件）给显式豁免：登记"占位中 + 填实触发条件 = 真件采购批"，豁免随填实
  自动失效；空格仍不允许，但**占位件不再算已达标**。

- **③ L3 注入面从口号变成被校验的数据（补强裁定 5）。** 裁定 5 的 L3 写"策略经 `ops` 函数表 +
  `.manifest` 数据化注入，件只见 ops 指针与描述符给的绑定句柄"。第 II 轮的实况：17 份
  `assemble.toml` 全部 `handles = []` / `ops = []`，且**全仓无任何代码或门禁读它**——件拿参数的
  真实通道是 `config.toml` 解析在组合件里做、把 cfg 结构体当形参传进件（`servo` 一例：
  `rr3_servo_parse_args(args: &Value, cfg: &Rr3ServoCfg)`）。这确实是注入，但它不可校验、也不表达
  "哪些件要哪些句柄"。现定形（与 [ADR-0018](ADR-0018-跨操作系统移植-机制核与主承载层分离.md)
  修订 1 ③ 第三条同处落）：`[assemble.handles]` 声明件用哪个能力面 trait ← 绑描述符哪个键、
  `[assemble.ops]` 声明件暴露哪些参数槽 ← 取哪个 config/profile 键；装配段（Linux 为 rrd，
  无 OS 为机制核装配段）**校验缺项即该格 `Degraded`、点名到件**。三层读法随之校正：L1 = 件
  （承载层内的机制件，非 no_std 面）、L2 = 契约（含新建的能力面契约）、L3 = 注入数据面（本条）、
  L4 = 策略（brain / 形态配置 / 生态层，不动）。

- **④ 机制核外延与 ADR-0018 定名对齐（改判裁定 7 的求和公式）。** 原句"机制核 = 本模型的
  原子件 + 组合件 + 安全核（守护面）之和，`no_std` 可达"与代码不符：no_std 可达的是
  `rr-ipc::protocol` + `rr-core`，而 13 个 Rust 原子件里 4 件带 `rr_hal` 类型耦合、3 件带
  async HAL 句柄、2 件自持 std 线程/env，组合件全 std。现改为：

  > 机制核 = 字节契约（`rr-ipc::protocol`）+ 消息语义与模块运行时（`rr-core`）+ 控制与安全核
  > （`rr-core::control`）+ 能力面契约（待建 `rr-hal-api`）。原子件与组合件是**机制在承载层内的
  > 物理组织**：其中可下沉的语义正被逐片提出进机制核（第 II 轮批D 已提出总线语义、运行时、控制
  > 与安全核四片），其余留在承载层，按 ADR-0018 修订 1 的三档叠加。主承载层 = 经 `⊙` 编排进来的
  > 更重组合件与 brain。

  这条不是文字让步，它定的是施工顺序：**先把件从 std 形状里解出来（批F/G），再谈"件可在裸机跑"。**
  在此之前 §14 自检句"这块没 Linux 的板跑的是什么"的诚实答案是"目前只有字节契约在 MCU 上跑过"。

- **⑤ 门禁子集补三件、撤一条宣称（补强裁定 8）。** 新增可静态执法的三条：件级对拍用例门、件级
  依赖闭包门、`assemble` 注入面校验门。同时撤下一条**已写但未执法**的宣称：裁定 8 与 architecture
  §13 都写过"机制件业务阈值 grep 命中即红"，而 `check.sh` ⑦ 的注释已如实记下"业务阈值字面量无
  可靠静态判据（注释里的版本号同为点分数值），执法面 = 板无关门 + 描述符/ops 注入纪律 + 评审"。
  文档口径不得高于门的实际断言——阈值项在 §13 表里改标"评审 + 位点清单"，`fail-closed` 只留给
  真能判的（厂商/产品禁词、`F⊗F`、五件套、依赖闭包、契约冻结、层界单向）。

- **敞口**：`rr3-brain` 的 Python 面（四件两件式 + 机制本体 `.py` 原位）不在对拍判据与依赖闭包门
  的适用面内——它按 ADR-0014 是宿主档专属承载，Rust 化随 ADR-0016 线；在 Rust 化之前，brain 的
  件级达标一律记"登记豁免"，不写作已达标。
