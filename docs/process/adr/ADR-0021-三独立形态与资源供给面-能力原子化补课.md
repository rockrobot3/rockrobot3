## 背景

过去一周 ESP32 实机开发把底座的抽象欠账以**硬件损失**的形式付了利息：轨压被拉塌到 BOD 复位循环、
屏点不亮、舵机推到机械死点持续堵转发烫（用户现场另报告一次**插线冲突导致舵机过热烧毁**——此条仓内
只有口头与 README 现场注记，无独立取证记录，故本轮把它当**待取证事实**引用，不当实录引用）。
这四件事不是四个 bug——它们是**同一个错误的四个症状**：
底座把"平台事实"当代码写、把"资源"当不存在、把"能力"抽象成了动词而不是对象。

以下六条是可以在文件里指到的事实，不是推理：

再加一条对核心口号的事实核查：architecture §12.8 的收口句"部署到一块新板 = 写两件码 + 交七段描述符 +
填一行矩阵"，其适用条件 v0.9 只补过一条（新执行器种类要新格新 trait）。本周暴露的是**另一类**阻塞：
`esp-idf-hal` 的 `LedcDriver::new`/`UartDriver::new` **需要具名引脚类型，无法由 `i32` 常量构造**
（`board.rs` 引脚段自述）。这意味着引脚编号在全仓必然至少出现两次（一次数据、一次类型），
"两件码"这句若不写清这一处不对称，就是在宣称一个**结构上做不到的**零代码。

**根因判据（本轮立为收口标准）**：每一个坑必须升格为**五处之一**——① 供给位 ② 能力面 trait
③ 描述符键 ④ 格或主题 ⑤ 门禁判据。**升不进这五处的教训，只算一次现场处置，不算收口**。
配套判据：**同一类故障在第二个平台重现 = 抽象失败**（引脚冲突这条已经跨平台**出现过两次**：ESP32 上
实际撞了一次并被迫改线，树莓派路线上同一类互斥被文档预测到、靠换路线侥幸避开——"侥幸避开"不算抽象成功，
因为下一个形态不会读注释）。

## 决策

### 裁定 1（N-1）：三形态是**并列独立机器**，不是主形态与它的附件

| 形态 | 承载档 | 独立性 | 与另外两者的关系 |
|---|---|---|---|
| **RK3566 桌面具身形态**（Radxa ZERO 3 目标） | host 全承载 | 独立整机：自己配网、自己调云 API 大模型、自己带屏 | 与 ESP32 **零关系**（无桥、无共享进程、无共享供电） |
| **树莓派形态**（0.0.6 已点验的那台） | host 全承载 | 独立整机，是 host 档的**现役证据载体**，不是 RK3566 的替身 | 与 ESP32 **零关系** |
| **ESP32 微型形态** | rtos 轻承载 | 独立整机：**自带 OLED 表情面 + 双轴云台 + 双麦 + 配网**；认知经桥到某个 host 形态，桥只是它的可选能力升级 | 桥的一端是一台 host 形态机器，不是一台机器的两半 |

**作废面**（旧句原文**不改写**，在旧句处加指针，改判以本 ADR 为源）：
① [0.0.5 方案 §2.6 R31](../dev/0.0.5版本洛克三号对齐与裁定方案.md) 的 Q2"四件全挂 ESP32 协处理器"——
"协处理器"这个定性作废（施工事实保留：四件确实挂在 ESP32 上做完并实测）；
② [0.0.6 方案 §5.4 BOM](../dev/0.0.6版本洛克三号树莓派验证方案.md) 第 2/4 行"由 ESP32 协处理器承载替代"注——
"替代"关系作废：树莓派形态缺外设就是缺，不叫由谁替代；
③ [模块设计索引 §10](../../design/模块设计索引.md) 的 `F-A/F-B/F-C` 谱系——它把"经桥微型"排为"主形态裁剪出来的微型"，
读起来像附件。改为**两轴表**：形态（产品）× 承载档（技术），桥是形态间的一条**链路选项**，不是形态定义。

**这条改判的实际后果**（不是措辞问题）：`[hardware]`/`[pins]`/`[domains]` 必须是**每形态一份**的完整事实源，
不存在"宿主替它管外设"这条退路；ESP32 形态的观测面（欠压、温度、标定）必须在**板自己**的面板上可得，
"经桥让 host 的面板顺便看一下"不构成证据。

### 裁定 2（N-2）：能源是**第七位供给**，同时是**两张格**

判据同 ADR-0018 修订 4 ② 立看门狗那一次："结论引用的能力必须在前提里供给"。本周每个失效结论
（舵机不转 / 屏不亮 / 复位循环）引用的都是"这条轨此刻给得起多少电流"，而六类供给里没有这一项。

**供给位 `[supplies].domains`（数据结构，装载期可校验）**：

```toml
# profiles/<形态>.toml  —— 能源域：谁供、供多大、从哪采、跌破两级阈值怎么处置
[[supplies.domain]]
name = "rail5v"              # 域名，被 [pins] 的 rail 键引用（外键，校验 6 判在册）
nominal_mv = 5000            # 标称
current_cap_ma = 2000        # 该域可持续电流上限（板卡规格书的 SY8801 ~2A 走这里进软件面）
sense = "adc:gp34"          # 电压采自哪里（角色名，不是裸引脚号）；无采样点写 "none"
current_sense = "none"      # 电流采自哪里；"none" = 无逐域电流采样 ⇒ 标定路线 B 禁用、校验 ⑨ 退化为静态峰值加总
mild_mv = 4600               # 轻度欠压阈值
severe_mv = 4400             # 重度欠压阈值（须 < mild_mv）
switchable = false           # 可否由调度切断（T1/T2 这类断电轨 = true）
armed = false                # 接闸：false = 阈值占位、只观测不拒动（沿用 RAIL_GATE_ARMED 纪律）
```

**两张格**（`contracts/slots.toml`，append，schema_version 3）：
`power.rail`（轨压/域压**观测**，owner `rr3-power`，kind event，tier_scope 三档全在——bare 档经本地守护输出行观测）
与 `power.budget`（**能源预算仲裁**：并发峰值电流是否超域上限、超了切谁，owner `rr3-power`，tier_scope 三档）。
`power.battery` **保留不动**（号位只增不改；它读的是"电池"这一个域，与新格的"多域"不是同一对象）。

**三层语义**（谁都能少，不可混）：**供给**=域的存在与上限；**装载期**=静态预算校验（并发峰值 ≤ 上限）；
**运行期**=按档降载调度（`Mild` → 执行串行化/降亮，`Severe` → 拒动）。今日板侧已有的
`AXIS_SETTLE_MS` 串行降级与 `OLED_CONTRAST_LEVELS` 逐级降亮，正是这三层的**未经建模的版本**——
它们被裁定 2 建模后，才是"根据能源的负荷进行资源的裁剪调度"这句话的机械表达。

**执行件对域的需求申报**（进 `assemble.toml`，与 `handles`/`ops` 同批校验）：

```toml
[[atom.demand]]
rail = "rail5v"     # 引用域（外键）
peak_ma = 700       # 单件峰值电流（SG90 堵转 ~700mA/只即此量的来源）
sustained_ma = 120
critical = true     # true = 欠压时优先保它；false = 可被降载切断
```

**边界**：阈值/分压比的**取值**仍受"无真板对拍前不接闸、不 claim"纪律约束（`RAIL_GATE_ARMED = false`
同型）；本裁定立的是**对象**，不是标定值。

### 裁定 3（N-3）：引脚是**三层对象**，角色词表进契约、绑定进 profile、接线进装机档

| 层 | 落点 | 内容 | 换什么要改它 |
|---|---|---|---|
| **角色词表** | `contracts/roles.toml`（新建，契约层） | 每个外设信号一个**角色名**：归哪一格、信号类还是功率类、可否被降载切断、方向、是否 input-only | 加一类外设（跨形态共享，走格+trait+角色三处同批评审） |
| **绑定** | `profiles/<形态>.toml` 的 `[pins]`（描述符第八段） | `role / slot / controller / channel / physical[] / direction / rail / mux_group[] / failsafe` | 换底板、换走线 |
| **接线** | `hardware/<形态>/wiring.toml`（装机档，人读机查） | `connector / hdr_pin / signal=<role> / net / mate / keyed / rated_a / gnd_common` | 换线材、换连接器 |

**八条装载期 fail-closed 校验**（逐条对应本周真实发生或已被预测过的冲突）：
① `role` 在册；② `[slots].present` ∩ `enabled_slots` 所需角色在 `[pins]` 里存在（缺即该格 `Degraded` 并点名角色）；
③ 同一 `physical` 脚不被两个启用角色占；④ 同 `mux_group` 成员不得同时启用（ESP32 的 GPIO16/17↔I2C0、
GPIO18/19↔I2S+硬件 PWM 即此组的两个实例）；⑤ input-only 引脚集（ESP32 GPIO34–39）不得作输出角色；
⑥ 每角色必有 `rail` 且该域在 `[supplies].domains` 在册；⑦ `wiring.signal ⊆ pins.role` 且
`wiring.net ⊆ domains`；⑧ `[pins]` 与该平台的 **role→具名构造表** 对账（见下条不对称）。

**结构性不对称必须写进契约，不许假装全数据驱动**：`esp-idf-hal` 的驱动构造吃具名引脚类型，
所以引脚数字在全仓**只允许出现在平台侧一张 `role → 具名构造` 表**（`tools/esp32-periph-base` 内，
是"第三件码"的一部分），由校验 ⑧ 与 profile 双向对账——表里有、profile 里没绑，或反之，都拒 boot。
这条不对称是"换板零改码"的**真实边界**：数据决定"用哪个角色、接到哪、给多少电"，
平台代码决定"这个角色的引脚在 SDK 里叫什么类型"。architecture §12.8 的收口句按裁定 8 改判。

**回写面**（本裁定直接判错的句子）：`0.0.5增补轮五` 的"UART2 = GPIO16/17……与 0.0.7 实测接线零冲突"
必须订正为**已被推翻**（`board.rs` 自述 GPIO16/17 一装 UART2 驱动即打死 I2C0，故实际用 GPIO18/19，
而 18/19 与 I2S 双麦、点阵 VSPI 预留互斥）。订正后该段的正确形态 = 指向 `[pins]` 与 mux_group 的三条互斥记录。

### 裁定 4（N-4）：`[hardware]` **九键闭集改判**——C4"不扩键"作废，键集由角色词表导出

撤销 [0.0.5 方案 §13.1 C4](../dev/0.0.5版本洛克三号对齐与裁定方案.md) 的"不扩键"裁定。理由不是"想加键"，
是那条裁定的前提被事实推翻了：它假定九键覆盖"这块板/平台是什么"，而三个形态都要屏、
板侧要轨压、要双轴、要 I2S——`display` / `rail` / `i2s` / `servo_tilt` 四个对象在九键外，
其中 `display` 已把 `rr3-interact` 的注入面卡成空数组（见背景表第 5 条）。

改判后的规则，保留 C4 想防的东西（不许自造键位、不许两处漂移）：

1. **在册的定义从"写死的九个键"改为"角色词表的导出"**：`[hardware]` 与新增 `[pins]` 的合法键集
   = `contracts/roles.toml` 的角色集 + 九个既有物理绑定键的存量语义。
2. **未知键仍拒**（`descriptor.rs` 现有那句"未在册（`[hardware]` 不得自造键位）"的错误语义不变，
   只是查的表变了）。
3. **一次评审、三处同批**：加一类外设 = 加角色 + 加格 + 加 trait（或复用既有 trait 的新实现），
   三处必须同批，由 ⑦-e 型自指判等扩展检查（角色↔格↔trait↔键 四表一致，见批N3 的门禁增补）。
4. `schema_version` 由 2 升 **3**（破坏性契约变更，走 ADR-0012 的契约级评审），
   `rr-registry` 的 `RR3_ASSEMBLE_DESC_KEYS` 在册表与 `rr-hal::descriptor` 两处同批（该文件自己写的
   "副本滞后 = fail-closed 拒绝"仍成立）。

### 裁定 5（N-5）：新立 `Rr3Actuator` 能力面；**执行件档案**是行程与标定的唯一真值点

`Rr3PwmServo` 保留（只增不改，既有实现与 round-trip 用例不返工），但**不再是关节的抽象终点**。
新 trait 按 ADR-0019 修订的增长律以"新增 trait"落，禁止给 `Rr3PwmServo` 加方法：

```rust
// 落点：rr-hal-api（no_std + alloc 可达，签名无 alloc、无 async、无 Send+Sync）
pub struct Rr3ActProfile {           // 执行件档案：一块机的这个轴是什么
    pub center_deg: u16, pub lo_deg: u16, pub hi_deg: u16,
    pub dir_sign: i8,                // 接线极性（插反 = 改此数，不改码）
    pub slew_deg_s: u16, pub settle_ms: u16,
    pub hold: Rr3HoldPolicy,         // 保持激磁 / 到位释放（板侧 servo_release 即后者）
    pub current_ceil_ma: u16, pub warmup_ms: u16,
}
pub trait Rr3Actuator {
    fn rr3_profile(&self) -> Rr3ActProfile;
    fn rr3_enable(&mut self, on: bool) -> Result<(), Rr3HalError>;   // 激磁权（分时仲裁的抓手）
    fn rr3_goto(&mut self, deg: u16, deadline_ms: u16) -> Result<(), Rr3HalError>;
    fn rr3_position(&mut self) -> Result<Rr3Position, Rr3HalError>;  // 带可信度，见下
    fn rr3_store_profile(&mut self, p: &Rr3ActProfile) -> Result<(), Rr3HalError>;
}
pub struct Rr3Position { pub deg: u16, pub source: Rr3PosSource }    // Commanded | DutyRegister | Encoder
```

**回读可信度是契约的一部分**：今天 `Rr3PwmServo::angle()` 在 Linux 读 duty 寄存器、经桥档读板侧记账值，
**两者都不是轴的真实角度**。因此"舵机 round-trip 90/45/135/90 逐度一致"这条实录的证据对象是
**设定值回显一致**，不是**位置一致**——本裁定把这一区分钉进类型，防止后续判据拿回显冒充位置。

**执行件档案是行程的唯一真值点**：背景表第 4 条那三处（schema 0–180 / act config [70,110] / 板 [60,120]）
收敛为：schema 保留 0–180 的**线格式域**（那是字节契约，不是机械行程），
机械行程只住档案，模块面与板侧帧面**都读同一份档案**（经 `[hardware]`/档案文件/面板三层同源）。

**标定四路线**（`0.0.5批N` §6 给执行细节）：A 工装标定（外部量角器/治具，立即可用）·
B 电流找挡块（受控堵转，**依赖裁定 2 的电流采样**）· C 开环自恢复 + 软挡块（建议默认：上电到软边界、
记 duty 端点、运行期越界拒收）· D 换闭环执行器（新格新 trait，走契约级评审）。
**硬约束**：标定动作本身可能烧执行器，故标定必须限流、限时、限次数、限单步，失败退回上一份档案——
"标定流程"不得成为"第二次烧舵机的路径"。

### 裁定 6（N-6）：面板是**配置面**；面板覆盖率成为门禁

- **覆盖率门（新立）**：`面板配置项集 ⊇ （全部 `assemble.toml` 的 `ops` 槽 ∪ 描述符 `[hardware]`/`[pins]` 键
  ∪ 角色集 ∪ 每轴 `Rr3ActProfile` 字段）`。集合差非空即门禁红，红名单点名到键。**没有这条门，
  "所有配置都能在面板上改"永远是不可检验的宣称**——今天的现状就是背景表第 6 条。
- **观测面成契约**：每档至少两条腿——① 本地守护输出行（已有，`rr-core::runtime` 定形）
  ② 面板一份**当前生效绑定快照**（描述符 + 应急 env 覆盖 + 执行件档案三者合成后的那一份，
  不是原始文件）。只给原始文件 = 看不见"实际生效的是哪个"，正是 §12.3 那条静默的病。
- **写权限边界**：面板可写 = 策略量（阈值、行程、速率、亮度档、标定值、配网、模型 key）；
  不可写 = 契约量（格、主题、字节头、角色定义）。拒动类阈值（`severe_mv`、`armed`）的写必须带
  二次确认与留痕（这是运维面，不是安全旁路）。
- **链路**：WiFi 面板路径今天存在（http 14 端点）；**BLE 路径不存在**（`net.bt` = placeholder）。
  用户要求的"手机蓝牙连面板"是 rtos/bare 档**没有 WiFi 时唯一**的运维入口，故按形态分档裁：
  host 档 WiFi 先行，rtos 档 BLE 配网 + 只读诊断立为**待裁 D12**（要动 `net.bt` 的 status 与 connect 册）。

### 裁定 7（N-7）：板侧主题串与 `body["topic"]` 形状由**生成器**产出

`board.rs` 今天手写 `RR3_SERVO_TOPIC`/`RR3_FACE_TOPIC`/`RR3_AUDIO_TOPIC` 三串，并自述"与 topics.toml 同串"、
自行按 `rr3_publish` 的形状把 `topic` 键并进事件体——**靠人记，无门**。裁定：
`contracts/topics.toml` 是主题串与 payload 形状的唯一真值，板侧常量表由构建期生成器产出
（`tools/rr3-mkmod` 加 `--gen board-topics` 或独立 `tools/rr3-gen-board-topics`），
生成物入仓、由一致性门判"重跑生成器 diff 为空"。**一个事实一个真值点在这里的落法不是"板去读 toml"
（板没有文件系统与解析器），而是"真值点生成板的那份副本"**。

### 裁定 8（N-8）：**第四处窄缝**——资源与语义缝；"两件码"改判为"三件码 + 八段 + domains"

§12.8 三缝之外补第四条：

| 缝 | 连接什么 | 定形 | 今天为什么必须新立 |
|---|---|---|---|
| **接缝四 资源与语义** | 平台 ↔ 物理资源（引脚/域）；真值点 ↔ 板侧副本 | `[pins]` + `[supplies].domains` + 平台侧 `role→具名构造` 表 + 主题串生成物，四者由装载期八校验与一致性门互相对账 | 三缝把"能不能跑起来"接通了，没有一条管"接了什么物理东西、给多少电"——本周全部硬件损失都发生在缝四的位置 |

**核心口号按实况改判**：新形态接入的动作面 = **三件码**（① 能力面后端 ② `Rr3ByteStream` 实现
③ 平台侧 `role→具名构造` 表与主题串生成物入仓）+ **八段描述符**（增 `[pins]`，`[supplies]` 含 domains）
+ **一行点验矩阵**。这不是把缝放宽，是把"两件码"从**做不到的宣称**改回**做得到的清单**——
本项目自己的证据纪律（设计承诺 ≤ 代码事实）要求这样改。

## 备选与否决

| 备选 | 为什么不取 |
|---|---|
| **只在板 crate 里把 `board.rs` 的常量搬到同 crate 的一个 toml** | 换的是文件格式，不换归属：仍是这块板私有的、底座不认识的数据；树莓派与 RK3566 一个字节也复用不到。**抽象失败的判定就是"同类故障在第二平台重现"**，此方案不满足 |
| **给 `Rr3Power` 加 `rail()`/`budget()` 两个方法**（最省事） | 违反 ADR-0019 修订的能力面增长律"禁止给既有 trait 加方法"——那要求 `rr-hal` 的 linux/sim 两实现与所有件同批改，等于变更契约语义。新 trait + 新格才是零改动路径 |
| **保持"ESP32 = RK3566 的协处理器"这个更常见的工程直觉** | 用户明确裁定零关系，且这是产品事实：ESP32 形态自己配网、自己有屏有舵机有麦。把它写成协处理器，会让"外设可以没有本地观测面、由宿主代管"这个错误假设继续留在契约里——板侧欠压与标定问题恰好都死在这个假设上 |
| **把 `[pins]` 塞进现有九键**（不新增段） | 九键是"每键一个物理量"的扁平形状，表达不了 `mux_group`、`physical[]`、`rail` 外键与方向性；硬塞会造出 `pins = "18,19,20,21"` 这类字符串内语法——装载期没法校验，正是本周两条互斥没能被机械拦下的原因 |
| **标定取 B 路线（电流找挡块）为默认** | 依赖尚未存在的电流供给（裁定 2 的域采样在 ESP32 只有轨压 ADC，且未标定），且受控堵转在双轴云台上已实测造成过热。默认取 C（开环自恢复 + 软挡块），B 作为 N2 之后的增强 |
| **等 RK3566 板到了再一起做** | 三形态独立，RK3566 未采购是既成敞口；把缝四拖到那台机器上，等于让**第三块板**再去踩同一个坑——而本项目已为这个坑付过一只舵机 |

## 后果

**变好的（可检查）**：
- "按能源负荷裁剪调度"第一次有了数据结构（`domains` + `demands` + 装载期预算校验），
  不再是运行时靠串行化凑出来的行为。
- 本周四起真实冲突（UART2/I2C、I2S/硬件PWM、GPIO34 输入档、轨压无观测）各对应一条装载期校验，
  第二、第三块板再犯同一错会被 boot 拦住而不是靠人记注释。
- 显示面句柄从"被 C4 卡死"变成可注入；`rr3-interact/atoms/face/assemble.toml` 的 `handles` 有了填法。
- 行程与标定有了唯一真值点，三处漂移（含两处注释的错声称）可被一条对账门收掉。
- "所有配置面板可得"第一次变成可判真伪的门（覆盖率门），现状红着——这是**设计文档如实**的产物，不是倒退。
- "两件码"这句核心口号的适用条件补齐，含那处不可消除的 SDK 不对称。

**代价（明写）**：
- **契约级破坏性变更**：`slots.toml` 与 `profiles/*.toml` 的 `schema_version` 2→3，
  `rr-registry` 形状 pin、`rr-hal::descriptor` 键集、`rr3-pack`、两份 profile 文件、六册 §13 字面量清单
  全须同批改——这是一个批次量的活，不是一次提交。
- 点验矩阵要加列（⑧ 资源装载门）或把缝四并入 ③④ 两列的判据，两者都要改 `matrix.sh` 与 ⑦-e 型自指清单。
- 板侧新增生成物（主题串表、role→构造表）→ 新增"生成物与真值点漂移"这类失败模式，须配一致性门。
- 面板要长出配置读写面，前端与端点表同时扩；覆盖率门上线即红，须按批次逐面补齐并**如实登记为敞口**，
  不得为了让门绿而缩小分母。
- `power.rail`/`power.budget` 两格 + `Rr3Actuator` trait + `[pins]` 段是**新增面积**，每格都要有件、
  每件都要两条腿对拍——"每格一件·不留空格"门即刻生效。

**本 ADR 不主张的（边界）**：不主张任何阈值/分压比/电流上限的**数值正确**（全部待真板对拍，`armed=false`
纪律不变）；不主张 BLE 面板已可达（`net.bt` 仍占位，路径待裁 D12）；不主张标定精度（四路线里只有 A/C
今天能做，且 A 需要工装）；不主张 RK3566/树莓派形态已具备新数据（它们同样待施工）；
不主张缝四落完后"换板零代码"——按裁定 3 的不对称，**平台侧那张 role→构造表永远是码**。

## 施工与归属

本裁定的施工编排见 [0.0.5 增补轮六全案](../dev/0.0.5增补轮六——底座资源模型与能力面抽象补课全案.md)：
**批N1** 契约与数据结构（roles/domains/pins/schema 3 + 生成器）· **批N2** 能源供给与预算门（含电流采样前置）
· **批N3** 执行件档案与 `Rr3Actuator`（含标定四路线中 A/C 的实施、B 的护栏用例与门禁四表对账）· **批N4** 面板配置面与覆盖率门。
批次字母用 **N** 前缀不复用单字母，避免与 0.0.5 批A–M、0.0.6 批F5a/F5b、0.0.7 批A–H、增补轮四批W 撞名
（撞名已在本仓造成过一次真实误挂，见 §14 归属表的历史注记）。

**待裁（用户裁定窗，新立 D10–D15，登记进索引 §8）**：D10 三形态 BOM 与硬件接口定案（屏 I2C/SSD1306
还是 SPI/点阵、舵机 LEDC 硬件 PWM 还是 PCA9685、是否独立 UBEC + 分压测点 + 逐域电流采样）——
它决定 `[pins]` 与 `domains` 的键集**取值**，**不卡结构**；D11 面板写通道的档位边界（rtos 档能否写阈值
与档案，建议允许写档案/阈值、禁写 `[pins]`）；D12 BLE 路径要不要在 rtos 档立为必达
（`net.bt` 现为 placeholder，"手机蓝牙连面板"这条路径今天不存在）；D13 标定默认路线是否取 C
（建议 C 默认、A 工装、B 依赖 N2 后作增强、D 不排期）；D14 独立 ESP32 形态的主题前缀
（新立 `rr3-mini/*` owner 还是复用既有模块 owner）——它决定 ADR-0018"自足档不宣称发布主题"
要不要按"经桥微型形态其实有 owner"改判；D15 蜂鸣 `/api/beep` 要不要立格（今天它是
"能力真实存在、坐标系里不存在"，**保持现状是最坏的一种**——既不进坐标系也不退役）。
