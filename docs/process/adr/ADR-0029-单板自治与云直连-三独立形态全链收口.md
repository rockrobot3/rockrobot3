# ADR-0029：单板自治与云直连——三独立形态的全链收口

## 背景

现有三平台验证（Pi 4B / ESP32 classic / ESP32-S3）是"宿主 + 末梢板"的组合形态：
Pi 跑 `rrd` 与六模块，ESP32 只做外设面，经 UART 桥接。这套形态证明了协议接缝，
但**不是产品形态**：

1. 用户 2026-11-19 明确裁定：每块板都是独立整机，没有主、副板；Pi 当宿主不是目标。
2. 现状事实与目标存在硬差距（见 [status](../../status.md) 与计划册 §1）：
   - Pi 4B 只有 host-only 七格装配（回放/显示/网络/认知），**没有** capture/vad/servo；
   - ESP32-S3 只有末梢装配与板级外设证据，**没有**自治运行核与云客户端；
   - ESP32 classic 只有作为双板末梢的全链证据，**没有**单板全链；
   - 板载播放：Pi 有 USB 声卡；ESP32 侧 sink 是占位，板上无扬声器。
3. `rr3-sense` 的 VAD/DoA、`rr3-brain` 的意图规则与云客户端已存在，但分别绑在
   宿主进程与 `ureq`+rustls 依赖上，固件无法直接复用。
4. 严格 `no_std` 裸金属没有 WiFi/TLS/音频输出栈，520 KB SRAM 也放不下云语音
   全链缓冲；把"裸金属"当全链载体是**结构上不可达**的目标。

因此需要一次裁定：三块板各自如何承载全链、自治固件的边界在哪、哪些现有资产
按什么方式复用、什么算单板全链证据。

## 决策

### 裁定 1：全链按"独立整机"收口，桥降为可选

- 全链固定为：`唤醒/VAD → 云 ASR → 云 LLM → 云 TTS → 本板播放 → 意图 → 舵机/表情/听声识位`。
- **Pi 4B**：host 全承载，`rrd` + 六模块全部跑在本机，本机麦、本机声卡、本机舵机。
- **ESP32-S3 / ESP32 classic**：rtos 轻承载，**单进程自治固件** + 云直连；
  不依赖任何宿主、不依赖 UART 桥。
- UART 桥保留为**可选能力升级与测试台架**（既有 T1/T2 证据继续有效），但不再是
  任一形态跑通全链的前提。ADR-0021 裁定 1 的"认知经桥到某个 host 形态"一句，
  自本 ADR 起改读为"认知可经桥，也可云直连；独立整机默认云直连"。

### 裁定 2：自治固件 = 单进程多任务，无 rrd 面

- 固件是**一个进程**，任务表固定六项：`net` / `audio-in` / `dialog` / `audio-out` /
  `motion` / `ui`；`supervisor-lite` 只做状态机、看门狗与重启计数。
- **没有 `rrd`、没有 UDS、没有 fork/exec、没有动态模块加载**。`rrd` 的进程模型
  是 host 档专属；MCU 不复用其运行核，只复用其协议与机制件。
- 进程内边界仍用 `rr-ipc` 帧与 `contracts/topics.toml` 既有主题；投递走有界
  队列，满队列点名丢弃并计数，不阻塞音频线程。
- 配置分两层：装配真值（引脚/角色/预算）编译期嵌入；可变凭据（WiFi、API key、
  标定偏置）落 NVS。凭据不编译进固件、不进日志。

### 裁定 3：不新增承载档；`solo` 是装配单与运行形态，不是第四档

- 承载档词表维持 `host | rtos | bare`，`contracts/slots.toml` 的 `tier_scope` 不改。
- Pi 4B 单板用 **host** 档；ESP32-S3/classic 单板用 **rtos** 档。
- 新增装配单命名 `<chip>-solo.toml`（Pi 为 `pi4b-solo.toml`），与既有 `-mini`、
  `-host` 并列；机型集 pin 在 `rr-registry` 契约测试同批扩，形状测试同批立。
- rtos 档的既有语义不变：`rrd` 不派生、不注入；solo 档的装配真值由固件编译期
  消费，**不表示 rrd 会为它派生**。

### 裁定 4：云 API 是唯一对话后端，格式与失败语义固定

- 三家端点与现有 `rr3-brain` 真云实现同口径：
  ASR `POST /v1/audio/transcriptions`（multipart WAV）、
  LLM `POST /chat/completions`（OpenAI 兼容 JSON）、
  TTS `POST /v1/audio/speech`（`response_format=pcm`）。
- **TTS 只收 PCM/WAV**；板端不解码 MP3/AAC。供应商只给压缩格式时显式报错，
  换供应商或加代理，不引入解码器。
- 鉴权 `Authorization: Bearer <key>`；key 来源：Pi 为 secrets 文件/环境变量，
  ESP 为 NVS；两者都**不回显、不落日志、不编译进固件**。
- TLS 根证书随固件；开机 SNTP 对时；证书或时间失败显式点名并拒绝明文回退。
- 超时与重试沿用既有策略：单轮 8 s 超时、瞬时失败（429/5xx/传输层）最多 2 次
  尝试、固定 500 ms 间隔；鉴权/请求形状 4xx 不重试。

### 裁定 5：半双工播放，本轮不做 AEC

- TTS 播放期关麦或门控拾音（沿用 `rr3-sense` 的 tts_gate 语义），避免自触发。
- 回声消除、双讲、全双工属独立能力，单独立项；不得为"看起来流畅"而假装存在。

### 裁定 6：证据口径

- "单板全链"只认**该板自跑**的证据：云真调用、本板出声、本板舵机/表情/DoA。
- 宿主代理、双板组合、`sim`/`mock` 档、只跑 API 的台架，均不计入单板全链。
- classic 必须先过内存 Go/No-Go（30 min 稳态 free ≥20% SRAM、3 轮无 OOM）；
  不过则如实登记终态，不用"基本跑通"替代结论。

## 备选与否决

| 备选 | 否决理由 |
|---|---|
| 严格 `no_std` 裸金属跑全链 | 缺 WiFi/TLS/音频输出栈；520 KB SRAM 放不下缓冲；结构不可达 |
| 新增 `solo` 承载档 | 档位表达的是"谁派生/谁注入"，solo 是运行形态；新增档要改 `tier_scope` 全域，收益不抵扩展面 |
| Pi 继续当宿主、ESP 当末梢 | 用户已否；且不是独立整机，无法证明"每块板都能单独用" |
| MCU 上继续用 `ureq`+rustls | rustls 的加密后端对 xtensa 不支持；改用 ESP-IDF 自带 `esp_http_client`/mbedTLS |
| 为固件另写一套协议 | 与 `rr-ipc`/`rr-periph-proto` 既有真值冲突，制造第二套线格式 |

## 后果

- 正面：三块板有统一验收口径；Pi 先出证据，S3 随后，classic 有明确 Go/No-Go；
  现有机制件与云协议件被收敛为可复用边界，而不是复制两份。
- 负面/代价：需要新增 `rr-audio-mech`、`rr-cloud-proto` 两个抽取边界与一个
  自治壳；ESP32 侧需要 I2S TX/功放与 HTTPS 客户端；Pi 侧需要麦阵列与本地舵机。
- 风险：classic 可能 No-Go；TTS 供应商 PCM 支持不稳定；Pi USB 声卡可能只有
  单声道输入。三者都在计划册 §7 有对应门与处置。
