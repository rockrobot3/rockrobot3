## 4. 设计要点（边界以各 ADR 不做清单为界）

- **rrctl counters 渲染**：`rr3.ctl.counters` 回全表快照（键 = `模块名/键`，rrd 自有键
  `boots` 在册）；CLI 按模块名前缀分组渲染人读表（模块 → 键值对），空表打"无计数"；
  与 `status`（在册表）、`health`（心跳三数）同一表格风格
- **rrctl reboot 语义边界**：CLI 不加本地门——rrd 侧双重门（cfg(linux) 且
  `RR3_REBOOT_OK=1`）是唯一真值点，CLI 加门就是第二处真值；本地 sim 直跑 rrd 恒拒，
  CLI 回显拒绝文案并以非 0 退出，`--help` 与 README 写明"解锁面在装机环境"
- **brain 裁定的四个必答子项**（Q2 裁定文档的骨架，缺一不落档）：
  ①**不变量**——功能语义不变（对话闭环/意图规则/mock 注入点逐语义对照），
  七步门禁与契约校验不减；②**部署形态**——迁移完成后 deb / Buildroot 镜像不再含
  python3 运行时（defconfig 的 Python 包去向随板上批核对），`module.toml` 的
  `lang=rust`，tomllib ≥3.11 门槛自然消失（rr3-sim `which_python3` 能力验证面随
  迁移收敛）；③**切分**——首件 bus.py（rr-bus client.rs 已是真值，镜像纪律退役），
  次件 cloud 三客户端（urllib → Rust HTTP 的依赖预算裁定随批），dialog/intent 状态机
  收尾；④**批次归属**——0.0.6 专项，不与板上批、CI 结项批混排
- **pcm 不冻结的理由落档**：b64 JSON 是 uds 承载期的编码，shm 零拷贝后大概率改
  环形直读；schema 冻结一次、返工一次不如一次冻结到位——演进登记里"冻结时机属
  M5 shm 迁移裁定"的原表述升级为"冻结与接线绑定同一 ADR"
- **契约只增不改**：本版本预计零契约变更（rrctl 是消费端、裁定是文档面）；
  若裁定产生新 ADR，编号从 ADR-0016 起顺序取号，architecture 对应节回链

### 9. 设计要点（边界以 ADR 不做清单为界）

- **三层 manifest 的字段切分**：Atom 只声明"占哪个格 + 依赖 + publishes/subscribes + 板无关"；Composite 声明
  "装配了哪些原子件（`⊗` 链）+ 落为哪种执行单元（进程/任务/内联）"；Facade 声明"呈现哪个职责面 + 引用哪些 Composite"。
  三者的机器可读校验共用 `rr-registry` 查册门真值（承 ADR-0012 裁定 5②）。
- **`⊗`/`⊙` 落地边界**：`⊗` 装配 = 编译/装配期、执行单元内函数调用；`⊙` 编排 = 运行期跨执行单元、经 `rr-ipc`
  transport trait（Linux=UDS；无 OS=UART/SPI/BLE，见批D）。`F⊗F` 与"薄胶水直连原子"由 §13 静态/链接图门拒。
- **零策略载荷怎么写断言**：机制核目录 grep 厂商名 / 产品名 / 业务阈值字面量 / `if (vendor|product == …)` 命中即红；
  策略一律经 `ops` 函数表 + 描述符注入（ADR-0019 裁定 5）。这把第 I 轮 ADR-0017"策略不进模块"从评审项升级为静态门。
- **`[faces]`→`enabled_slots` 的波及面**：`profiles/*.toml` 两处、`rr-registry` 查册门字段、`contracts` 无关、
  第 I 轮 dev 方案 §2 表内引用、architecture §4.3/§3。先改数据事实源与查册门、再改引用，改名与查册门同批（防 CI 判红）。
- **功能守恒核对**：批C 每模块重铺前后，`topics.toml` 28 条对外主题、`module.toml` provides/exposes 逐条对账不变；
  原子化只动**内部结构**，不动**对外可见面**——这是 0.0.5 第二轮的硬红线，每批 DoD 复述。
- **no_std 线的落点**：字节协议层已下沉（`rr-ipc`，0.0.7 批B）为基线；批D 明确"下一刀切到总线语义 + Dispatcher 运行时 +
  控制/安全核"，`rrd` 跨进程监督 / 全 HAL / cloud brain / 打包 留在主承载层不下沉（ADR-0018 裁定 1）。

### 13.2 执行宿主定形（D4 裁定：**标准化环境**，不是"指定哪台机器"）

D4 原先问"xtensa / musl / 板 / 器件放在哪台机器上跑"。这个问法本身错了——它把**可复现性**问题
当成了**资源分配**问题：机器会变、环境会漂，矩阵行今天绿、下个月没人能重跑。现裁定：
**执行宿主 = 一组钉死版本的标准化环境**，机器只是环境的载体；每个环境能出哪些矩阵列、
不能出哪些，写死在下表里，越界取证据一律视为无效（同 architecture §12.6"不以设计已覆盖充当已验证"）。

| 环境 | 定义（载体 + 版本钉） | 出得了的证据（点验矩阵列） | **出不了的证据（不得冒领）** | 落地成本 |
|---|---|---|---|---|
| **E1 host-x86_64** | GitHub-hosted `ubuntu-latest` 或本地 WSL2，镜像 `rust:<钉版本>-bookworm` + `aarch64-unknown-linux-musl`/`-gnu` target + `qemu-user` + docker CLI | ① 字节契约**实跑 2 路**（宿主 x86 + arm64 容器）；③④ 装载门脚本；⑤ 安全核逐拍**数值一致**（host tests）；⑥ 生命周期（`rrd` e2e + `tools/sim --chain`） | **⑦ 时序达标**（云 runner 是共享 x86、qemu-user 是**指令级模拟**，两者的时间都不是硬件时间）；任何真外设行为 | 低——现有 `check.sh` 九步 + `ipct003.sh` 全部可在此跑，脚本一行不改 |
| **E2 xtensa-none-elf** | 镜像 `ghcr.io/esp-rs/...`（espup 装的 Xtensa Rust fork，版本 = **esp-rs fork v1.90.0.0**，与 0.0.7 批A' 台账同源）+ `build-std=core,alloc` | ② 机制核编译面（bare 档）+ ① 的编译期 const 断言在该目标**重求值**（就是 `tools/ci/rr-core-xtensa-check.sh` 的三查） | **运行期任何东西**——none-elf 目标上没有 runner；"⑤ 逐拍一致"在这里只是**编译证据**，运行证据归 E4 | 中——镜像体积大，必须配缓存；本机 Windows 侧装不上（0.0.7 修订版 8 的实况），容器化恰好绕开 |
| **E3 espidf-std** | `espressif/idf:<v5.x>` + esp-clang + `build-std=std,panic_abort`（0.0.5 增补轮四批W1/W2 的既有冒烟形状） | ② 的 rtos/std 编译面（0.0.7 层② 适配器、批C④） | FreeRTOS 任务切换与 UART 边界的**真实行为**（编译过 ≠ 保消息边界，③ 供给自证仍要 E4 实测） | 中——ESP-IDF 克隆与 target 体积；`espidf-std-check.sh` 已是专用门，不改判据 |
| **E4 真板（不可替代）** | self-hosted：树莓派 5（0.0.6）/ ESP32-S3 + **CP2102**（0.0.7 §9 手册，C11 已点名该件不在 BOM） | ⑦ 时序达标的**周期直方图**；⑤ 在目标上**真跑**逐拍；③ 供给自证的实测值；断电重启、看门狗复位、外设真信号 | —— | 高（要物理设备 + 人），但它是**唯一能让"跨 OS 已验证"这句话成立的环境**。标准环境做得再好也只是编译面与数值面 |

**版本钉三则**（矩阵行可复现性的全部前提，随批K `tools/ci/matrix.sh` 一起落）：
1. **镜像按 digest 引，不按 tag**——tag 会漂，漂了以后矩阵行无法重跑，"实跑第几路"就成了考古题。
2. 矩阵每行必须带**环境指纹**三件套（镜像 digest + `rustc -Vv` + 目标三元组），写进 `matrix.sh` 的产出，
   并回写 `status.md` 的矩阵行；指纹缺失的行按"无载体"处理，不按 PASS。
3. **换代即重跑**：指纹一变，该列的旧绿迹作废并标"环境已换代"，不许沿用（与 0.0.6 修订版 11
   "历史板录按当时实况读"是同一条纪律）。

**CI 真源不迁移**（避免造出第二套判据）：判据的唯一真源仍是 `tools/ci/*.sh`（入口 `check.sh` 十步 +
`matrix.sh --strict`）。GitHub 上的 workflow 与 `.github/workflows/ci.yml` 都只是**调用清单**，
两处清单调同一批脚本；哪边先跑、跑几路属于宿主事实，写进矩阵行的"实跑 N/4 路"里，
**不允许**在清单里另写判定逻辑。这条与既有约定（步序与条数唯一落点 = `conventions.md` §2）一致。

**两条前置未结，如实登记**：① 本仓今天**只配了 atomgit 一个远端**，走 GitHub-hosted 需要先建镜像仓
并授权推送——这是资源动作，不在本轮设计范围内；② 私有仓的 Actions 分钟数有限额，E2/E3 的 esp 镜像
首次拉取很贵，**必须先配缓存**再谈把它当默认承载体。二者未清之前，E1 的本地 WSL2 形态仍是可用承载体，
矩阵照 `--strict` 口径记"实跑几路 + 其余无载体"，不假装四路齐。

### 14. 任务分解（WBS · 批 I–K）

每批独立提交（Conventional Commits 中文信息 + 引用 ADR-0018/0019 修订 1），每批收尾 `git status --short`

**每批验收四件套的统一口径**（v0.9 同日五轮补——§14 表只有五列，四件套在这里展开）：

- **操作步** = 该批内容项列出的动作（F/G/H 编号逐条对号）；
- **预期输出** = `check.sh` 全步 PASS + 该批新增门的首次回执 + `git status --short` 对账；
- **判定标准** = §17 对应勾点 + 该批红线列（对外面零改动逐条核）；
- **失败处置**（三档，写死不许临场判断）：
  ① **C 项未结** → **停批回填**，该批 DoD 一项不勾，在 `status.md` 敞口表记"C 几、缺什么、谁结"；
  不许"先做完再说"（那会把门做成永远红的门，最终被人绕过去）；
  ② **载体不在**（E2/E3 镜像未就位、E4 板离线、外设未到）→ 该判据记**"无载体 + 触发条件"**，
  禁记 SKIP 为通过；批内其余不依赖载体的动作照做，并在 DoD 上**分项勾**（不允许整批不勾或整批全勾）；
  ③ **门与数据互斥**（如批J G4 的注入面校验 vs 17 份空 `assemble.toml`）→ 按 C3 的"模板、门、数据三者同批"
  处理，先以 **power 单元**为样板落一份真值再开门（承第 II 轮 Q-P2 与索引 §11 L-3 的破环法）。

### 15. 设计要点

- **三缝各自的"动什么 / 绝不动什么"**（这是本批爆炸半径的控制面）：

  | 缝 | 动 | 绝不动 |
  |---|---|---|
  | 能力面契约 | trait 签名形状（async→同步）、值类型载体、件对 `rr-hal` 的 import 源 | 后端实际行为（ALSA/sysfs/chardev 读写序）、`Rr3HalError` 语义、sim 后端形状 |
  | 总线字节流 | blanket impl 的**下底**（从 `Read+Write` 换到 `Rr3ByteStream`）、加一个 adapter | 帧格式 128B、payload 前缀、`rr3_seal` 幂等语义、三实现的文件路径与 env 键 |
  | 注入数据面 | `assemble.toml` 的内容与读者、描述符新增三段 | `contracts/slots.toml` 格名、`module.toml` 的 provides/exposes/subscribes/bindings、装配单 `[bindings]` 现有键 |

- **件的"三条不持有"**（§4.0.3 依赖闭包的口语版）：不持有决策（阈值/编排/人格，一律 ops 或 config）、
  不持有平台形状（不 `use std::`、不 `use rr_hal::`）、不持时钟与调度（不自睡、不起线程，节拍由组合件
  注入）。三条同时满足的件，才写得出对拍用例——**对拍用例是"这是机制吗"的可执行答案**，不是文档口号。
- **兼容策略照抄第 II 轮先例**：批D①/③ 把真值迁进 `rr-core` 时用 re-export 保住 `rr-bus`/`rr3-act`/
  `rr3-power` 的既有 import 路径，对外零改动、模块面 `use` 语句一行不动。`rr-hal-api` 同法。
- **缺格判定三源合一，只留一个出口**：`[slots].present`（声明缺）+ `handles`/`ops` 校验（注入缺）+
  硬件探测（实测缺）三个来源都汇到 `Rr3Phase::Degraded` 一个出口（不新增相位，承 §4.3 与 ADR-0012）。
  今天的实况是探测面恒真（`Rr3SimProbe`）且 `Rr3LinuxProbe` 未被构造，降级环不转——G3/G4 之后它才有
  真数据可判。**探测真值仍按平台批实装，本版本不为其凑假实现**。
- **功能守恒核对法**（承第 II 轮）：每批重铺前后对 `topics.toml` 28 条、六份 `module.toml` 的
  provides/exposes/subscribes、128B golden 逐条对账；本版本动的是**接缝**，比第 II 轮更不该碰对外面。
- **点验矩阵的"填不到"是常态不是失败**：七列里必然有格落在本机跑不到（真件、真芯、远端流水线）。
  纪律同 H5 与 ADR-0018 裁定 6：写"敞口 + 触发条件"进 status.md，不空着、不拿设计充数、不把 SKIP 记成 PASS。

### 20. 设计要点（本轮六个判断，每个都能被推翻）

1. **下行音频流的形状 = 复用上行 stream 体，不新建编码**。三个备选：
   **(a) 选**——新增 `rr3-brain/audio/tts_pcm`（`kind = "stream"`），载荷体逐字段复用 `rr3_pcm_event_body`
   已定的 `{seq, format:"s16le", rate, channels, ms, pcm_b64}`。理由：同一编码同一分帧，`envelope` 与
   128B 头不动，跨语言（Python 产 / Rust 消费）只有一份对拍面，上行已有线级与 golden 先例。
   **(b) 否**——把 PCM 塞进 `tts/text` 的 JSON-RPC 请求体：事务面没有 `seq` 也没有背压语义，播一半失败
   无从表达，且等于给"播放"造第二条通路（点名与流两读，违"一个事实一个真值点"）。
   **(c) 否**——走 shm：ADR-0011 已裁"M5 前不接线"，不为一条功能重开传输层裁定。
2. **低电禁动的语义在此拍板（A-5 的"待裁"结案）**，四条：① **触发源唯一** = rrd 的低电旗广播
   `rr3-runtime/system/power`（`Rr3LowEdge` 判定已在 power 侧、rrd 置旗已在，再加第三个判定点就是三真值）；
   ② **禁动范围 = 执行面**（servo/relay 的点名与意图两路同判），**妆面不禁**（led/face 写失败按 D8/A-12
   分类表折日志不退；禁动它们只增加卡死面积）；③ **解禁 = 回阈 + 迟滞**，且不自动重放被拒的令（拒因回显，
   由上层决定是否重发）；④ **bare 档无 rrd** 时本地兜底由安全核段自判 `Rr3LowEdge` 并出 `RR3G` 守护行
   （P-8 ⊕ A-5 = L-8，合并成一个动作，不再两册分头挂单）；⑤ **本版唯一低电保护动作 = 本条的禁动**，
   `battery.cutoff_voltage_mv` **声明未生效**——**本版不关断**（关断动作归 M6 关机链，需 T1/T2 物理断电
   硬件），键保留为策略数据、机器读者 = 注入门（`atoms/battery/assemble.toml` 的 ops 槽，
   `rr3_registry_assemble_injection_gaps` 按点路径取值、⑧-c 门仓级强制；`println` 回显不算读者）。
   MC-8① 由此结案（2026-10-13 裁定 (c)），不再留"回显即当作已实现"的中间态。
3. **功能码进哪一层，按第 III 轮 §15 三缝表判，不许就近写**。MC-3 / MC-6 / MC-7 全是**承载层**
   （`rr-hal` 后端与 cfg 面）工作，件面只换句柄来源与错误语义；`rr-core` 只接受 MC-5 的闸门**判定**
   （复用已有原语），不接受任何板名、器件名或设备路径字面量。这条判据可被 grep 证伪：
   `rr-core` 与 `rr-hal-api` 里出现 `max7219` / `nmcli` / `/sys/class` 即为违例。
4. **fail-closed 优先于"能跑"**。MC-4 的探测拿不到答案时**不得**当作"在位"；MC-3 的显式 `linux` 请求
   在器件不在位时必须 `Unsupported` 点名。站替件的价值是"如实报缺"，不是"装作可用"——这与 §17 已勾的
   "占位 ≠ 通过"是同一条纪律的两面。
5. **申报面变更只有两种合法形式**：经 MCP-3 / C14 类评审的在册变更，或"补实现 / 撤申报"二选一。
   本轮动到 `module.toml` 的评审授权处只有 `rr3-act` 一条订阅（MCP-3）；**MC-1 落地（2026-10-13，`f959e3a`+`70e8fb6`）另有两处申报面变更，走的是第二种合法形式（补实现）**——`rr3-brain` 增发布 `rr3-brain/audio/tts_pcm`、`rr3-interact` 增订阅同名主题：主题本体早在 MCP-1 评审（`8d05590`）时已在 `topics.toml` 在册（30 条计数未动），申报随实现落地补齐，属"补实现"形式而非新登记。**功能守恒口径 v2**：`topics.toml` 的 append
   **一律合入 MCP-1 那一次评审**（本轮的下行音频流 + 增补轮五批C/批D 的 `display`/`servo`/音频上行帧
   一并改表、一并改门 pin、一并改 `contracts/README.md` 计数），**除此之外零改动**——本句已由 `8d05590` 兑现，`topics.toml` 现 30 条；128B 线上字节零改动；
   `module.toml` 申报面除评审授权的两处（C14 已执行、MCP-3 一次）外零改动；`contracts/slots.toml` 除
   MC-9 的状态位改记、以及批C 若立显示/音频新格位时走的 ADR-0012 评审外，格名与层零改动。
   **同轮出现第二次改主题计数，即视为 §18.4 分账失效**——那说明两轮各自改了同一张表。
6. **"清零"类判据必须给可执行观察式，不写形容词**：台-2 的清零 = 件面 `grep` 不到 `440` 与
   `RR3_TTS_MS_PER_CHAR`；台-1 的清零 = `rr3_probe_default` 在非 test 面按目标分流；台-4 的清零 =
   `slots.toml` 的 `net.bt` 状态位与实现一致且 ⑧-a 读它出结论。**写不出观察式的判据不进 DoD**。
