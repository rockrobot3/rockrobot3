## 1 背景与目标

**为什么 ESP32 是这套底座的关键试金石（承 [ADR-0018](../adr/ADR-0018-跨操作系统移植-机制核与主承载层分离.md) 及其修订 1）**：
ADR-0018 把底座价值定为"**跨操作系统快速部署**"——同一机制核要在三档板卡上都成立（全承载 host /
轻承载 rtos / 无承载 bare，判据是"四类供给齐不齐"而不是"有没有 Linux"）。ADR-0013 把 rock3 交付物
定义为"Linux 起来之后的一切"，此前全部验证（x86 宿主、aarch64 交叉、树莓派真板）都在 **Linux 可用**
的前提下成立。ESP32 上没有 Linux——若契约头、帧读写、transport 语义**脱离 Linux 仍成立**，
rock3 的"契约即资产"就从 Linux 系主张升级为**跨系统类别主张**。**ESP32 因此是轻承载档（rtos）的
第一个一等承载平台**：本版按 §3 Q2 裁定走 esp-rs **std** + FreeRTOS，所以它**有操作系统**（RTOS 即 OS）
却没有主承载层（无 rrd 跨进程监督、无富文件系统、无 ALSA/CPython）——0.0.5 第 II 轮改写本节时把它
标成"无 OS 端第一个一等承载平台"是错的，按 ADR-0018 修订 1 的三档表订正于此。它验证的不是一个附件，
是整套底座核心命题里的**中间那一档**。

**模型边界（本版只坐实轻承载档的地板，不推翻 ADR-0013）**：底座分**机制核 / 主承载层**两层，
"某平台承载多少"是一条按能力定的谱（[architecture.md](../../architecture/architecture.md) §12.1 / §12.7）。
本版做的是这条谱上轻承载档的**地板**——让 ESP32 承载机制核的两个最底层资产：契约（rr-ipc 编解码）与传输
（transport trait，正是 [ADR-0019](../adr/ADR-0019-原子功能模块模型-格件面与组合代数.md) 裁定 2 里 `⊙`
跨执行单元通道在非全承载平台的实现位）；层③④ 再验最小哨兵模块与桥接。**一处诚实**：`⊙` 在板上今天
走的是 std 侧形状——`Rr3TransportConn` 的实现路径是 `impl<T: std::io::Read + Write>`，本版的 UART 也是
**宿主侧**开 `/dev/ttyUSB`（`rr-ipc/src/transport/uart.rs` `cfg(any(linux, macos))`）。真正的板侧通路
（`Rr3ByteStream` 窄缝，architecture §12.8 接缝二）随 **0.0.5 第 III 轮批J** 落，本版不主张它已完成。
模块语义的更重部分（装配单仲裁、降级、cloud brain）仍落全承载档；"一枚 MCU 自成整机"（§12.7 的无承载档）
是远期目标，本版不主张、只把地基坐实。0.0.6 §7 候选路径 **a. 桥接模块**被采纳为层④ 形态，**b. 协处理器**
角色维持 ADR-0015 裁定 4 的后置归属。

**本版收口改用点验矩阵（architecture §12.6，ADR-0018 修订 1 ⑥）**：ESP32 填**轻承载档那一行**，七列对位
如下——① 字节契约 = 层① `ipct003` 四路 golden；② 机制核编译面 = 层① xtensa 编译 + `rr-core` tripwire；
③ **供给自证** = 本版新项，port 须交时基（esp_timer/OS tick 分辨率与单调性）、内存模型、事件循环
（FreeRTOS 任务 + 队列）、传输（UART 是否保消息边界）四条，与描述符 `[supplies]` 逐键核对
（`[supplies]` 段随 0.0.5 批J 落，本版先按模板登记实测值）；④ 描述符装载 = 三格 `[slots].present`
与 `handles` 校验过、错误不吞；⑤ 安全核逐拍 = `rr-core::control` 对拍用例在板上真跑；⑥ 生命周期 =
层③④ 的注册→心跳→应答→桥接（无监督重启面，如实记"不适用 + 原因"）。⑦ **时序达标**（architecture v0.9 补的第七列）= 本版 §9 板上取周期直方图——uart 收帧间隔、桥接往返
耗时、`rr-core` 对拍用例的调用间隔上界，与 `[supplies]` 声明的名义周期对表；本机只核"声明与代码常量
一致"，真值必须由本版给出。层①②③⑤⑥⑦ 的实测条数与
敞口随本版各批登记 conventions §2 与 status.md。

**四层验证梯子（R5 裁定原文展开）**：

| 层 | 内容 | 必达性 | 判据 |
|---|---|---|---|
| ①契约 parity | rr-ipc 编解码在 xtensa 目标编译 + golden dump 对拍 | **必达** | 编译期 const 断言过 = 任意目标成立；`ipct003` 四路对拍（x86 / aarch64 交叉 / 容器 arm64 / xtensa）golden 逐字节一致——IPC-T-003 第④路 |
| ②传输第三实现 | UART transport（补 ADR-0008 第三实现位） | **必达** | Linux 侧单测帧往返；ESP32 板级 round-trip（128B 头 + payload 完整收发，半帧/坏帧拒收路径表现正确） |
| ③模块层 | esp-rs std 最小哨兵模块（**内跑 `rr-core::runtime`**，注册 / 心跳 / 回应答） | **必达**（R19） | 双证：**xtensa 编译面** `rr-core` 在该目标可编译 + **板上真跑**一次完整注册→心跳→round-trip；两证都算过才算过（只编译 = 无载体，只真跑自己写的状态机 = 没验证机制核）；RAM 峰值有实测数 |
| ④系统集成 | Linux 侧 rr3-bridge 桥接模块接真总线跨芯片 e2e | **必达**（R19） | 树莓派/mac 上 rrd 带 bridge，总线任一模块与 ESP32 对端按既有主题收发成功 |

层③④不可达时的处置（R19 后裁覆盖 R5 原档位，R5 原文见 0.0.5 §2.1 与本文件
修订版 1–3 记录段）：经典 ESP32 实测 RAM 不可达即触发批D2——ESP32-S3（RAM
512KB→2MB 级 + PSRAM）采购入库，target/PSRAM 迁移后按同判据继续真板验收，
**四层全真板验收，无"受阻态收口"出口**；RAM 峰值实测数仍必记（D1→D2 触发判据
数字口径见 §9.3）。

## 3 裁定问题（Q1–Q6，已裁——R20）

> 裁定记录区：Q1–Q6 已随 0.0.5 增补轮三 R20 全部裁定（2026-10-06），裁定行已
> 逐题回填如下——修订版 1–3 期间"仍待裁"状态至此终止；各题裁定只落档位结论，
> 论证细节以题内建议口径为准。

### Q1：层② 传输介质——UART vs USB-CDC

- **建议 a：UART**——经典 ESP32 **无原生 USB**（S2/S3 才有 USB-CDC/OTG），板上
  CP2102 只是 USB-UART 桥；直连 UART 引脚（3.3V TTL）接树莓派/mac USB 转串口
  亦通。速率 115200 起步（帧最大 128 + payload，半容量守卫在环内不适用——UART
  无环，靠流控与帧语义拒收）。**transport trait 第三实现位按 UART 落**，线上
  帧格式不变。
- b：USB-CDC——需换 S3 板，违反"经典 ESP32 在手"事实，弃。

  **裁定**：a（UART）——transport trait 第三实现位按 UART 落，线上帧格式不变
  （0.0.5 §2.4 R20，2026-10-06）。

### Q2：层③ 运行时——esp-rs std vs no_std

- **建议 a：esp-rs std**（esp-idf-sys / esp-idf-hal，FreeRTOS 任务）——模块语义
  （注册/心跳状态机）用 std 写与 Linux 侧同构；代价是 ESP-IDF 构建链重 +
  内存足迹大，正是"按实测内存裁"的实测对象。
- b：no_std 裸机轮询——内存最小，但层③"模块层语义可移植"的验证力弱化
  （裸机写不出同构状态机，只剩字节回声），且 no_std 下 std trait 面（Read/Write）
  缺失，transport blanket impl 复用不了。作为层③④ 裁"不可达"时的降级备选保留。

  **裁定**：a（esp-rs std）；b（no_std）的"降级备选"出口随 R19"无受阻态收口"
  口径失效——受阻即批D2 换板续做，不再降级（0.0.5 §2.4 R19/R20，2026-10-06）。

### Q3：层③④ 必达性口径

- **建议（R5 原口径确认）**：层①②必达是版本 DoD 硬项；层③④做成即超额、
  实测 RAM 不可达则登记"层①②已证 + 层③④受阻于实测内存 X KB < 需求 Y KB"并
  出 ESP32-S3 换板建议进采购敞口。**验收判据不许为凑数降级**（如砍心跳只留
  回声——回声不是模块语义）。

  **裁定**：R19 后裁覆盖本题 R5 原档位——层③④ 必达，实测不可达即批D2 采购
  ESP32-S3 移植续做，四层全真板验收，无受阻态收口；"验收判据不许为凑数降级"
  原句继续有效（0.0.5 §2.4 R19/R20，2026-10-06）。

### Q4：rr3-bridge 归属与形态

- **建议（修订版 2 按 R15 订正）**：桥 = **transport 级连接多路器**——每哨兵一条
  独立 uds 连接，UART 字节流直灌对应连接（UART↔UDS 纯字节搬运，不解析模块语义）；
  对端哨兵自己发 register 帧，以完整注册/心跳/前缀语义进城，rrd 语义零改动、
  **零新契约从结构上成立**（rrd 现行反伪装 src 校验与前缀归属即白名单）。桥因此
  **不进 manifest 注册面**（原建议"进注册面"按 R15 订正——原弃案理由"绕过注册面
  即第二套模块语义"失效：对端走完整语义，桥不经模块语义），形态为 tools/ 伴生
  Rust crate（与 sim_peer 同级）。层④判据不变（总线任一模块 ↔ ESP32 对端按在册
  主题收发）。
- 原建议"新立 `modules/rr3-bridge` 进 manifest 注册面 + 只透传白名单"弃——透传
  register 帧会被 rrd 按 spoofed src 拒（每连接一身份），桥 NAT 改写 src 则点对点
  dst 语义坏；本节为建议口径的 R15 订正，Q4 已随 R20 裁定（裁定行见上）。

  **裁定**：R15 订正后的建议口径成立——桥 = transport 级连接多路器，tools/
  伴生 crate（与 sim_peer 同级），不进 manifest 注册面，哨兵完整 register 语义
  进城，零新契约（0.0.5 §2.4 R20，2026-10-06）。

### Q5：ESP-IDF 密钥门清理口径

- **建议**：批A 随方案落档一并清理历史遗留敞口——ESP-IDF 不进本仓（构建依赖
  外置，写明版本与获取方式进 boards 笔记），密钥门按 0.0.4 批D 同款处置（不
  claim 即注销）。若层③ 裁 std 路线，ESP-IDF 是外部工具链依赖不是仓内资产。

  **裁定**：建议口径成立——ESP-IDF 外置不进本仓 + 密钥门按 0.0.4 批D 同款
  注销（0.0.5 §2.4 R20，2026-10-06）。

### Q6：验收环境——桥接 e2e 的 Linux 侧宿主

- **建议**：e2e 分两档——本机 macOS（/dev/tty.usbserial，开发期日跑）+ 树莓派
  （/dev/ttyUSB0 或 GPIO UART，0.0.6 板上批后复用）。树莓派档依赖 0.0.6 批F4
  完成（装配链已含真硬件面），不阻塞 0.0.7 批B/C/D。

  **裁定**：macOS + 树莓派双档成立（0.0.5 §2.4 R20，2026-10-06）。

## 5 设计要点

- **层① 的"编译即证明"**：header.rs const 断言的价值在 xtensa 上兑现——不需要
  跑测试，目标编译通过即偏移/长度/magic 冻结成立。golden dump 对拍是第二重
  （运行期编码线上字节 vs 黄金文件），两重独立。
- **UART transport 的接缝纪律**：只实现 trait 三件套，**不新增关联类型、不改
  签名**（ADR-0008 接缝定型）；ESP32 侧复用同一 rr-ipc crate 源（`cfg` 目标分
  平台实现，帧语义源码共享）——这是"契约即资产"的字面兑现：同一份编解码源码
  在两测编译，不存在"ESP32 版协议"。
- **内存裁定先行（批D 的第一产出是实测报告）**：哨兵最小语义（注册一帧 + 心跳
  周期帧 + 应答一帧）先在板子跑起来量 RAM，再谈功能完整度——顺序反了就是
  先写半成品。
- **桥零策略（R15）**：桥是 UART↔UDS 字节管道（连接多路器），不解析模块语义、
  不做白名单——放行面由 rrd 现行注册/前缀归属/反伪装 src 校验承担（未注册主题/
  伪造 src 本来就拒，fail-closed 同款纪律）；桥不持任何主题清单，装配单 bindings
  不需要为桥改一行（修订版 2 前"透传白名单"口径按 R15 订正）。
- **与 pcm STREAM 空缺的关系**：语音面若延伸到 ESP32（拾音协处理器），pcm
  schema 冻结与 shm 接线绑定同一 ADR 的裁定（0.0.5 Q3）不变——本版**不碰
  STREAM 负载**，哨兵与 e2e 只用 Event/Request 级主题。

### 5.1 rr3-bridge 桥件形状钉死（修订版 5 随批W6，R15/R20 复核零冲突）

> 批E 照本节直写（ crate 结构、任务模型、参数名之外零设计决策剩）；实现细节
> （缓冲块大小、日志措辞、退避参数）以批E 实装为准替换，形状与判定分界不因实装变。
> R15/R20 复核结论：**零冲突**——逐条依据见本节各条括注。

1. **定位与形态**：`tools/bridge/` 伴生 Rust crate（与 `sim_peer` 同级，Q4/R15），
   不进 manifest 注册面、不进装配单 bindings——桥不是模块，rrd 侧看不到桥（看到
   的是哨兵的完整 register）。
2. **连接模型**：一条 `--uart <dev>` 实例 = 一条 UART 链路 = 一个 ESP32 哨兵 ↔
   **恰好一条** UDS 连接（连 rrd 的 `rock3-ipc.sock`），1:1 映射、互不共享；
   多哨兵 = 多个 `--uart` 实例（多路器语义的形状预留；批E 单路验收，多路不是
   批E 判据）。`--socket` 指向 rrd socket，`--baud` 缺省 115200。
3. **字节透传语义**：双向全双工、**零解析**——UART 读多少转发多少（固定块搬运），
   帧边界归两端的帧读写层（`rr3_frame_read` 半帧/坏帧拒收语义现成）；桥不认识
   128B 头、不校验 magic、不组帧、不改写任何字节（src/dst/trace 原样）。
   R15 依据：哨兵完整 register 语义进城 + rrd 反伪装 src 校验即白名单，桥持
   任何清单都属多余策略。
4. **握手与身份**：rrd 的注册握手是**帧级协议**（`conn.rs` 的 `rr3_handshake`
   §4 门序 1–10 全部对帧内容——首帧读取 / payload 前缀 / `dst_task` / Request
   类型 / RPC 信封 / register 方法 / manifest 文本 / entry 绝对性，**无连接级
   creds 门**）——哨兵自己发 register 帧（manifest 全文随 `params.manifest`
   过桥），桥对握手不可见；身份 = 帧内语义，桥零参与。R20 依据：Q4 裁定原文
   "哨兵完整 register 语义进城，零新契约"。
5. **寿命管理（三态循环，每条链路独立）**：
   - **UDS 未就绪**（rrd 未起 / socket 权限拒 / rrd 重启窗口）：connect 退避
     重试（1s 起步指数退避至 10s 封顶，恢复即连）；期间 **UART 上行丢弃 + 丢帧
     计数日志**（不缓冲）——自愈依据 [`rrd-rpc.md`](../../reference/rrd-rpc.md) §5
     `TimedOut` 行："该 task 已过期或不在册，需重新注册"——哨兵 register 应答
     超时重发 / 心跳被拒即重注册，rrd 语义零改动；下行无连接自然无数据。
   - **UART 断链**（拔线 / 哨兵掉电重启）：读侧 EOF/错误 → 关闭对应 UDS 连接
     （rrd 侧走 EOF 干净收尾或心跳判死，`rrd-registry.md` §6/§7 既有语义）→
     持续重开 UART 设备节点 → 成功后回 UDS 重试循环——哨兵重启后重新 register，
     全链自愈。
   - **UDS 断链而 UART 存活**（rrd 重启）：UART 口持续持有（哨兵侧无感知），
     UDS 重连后恢复透传；哨兵经 TimedOut 语义重注册。
   - 桥自身退出：SIGTERM → 逐条关 UDS → 释放 UART 设备节点（退出码 0）。
6. **下行带宽核算**：rrd 下行广播（`rr3-runtime/module/state` + system/heartbeat，
   `rrd-rpc.md` §6）经桥透传到 UART，哨兵按帧内 `dst_task` 自行过滤（广播帧
   过滤是**哨兵**职责，归批D1 实装约束，桥不管）——115200bps ≈ 11.5KB/s，单条
   192B 帧容量约 60 帧/s，广播周期流量占比可忽略；此核算入批E 验收记录。
7. **权限注记**：`/var/run/rock3-ipc.sock` 实况 `srwxr-xr-x root:root`（0.0.6
   批D 真板发现，other 无 w 位）——桥运行用户必须可写该 socket；非 root 放行
   （bind 后 fchmod / service 运行时目录权限）已在 0.0.6 敞口表在案，桥不做
   任何权限特判（打不开就连不上，走第 5 条 UDS 重试态，如实报错）。
8. **零策略断言**（继承 §5"桥零策略"与 §9.4 ④ 核对清单）：不持主题清单、不解析
   帧、不改写字节、不做权限特判——四条核对结论随批E 提交说明附源码审查记录。

### 9.1 层① 契约 parity runbook（批B）

**① 工具链核验（批A' 延伸，进批B 前置自检）**：

- 操作步骤：

  ```
  espup install
  rustup toolchain list
  cargo +esp --version
  ```

- 预期输出：`rustup toolchain list` 回显含 `esp` 工具链行（形如
  `esp-1.xx.x` (override)）；`cargo +esp --version` 回显 cargo 版本号
  （形如 `cargo 1.xx.x (esp)`）。
- 判定标准：三条命令零报错即过。
- 失败处置：espup 安装失败 → 改走 esp-rs 官方 rust-build 安装脚本（按当时
  官方文档定，批A' 已备等价路径）；fork 工具链与 workspace 锁不匹配 → 按
  esp-rs release 对表后重装对应版本。

**② xtensa 目标编译（编译即证明）**：

- 操作步骤：

  ```
  cargo +esp build -p rr-ipc --target xtensa-esp32-none-elf
  ```

- 预期输出：`Finished dev [optimized ...] target(s)`；header.rs 编译期 const
  断言（偏移连续 / 头长 128 / magic LE 线上字节 / payload 枚举冻结）全部静默
  通过。
- 判定标准：编译成功即过——const 断言是编译期门，无运行期判据；同一份编解码
  源在 x86 与 xtensa 两侧编译通过 = 平台无关成立。
- 失败处置：目标缺 std 组件 → esp fork 工具链加装 std 组件后重试；const 断言
  炸 → 编解码源被平台假设污染（指针宽度/对齐假设），如实登记为层① 抓到的缺陷
  并修复——修复属批B 范围，不属豁免。

**③ ipct003 第④路对拍**：

- 操作步骤（第④路接入随批B 落 ipct003.sh）：

  ```
  # 生成 xtensa golden dump（命令随批B 实装落 ipct003.sh，此处为操作骨架）
  # 四路逐字节对拍（x86 / aarch64 交叉 / 容器 arm64 / xtensa）
  diff contracts/golden/event-header-128.hex <xtensa 路 dump>
  ```

- 预期输出：`diff` 空输出——四路 dump 逐字节一致。
- 判定标准：四路 diff 全空 = 过；任一路非空 = 不过。
- 失败处置：diff 非空 → 先查 dump 生成器字节序假设（magic 是 LE 线上字节），
  再查目标端结构 padding——修复后重拍直至空输出；CI 缺 xtensa 环境时按
  ipct003 既有先例措辞登记 `SKIP(缺 xtensa 环境)，本机已实测第④路`
  （R16：不以 SKIP 冒充绿）。

### 9.2 层② UART transport runbook（批C）

**① 接线（六列）**：

| 针号（ESP32 devkit） | GPIO | 物理脚号 | 连接对象 | 信号方向 | 供电轨+共地 |
|---|---|---|---|---|---|
| GPIO17（UART2 TX） | GPIO17 | devkit 排针（丝印 P17） | USB 转串口板 RXD | ESP32 → 宿主 | 3.3V TTL 电平，严禁接 5V 轨；GND↔GND 共地（单点回宿主 USB 轨） |
| GPIO16（UART2 RX） | GPIO16 | devkit 排针（丝印 P16） | USB 转串口板 TXD | 宿主 → ESP32 | 同上 |
| GND | — | devkit GND 排针 | USB 转串口板 GND | — | 共地 |

注：批C 实装如改用 UART1 具体引脚，以批内实装替换前两行针号/GPIO 列，其余列
不变。

**② 宿主串口准备**：

- 操作步骤：

  ```
  # Linux（树莓派档）
  ls /dev/ttyUSB*
  stty -F /dev/ttyUSB0 115200 raw -echo
  # macOS 档
  ls /dev/tty.usbserial*
  ```

- 预期输出：Linux 回显 `/dev/ttyUSB0`；macOS 回显
  `/dev/tty.usbserial-XXXXXXXX`；`stty` 零输出即成功。
- 判定标准：设备节点存在 + stty 退出码 0。
- 失败处置：无设备节点 → macOS 装 CP2102 驱动后重插 / 换线缆；权限拒（Linux）
  → `sudo usermod -aG dialout $USER` 后重新登录。

**③ Linux 单测（三路径）**：

- 操作步骤：

  ```
  cargo test -p rr-ipc --features uart
  ```

  （feature 名按批C 实装定。）

- 预期输出：`test result: ok`；半帧/坏帧/正常帧三路径用例全绿。
- 判定标准：三路径全过——半帧（截断帧）与坏 magic（首字节改写帧）都必须拒收，
  正常帧完整往返。
- 失败处置：半帧用例红 → 读超时/水位参数排查；坏帧误收 → `rr3_frame_read`
  拒收路径回归（帧语义守卫是契约一部分，不许放松）。

**④ 板级 round-trip**：

- 操作步骤：宿主构造标准帧（128B 头 + payload，字节面按 golden dump）写入
  串口 → ESP32 收帧回发 → 宿主收回比对：

  ```
  cat frame.bin > /dev/ttyUSB0
  cat /dev/ttyUSB0 > frame.echo
  cmp frame.bin frame.echo
  ```

- 预期输出：ESP32 monitor 日志收帧行样例（形如 `frame received: len=192`，
  措辞随批C 实装）；`cmp` 空输出。
- 判定标准：128B 头 + payload 完整往返逐字节一致（cmp 空输出）。
- 失败处置：乱码 → 波特率不匹配特征，核对两端均为 115200；随机错帧 → GND
  未共地特征，核共地线；完全无响应 → TX/RX 接反（对调重试）。

**⑤ 坏帧注入（零代码，dd/head/cat）**：

- 操作步骤：

  ```
  # 半帧截断
  head -c 64 frame.bin > /dev/ttyUSB0
  # 坏 magic 首字节改写
  printf '\x00' | dd of=frame.bad bs=1 seek=0 conv=notrunc
  cat frame.bad > /dev/ttyUSB0
  ```

- 预期输出：ESP32 日志拒收行样例（形如 `reject: bad magic` /
  `reject: short frame`，措辞随批C 实装），随后正常帧仍可收发。
- 判定标准：两类注入均被拒 + 注入后不进死锁、后续正常帧收发不受影响。
- 失败处置：注入后死锁 → 帧状态机半帧残留清空路径排查（半帧后收到新帧 magic
  必须能重新同步）。

  下限）；harness 开口 BadMagic → CP2102 驱动输入缓冲残留（`Rr3UartConn::open`

**③ RAM 实测三点采样**：哨兵启动后 / 注册帧发出后 / round-trip 完成后三点调用
`esp_get_free_heap_size()` 打日志；实测报告按"场景 × 剩余堆"记录，RAM 峰值
估算列必填——RAM 峰值实测数是层③ 验收硬项（梯子表判据）。

**④ D1→D2 触发判据（数字口径）**：实测运行峰值剩余堆 < 20% 总堆（或 std 哨兵
不可起）即触发批D2。S3 迁移差异面清单：`--target esp32s3`、PSRAM 使能
（`CONFIG_SPIRAM`）；批D2 验收同 D1 判据（注册→心跳→round-trip + RAM 实测
报告）。

**⑤ 预期行为**：注册帧发出 → 心跳周期日志（`Rr3Beat` 三态对齐线上字节）→
round-trip 应答；`rr3.ctl.status` 可见哨兵条目在层④ 联调时核验（见 §9.4
步骤 3）。

**⑥ S3 切换预案（批D2，R19——D1 不可达时是必达手段不是收口出口；修订版 5
随批W6 扩为四件套）**：

- **触发条件（与 ④ 数字口径同源）**：D1 实测运行峰值剩余堆 < 20% 总堆
  （经典 ESP32 ~520KB SRAM 即 < ~104KB）**或** std 哨兵不可起（espidf 链在
  经典 ESP32 上 panic / 堆池不足）——触发即立批D2，不重开裁定（R19 已裁）。
- **target 差异点清单**（迁移即改三处，其余源码零改动——rr-ipc 契约面
  target 无关是层① 已证事实）：
  1. `.cargo/config.toml`：`target = "xtensa-esp32-espidf"` →
     `"xtensa-esp32s3-espidf"`（build-std 与 esp-clang 同链，批W1 冒烟件
     换 target 复跑即验）；
  2. `sdkconfig.defaults` 追加：`CONFIG_SPIRAM=y` + 堆池分配项
     （`CONFIG_SPIRAM_USE_MALLOC` 系，按 esp-idf v5.2.2 实装对表）+ S3
     Flash/晶振项；
  3. 烧录器差异：S3 devkit 原生 USB-Serial-JTAG（无外部 CP2102 亦可烧），
     espflash 参数按 S3 口径。
- **到货验收单（S3 devkit 四项，采购入库即验）**：
  | 项 | 操作 | 判定 |
  |---|---|---|
  | USB 口 | 插机看 `ls /dev/tty.usbmodem*`（JTAG 口）/ `tty.usbserial*`（UART 口） | 两口至少其一在列；bare-metal 烧录走 JTAG 口 |
  | Flash 容量 | `esptool.py flash_id` | ≥ 8MB（N8 级起——PSRAM 版本号 N8R8/N16R8 前段即 Flash 大小） |
  | PSRAM 在板 | `esptool.py flash_id` 回显 + sdkconfig 使能后 `CONFIG_SPIRAM` 启动日志 | 回显含 PSRAM/ octal 字样；哨兵启动日志无 PSRAM 缺失 panic |
  | 引脚兼容 | 对照哨兵实装引脚（UART2 = GPIO16/17 在 S3 上仍可用；`CONFIG_SPIRAM` octal 占用 GPIO35–37 注记） | 实装引脚与 SPIRAM 占用引脚无交叠 |
- **失败处置**：PSRAM 使能后启动 panic → `CONFIG_SPIRAM_SPEED` / octal 模式
  项对表 esp-idf 5.2.2 例程；烧录器不识别 → 换 JTAG 口 / 装驱动；
  迁移后 D1 同判据复验（注册→心跳→round-trip + RAM 实测报告），**报告照交，
  S3 上不再有二级降级**（R19：D2 不可达 = 层③④ 无出口，如实红灯——事实
  上 S3 2MB+PSRAM 较经典 ESP32 有 4× 以上余量，风险敞口已闭合）。

### 9.4 层④ e2e runbook（批E）

**① rr3-bridge 启动**（参数名随批E 实装对齐，R15 形态）：

- 操作步骤：

  ```
  rr3-bridge --uart /dev/ttyUSB0 --baud 115200 --socket /var/run/rock3-ipc.sock
  ```

- 预期输出：桥日志 UART 链路就绪行样例（形如 `uart link up`）。
- 判定标准：桥进程存活且 UART 设备打开成功。
- 失败处置：设备打开失败 → 回 §9.2 ② 串口准备；socket 路径权限 → 目录与
  umask 核验。

**② rrd 启动**：

- 操作步骤：`rrd --manifest <真模块 manifest 目录>`（哨兵经桥以完整 register
  语义进城，不在 rrd 侧预注册——R15）。
- 预期输出：rrd 启动日志 + 监听 socket 就绪行。
- 判定标准：rrd 存活；两种启动顺序（先桥后 rrd / 先 rrd 后桥）都验——桥应答
  rrd 未起时须重试注册面。
- 失败处置：时序失败 → 桥重试逻辑排查（属批E 缺陷，不属运行豁免）。

**③ e2e 五步**：

1. 桥启动（①）。
2. 哨兵经桥注册 → 桥日志注册行样例。
3. `rrctl status` 观察哨兵在册条目——预期回显：模块列表含哨兵 id、心跳三态
   正常。
4. 总线任一模块 ↔ 哨兵 round-trip：点名主题对（如 `rr3-act/…` RPC → 哨兵回应
   答帧）双方日志样例。
5. 心跳持续与断链恢复：拔 UART → 桥断链日志 → 重插 → 桥重连 → 哨兵再注册 →
   `rrctl status` 回到在册。

- 判定标准：五步全过；断链恢复后注册/心跳/收发全链路自愈。
- 失败处置：注册被拒 → 核哨兵 register 帧 src 与前缀语义（rrd 反伪装校验是
  正确行为，改哨兵不改 rrd）；round-trip 超时 → 主题归属对表（装配单
  bindings）。

**④ 桥零策略断言核对清单**：桥不持主题清单（源码审查项，批E 提交说明附核对
结论）；未注册主题经桥直灌后被 rrd 拒（拒收日志样例入验收记录）。

**⑤ e2e 双档判据（修订版 5 随批W6，Q6 裁定双档；批E 按 macOS 档验收，树莓派
档板上线即补——0.0.6 已收口，硬件在册）**：

两档共用 §9.4 ①–④ 流程骨架（桥启动 → rrd 启动 → e2e 五步 → 零策略核对），
差异只在宿主与总线对端面：

| 项 | macOS 档（批E 验收档，Q6 宿主） | 树莓派档（板上线即补，真部署面） |
|---|---|---|
| UART 设备 | `/dev/tty.usbserial-*`（CP2102，USB 转串口板 + 数据线） | `/dev/ttyUSB0`（USB 转串口板）或 GPIO UART 直连 |
| 宿主进程面 | rrd（本机构建）+ `rr3-bridge` + ESP32 哨兵 + **总线对端 = `sim_peer` 真模块**（rr3-interact 身份，`publish_once` 发契约主题，tools/sim 构建产物，`--socket` 指向同一 rrd） | rrd（deb 系统实例或演练实例）+ `rr3-bridge` + ESP32 哨兵 + 真模块面（六模块 deb 在册，rr3-interact 天然在总线） |
| rrd 启动 | `rrd --manifest <sim_peer manifest 目录>`（同演练口径） | `rrd --profile <装配单>` 正门（与 rr3.service ExecStart 同形） |
| 端口冲突规避 | 无（本机无 deb 实例） | **演练实例统一注入 `RR3_SIM_PANEL_ADDR=127.0.0.1:18080`**（批F4 口径：8080 归 deb 系统实例，常量在 drill.rs 的 `RR3_SIM_PANEL_ADDR`） |
| 巡检判据 | `rr3-ctl status` 含哨兵 + sim_peer 条目、**`denied_publish = 0`**、health 心跳三态正常 | 同左 + 对照 deb 实例并存（`rr3.ctl.logs` 区分两实例日志环） |
| round-trip | sim_peer 发点名 → 哨兵应答（点名主题对按装配单 bindings / 哨兵 manifest `[rpc].exposes`） | 总线任一真模块 ↔ 哨兵按在册主题收发 |
| 断链恢复 | 拔 USB → 桥断链日志 → 重插 → 自愈再注册（§5.1 第 5 条三态） | 同左（GPIO UART 档拔线 = 断 GND/TX/RX 三线） |

- **判定标准**：两档各自五步全过 + `denied_publish = 0` + 断链自愈 + 零策略
  核对清单（④）四条全过；macOS 档过 = 批E 结项，树莓派档补录 = 层④ 真部署
  面收口（status.md 重锚时如实区分两档状态）。
- **失败处置**：sim_peer 与哨兵抢前缀 → 两 manifest 身份分立（rr3-interact
  归 sim_peer，哨兵用独立 manifest 名，`Rr3RegisterError::Duplicate` → Busy
  即此症）；macOS 无设备节点 → CP2102 驱动后重插（§9.2 ② 同款）；树莓派档
  与 deb 实例 socket 冲突 → 演练实例走 `--socket` 换路径（`/tmp/rock3-ipc-e2e.sock`
  档），桥 `--socket` 同步指过去。

**⑥ 实装对表（批E E6/E7 落档，修订版 12）**——runbook 判据不动，补四条真板
实测实锤与两处实装订正：

- **E6 本机彩排（真板前先行）**：tools/rr3-sentinel-harness 假哨兵 + 假 rrd
  对拍全绿（PASS=18），揪出一处 harness 盲区——假哨兵点名帧 src 恒为
  `RR3_TASK_RRD(1)`，恰蒙混 rrd conn 上行 dst 门（`dst_task == RR3_TASK_RRD`），
  真 rrd 在链后才暴露；哨兵 handle_request 应答 dst 改钉 `RR3_TASK_RRD`（修复件
  `870cfe6`），harness bus_frame 补 src_task 入参变回归网。**教训**：对拍件
  src/dst 恒等真值时，地址门类缺陷会被静默遮蔽——对手件字段须可注入。
- **串口节点 macOS 档实装订正**：§9.4 ①/⑤ 命令样例与表格的 `/dev/ttyUSB0`、
  `/dev/tty.usbserial-*` 实装一律用 **`/dev/cu.usbserial-*` callout 节点**——
  `tty.*` callin 节点 open 返回 EBUSY（Resource busy os error 16），与占用无关；
  D1 harness 成功路径同款。Linux 档 `/dev/ttyUSB0` 不受影响。
- **串口参数生效机制**：`stty -f <dev> 115200 raw` 配置在设备 close 后丢失
  （macOS termios 不持久），"先 stty 后 open"读到的是 9600 缺省——表现恰似
  物理断链（Magic 全碎、零 JSON 特征）。判别法：cat 直听若收到 **magic
  `31 45 52 41`（"1ERA"）** 开头字节流即物理层通、参数错；串口参数必须与
  读写同 fd 生效（rust serialport open 后即 ioctl，与 D1 同构）。
- **并发 open 与复位时序**：macOS 允许重复 open 同一 USB 串口节点——残留旧桥
  会静默截走数据（新桥不报错但收不到帧）；清场必须 `ps` 核对 0 残留而非只看
  `kill -0`（桥带重试循环，进程存活≠链路活，"桥进程存活"判据须与
  `uart link up` 日志行同验）。另：桥 open CP2102 的 DTR/RTS 翻转会复位
  ESP32，板子 boot 时机不受脚本控制——哨兵 10s 注册窗口（超时退场不重试，
  §9.3 实装语义）要求 **rrd socket 先于任何复位点就绪**，e2e 脚本时序按
  "桥起 → rrd socket 就绪轮询 → monitor 连接（复位观测面）"排布；monitor 持
  UART0（console 观测面）与桥持 UART2（数据链路）两设备不冲突，可全程抓
  板侧日志。
- **（批G G7 登记②）设备路径稳定面**：Linux 的 `/dev/ttyUSB*N*` 编号按枚举序
  分配——多串口共存或重启后 `ttyUSB0`/`ttyUSB1` 会互换，脚本里写裸 `ttyUSB0`
  就是给断链自愈埋"重插后指到别人"的雷。CP2102 的稳定路径由 udev 内建规则自动
  在册：**`/dev/serial/by-id/usb-Silicon_Labs_CP2102N-*-if00-port0`**（序列号
  唯一，插拔/重启不漂）；macOS 档 `/dev/cu.usbserial-0001` 天然带序列号同样
  稳定。桥 `--uart` 与 harness 设备参数一律传稳定路径；E7 断链自愈"插回重开"
  的判据也因此才成立——路径漂了自愈对象就换了。
- **（批G G7 登记③）sim_peer 档位注记**：e2e 对端 `sim_peer` 的 manifest 档位
  （heartbeat/watchdog 等）是 **sim 量级假设**，不是板上哨兵真值；复用 e2e
  形状做真板判据时，对表名义值的**唯一来源 = 注册 manifest 在场值**（§9.4 ⑤
  表格 round-trip 行同口径）——批G ⑦ 列 harness 对表判据已按此实现（hb 取
  注册 manifest，jitter 取 profiles/esp32-mini.toml 声明），sim_peer 档位
  不得参与任何对表。
