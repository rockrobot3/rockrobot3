## 1 背景与目标

**为什么 ESP32 是正确的系统级验证物**：ADR-0013 把 rock3 交付物定义为"Linux 起来
之后的一切"，此前全部验证（x86 宿主、aarch64 交叉、树莓派真板）都在 **Linux 可用**
的前提下成立。ESP32 上没有 Linux——若契约头、帧读写、transport 语义**脱离 Linux
仍然成立**，rock3 的"契约即资产"就从 Linux 系主张升级为跨系统类别主张；这正是
"换开发板能快速部署"理念的极端边界测试。

**模型边界（不推翻 ADR-0013）**：ESP32 不进三层模型（Layer 0/1/2 语境是 Linux
起来之后），不走 deb/payload 路径。本版验证的是 **Layer 1 的两个最底层资产**——
契约（rr-ipc 编解码）与传输（transport trait）——能否移植；模块语义（装配单、
仲裁、降级）仍归 Linux 侧。0.0.6 §7 候选路径 **a. 桥接模块**被采纳为层④ 形态，
**b. 协处理器**角色维持 ADR-0015 裁定 4 的后置归属。

**四层验证梯子（R5 裁定原文展开）**：

| 层 | 内容 | 必达性 | 判据 |
|---|---|---|---|
| ①契约 parity | rr-ipc 编解码在 xtensa 目标编译 + golden dump 对拍 | **必达** | 编译期 const 断言过 = 任意目标成立；`ipct003` 四路对拍（x86 / aarch64 交叉 / 容器 arm64 / xtensa）golden 逐字节一致——IPC-T-003 第④路 |
| ②传输第三实现 | UART transport（补 ADR-0008 第三实现位） | **必达** | Linux 侧单测帧往返；ESP32 板级 round-trip（128B 头 + payload 完整收发，半帧/坏帧拒收路径表现正确） |
| ③模块层 | esp-rs std 最小哨兵模块（注册 / 心跳 / 回应答） | **必达**（R19） | 哨兵经 bridge 上总线完成一次完整注册→心跳→round-trip；RAM 峰值有实测数 |
| ④系统集成 | Linux 侧 rr3-bridge 桥接模块接真总线跨芯片 e2e | **必达**（R19） | 树莓派/mac 上 rrd 带 bridge，总线任一模块与 ESP32 对端按既有主题收发成功 |

层③④不可达时的处置（R19 后裁覆盖 R5 原档位，R5 原文见 0.0.5 §2.1 与本文件
修订版 1–3 记录段）：经典 ESP32 实测 RAM 不可达即触发批D2——ESP32-S3（RAM
512KB→2MB 级 + PSRAM）采购入库，target/PSRAM 迁移后按同判据继续真板验收，
**四层全真板验收，无"受阻态收口"出口**；RAM 峰值实测数仍必记（D1→D2 触发判据
数字口径见 §9.3）。

### 2.2 缺口（0.0.7 要补的）

1. **xtensa 工具链未装（R10：升级为 WBS 显式依赖）**：esp-rs rust 工具链（Xtensa
   target 是 fork，非 upstream rustup 直接可装）——**独立成批A'（工具链前置批，
   层① 之前）**，"装不上"不再只是风险注脚而是 WBS 显式门：批A' 不绿则批B（层①）
   不得启动，改走 P1 缓解（远端 CI Linux runner 跑 xtensa）。
2. **UART transport 不存在**：tcp 都只有签名（ADR-0008 不写半成品），UART 零行。
3. **esp-rs 侧依赖面未验证**：std 模式（esp-idf-sys）在经典 ESP32 上的内存足迹
   需实测——层③④ 的裁定输入。
4. **rr3-bridge 桥接中继不存在**（R15 订正：**transport 级连接多路器**，tools/
   伴生件，不进 manifest 注册面——对端哨兵以完整 register 语义经桥直灌 rrd，桥
   只是 UART↔UDS 字节管道）。
5. **ESP-IDF 密钥门遗留敞口**：随批A 一并清理（0.0.6 §7 遗留联动条款）。

## 3 裁定问题（Q1–Q6，已裁——R20）

> 裁定记录区：Q1–Q6 已随 0.0.5 增补轮三 R20 全部裁定（2026-10-06），裁定行已
> 逐题回填如下——修订版 1–3 期间"仍待裁"状态至此终止；各题裁定只落档位结论，
> 论证细节以题内建议口径为准。

### Q1：层② 传输介质——UART vs USB-CDC

- **建议 a：UART**——经典 ESP32 **无原生 USB**（S2/S3 才有 USB-CDC/OTG），板上
  CP2102 只是 USB-UART 桥；直连 UART 引脚（3.3V TTL）接树莓派/mac USB 转串口
  亦通。速率 115200 起步（帧最大 128 + payload，半容量守卫在环内不适用——UART
  无环，靠流控与帧语义拒收）。**transport trait 第三实现位按 UART 落**，线上
  帧格式不变。
- b：USB-CDC——需换 S3 板，违反"经典 ESP32 在手"事实，弃。

  **裁定**：a（UART）——transport trait 第三实现位按 UART 落，线上帧格式不变
  （0.0.5 §2.4 R20，2026-10-06）。

### Q2：层③ 运行时——esp-rs std vs no_std

- **建议 a：esp-rs std**（esp-idf-sys / esp-idf-hal，FreeRTOS 任务）——模块语义
  （注册/心跳状态机）用 std 写与 Linux 侧同构；代价是 ESP-IDF 构建链重 +
  内存足迹大，正是"按实测内存裁"的实测对象。
- b：no_std 裸机轮询——内存最小，但层③"模块层语义可移植"的验证力弱化
  （裸机写不出同构状态机，只剩字节回声），且 no_std 下 std trait 面（Read/Write）
  缺失，transport blanket impl 复用不了。作为层③④ 裁"不可达"时的降级备选保留。

  **裁定**：a（esp-rs std）；b（no_std）的"降级备选"出口随 R19"无受阻态收口"
  口径失效——受阻即批D2 换板续做，不再降级（0.0.5 §2.4 R19/R20，2026-10-06）。

### Q3：层③④ 必达性口径

- **建议（R5 原口径确认）**：层①②必达是版本 DoD 硬项；层③④做成即超额、
  实测 RAM 不可达则登记"层①②已证 + 层③④受阻于实测内存 X KB < 需求 Y KB"并
  出 ESP32-S3 换板建议进采购敞口。**验收判据不许为凑数降级**（如砍心跳只留
  回声——回声不是模块语义）。

  **裁定**：R19 后裁覆盖本题 R5 原档位——层③④ 必达，实测不可达即批D2 采购
  ESP32-S3 移植续做，四层全真板验收，无受阻态收口；"验收判据不许为凑数降级"
  原句继续有效（0.0.5 §2.4 R19/R20，2026-10-06）。

### Q4：rr3-bridge 归属与形态

- **建议（修订版 2 按 R15 订正）**：桥 = **transport 级连接多路器**——每哨兵一条
  独立 uds 连接，UART 字节流直灌对应连接（UART↔UDS 纯字节搬运，不解析模块语义）；
  对端哨兵自己发 register 帧，以完整注册/心跳/前缀语义进城，rrd 语义零改动、
  **零新契约从结构上成立**（rrd 现行反伪装 src 校验与前缀归属即白名单）。桥因此
  **不进 manifest 注册面**（原建议"进注册面"按 R15 订正——原弃案理由"绕过注册面
  即第二套模块语义"失效：对端走完整语义，桥不经模块语义），形态为 tools/ 伴生
  Rust crate（与 sim_peer 同级）。层④判据不变（总线任一模块 ↔ ESP32 对端按在册
  主题收发）。
- 原建议"新立 `modules/rr3-bridge` 进 manifest 注册面 + 只透传白名单"弃——透传
  register 帧会被 rrd 按 spoofed src 拒（每连接一身份），桥 NAT 改写 src 则点对点
  dst 语义坏；本节为建议口径的 R15 订正，Q4 已随 R20 裁定（裁定行见上）。

  **裁定**：R15 订正后的建议口径成立——桥 = transport 级连接多路器，tools/
  伴生 crate（与 sim_peer 同级），不进 manifest 注册面，哨兵完整 register 语义
  进城，零新契约（0.0.5 §2.4 R20，2026-10-06）。

### Q5：ESP-IDF 密钥门清理口径

- **建议**：批A 随方案落档一并清理历史遗留敞口——ESP-IDF 不进本仓（构建依赖
  外置，写明版本与获取方式进 boards 笔记），密钥门按 0.0.4 批D 同款处置（不
  claim 即注销）。若层③ 裁 std 路线，ESP-IDF 是外部工具链依赖不是仓内资产。

  **裁定**：建议口径成立——ESP-IDF 外置不进本仓 + 密钥门按 0.0.4 批D 同款
  注销（0.0.5 §2.4 R20，2026-10-06）。

### Q6：验收环境——桥接 e2e 的 Linux 侧宿主

- **建议**：e2e 分两档——本机 macOS（/dev/tty.usbserial，开发期日跑）+ 树莓派
  （/dev/ttyUSB0 或 GPIO UART，0.0.6 板上批后复用）。树莓派档依赖 0.0.6 批F4
  完成（装配链已含真硬件面），不阻塞 0.0.7 批B/C/D。

  **裁定**：macOS + 树莓派双档成立（0.0.5 §2.4 R20，2026-10-06）。

## 5 设计要点

- **层① 的"编译即证明"**：header.rs const 断言的价值在 xtensa 上兑现——不需要
  跑测试，目标编译通过即偏移/长度/magic 冻结成立。golden dump 对拍是第二重
  （运行期编码线上字节 vs 黄金文件），两重独立。
- **UART transport 的接缝纪律**：只实现 trait 三件套，**不新增关联类型、不改
  签名**（ADR-0008 接缝定型）；ESP32 侧复用同一 rr-ipc crate 源（`cfg` 目标分
  平台实现，帧语义源码共享）——这是"契约即资产"的字面兑现：同一份编解码源码
  在两测编译，不存在"ESP32 版协议"。
- **内存裁定先行（批D 的第一产出是实测报告）**：哨兵最小语义（注册一帧 + 心跳
  周期帧 + 应答一帧）先在板子跑起来量 RAM，再谈功能完整度——顺序反了就是
  先写半成品。
- **桥零策略（R15）**：桥是 UART↔UDS 字节管道（连接多路器），不解析模块语义、
  不做白名单——放行面由 rrd 现行注册/前缀归属/反伪装 src 校验承担（未注册主题/
  伪造 src 本来就拒，fail-closed 同款纪律）；桥不持任何主题清单，装配单 bindings
  不需要为桥改一行（修订版 2 前"透传白名单"口径按 R15 订正）。
- **与 pcm STREAM 空缺的关系**：语音面若延伸到 ESP32（拾音协处理器），pcm
  schema 冻结与 shm 接线绑定同一 ADR 的裁定（0.0.5 Q3）不变——本版**不碰
  STREAM 负载**，哨兵与 e2e 只用 Event/Request 级主题。

## 9 四层真板执行手册（修订版 4 新增）

> 体例：每条验收判据四件套——操作步骤（完整命令）→ 预期输出（回显样例）→
> 判定标准（过/不过分界）→ 失败处置（逐失败模式分支）。本手册是批B/C/D1/D2/E
> 的执行依据；批内实装参数（feature 名、桥参数名、日志措辞）以批内实装为准
> 替换，操作骨架与判定分界不因实装细节变。

### 9.1 层① 契约 parity runbook（批B）

**① 工具链核验（批A' 延伸，进批B 前置自检）**：

- 操作步骤：

  ```
  espup install
  rustup toolchain list
  cargo +esp --version
  ```

- 预期输出：`rustup toolchain list` 回显含 `esp` 工具链行（形如
  `esp-1.xx.x` (override)）；`cargo +esp --version` 回显 cargo 版本号
  （形如 `cargo 1.xx.x (esp)`）。
- 判定标准：三条命令零报错即过。
- 失败处置：espup 安装失败 → 改走 esp-rs 官方 rust-build 安装脚本（按当时
  官方文档定，批A' 已备等价路径）；fork 工具链与 workspace 锁不匹配 → 按
  esp-rs release 对表后重装对应版本。

**② xtensa 目标编译（编译即证明）**：

- 操作步骤：

  ```
  cargo +esp build -p rr-ipc --target xtensa-esp32-none-elf
  ```

- 预期输出：`Finished dev [optimized ...] target(s)`；header.rs 编译期 const
  断言（偏移连续 / 头长 128 / magic LE 线上字节 / payload 枚举冻结）全部静默
  通过。
- 判定标准：编译成功即过——const 断言是编译期门，无运行期判据；同一份编解码
  源在 x86 与 xtensa 两侧编译通过 = 平台无关成立。
- 失败处置：目标缺 std 组件 → esp fork 工具链加装 std 组件后重试；const 断言
  炸 → 编解码源被平台假设污染（指针宽度/对齐假设），如实登记为层① 抓到的缺陷
  并修复——修复属批B 范围，不属豁免。

**③ ipct003 第④路对拍**：

- 操作步骤（第④路接入随批B 落 ipct003.sh）：

  ```
  # 生成 xtensa golden dump（命令随批B 实装落 ipct003.sh，此处为操作骨架）
  # 四路逐字节对拍（x86 / aarch64 交叉 / 容器 arm64 / xtensa）
  diff contracts/golden/event-header-128.hex <xtensa 路 dump>
  ```

- 预期输出：`diff` 空输出——四路 dump 逐字节一致。
- 判定标准：四路 diff 全空 = 过；任一路非空 = 不过。
- 失败处置：diff 非空 → 先查 dump 生成器字节序假设（magic 是 LE 线上字节），
  再查目标端结构 padding——修复后重拍直至空输出；CI 缺 xtensa 环境时按
  ipct003 既有先例措辞登记 `SKIP(缺 xtensa 环境)，本机已实测第④路`
  （R16：不以 SKIP 冒充绿）。

### 9.2 层② UART transport runbook（批C）

**① 接线（六列）**：

| 针号（ESP32 devkit） | GPIO | 物理脚号 | 连接对象 | 信号方向 | 供电轨+共地 |
|---|---|---|---|---|---|
| GPIO17（UART2 TX） | GPIO17 | devkit 排针（丝印 P17） | USB 转串口板 RXD | ESP32 → 宿主 | 3.3V TTL 电平，严禁接 5V 轨；GND↔GND 共地（单点回宿主 USB 轨） |
| GPIO16（UART2 RX） | GPIO16 | devkit 排针（丝印 P16） | USB 转串口板 TXD | 宿主 → ESP32 | 同上 |
| GND | — | devkit GND 排针 | USB 转串口板 GND | — | 共地 |

注：批C 实装如改用 UART1 具体引脚，以批内实装替换前两行针号/GPIO 列，其余列
不变。

**② 宿主串口准备**：

- 操作步骤：

  ```
  # Linux（树莓派档）
  ls /dev/ttyUSB*
  stty -F /dev/ttyUSB0 115200 raw -echo
  # macOS 档
  ls /dev/tty.usbserial*
  ```

- 预期输出：Linux 回显 `/dev/ttyUSB0`；macOS 回显
  `/dev/tty.usbserial-XXXXXXXX`；`stty` 零输出即成功。
- 判定标准：设备节点存在 + stty 退出码 0。
- 失败处置：无设备节点 → macOS 装 CP2102 驱动后重插 / 换线缆；权限拒（Linux）
  → `sudo usermod -aG dialout $USER` 后重新登录。

**③ Linux 单测（三路径）**：

- 操作步骤：

  ```
  cargo test -p rr-ipc --features uart
  ```

  （feature 名按批C 实装定。）

- 预期输出：`test result: ok`；半帧/坏帧/正常帧三路径用例全绿。
- 判定标准：三路径全过——半帧（截断帧）与坏 magic（首字节改写帧）都必须拒收，
  正常帧完整往返。
- 失败处置：半帧用例红 → 读超时/水位参数排查；坏帧误收 → `rr3_frame_read`
  拒收路径回归（帧语义守卫是契约一部分，不许放松）。

**④ 板级 round-trip**：

- 操作步骤：宿主构造标准帧（128B 头 + payload，字节面按 golden dump）写入
  串口 → ESP32 收帧回发 → 宿主收回比对：

  ```
  cat frame.bin > /dev/ttyUSB0
  cat /dev/ttyUSB0 > frame.echo
  cmp frame.bin frame.echo
  ```

- 预期输出：ESP32 monitor 日志收帧行样例（形如 `frame received: len=192`，
  措辞随批C 实装）；`cmp` 空输出。
- 判定标准：128B 头 + payload 完整往返逐字节一致（cmp 空输出）。
- 失败处置：乱码 → 波特率不匹配特征，核对两端均为 115200；随机错帧 → GND
  未共地特征，核共地线；完全无响应 → TX/RX 接反（对调重试）。

**⑤ 坏帧注入（零代码，dd/head/cat）**：

- 操作步骤：

  ```
  # 半帧截断
  head -c 64 frame.bin > /dev/ttyUSB0
  # 坏 magic 首字节改写
  printf '\x00' | dd of=frame.bad bs=1 seek=0 conv=notrunc
  cat frame.bad > /dev/ttyUSB0
  ```

- 预期输出：ESP32 日志拒收行样例（形如 `reject: bad magic` /
  `reject: short frame`，措辞随批C 实装），随后正常帧仍可收发。
- 判定标准：两类注入均被拒 + 注入后不进死锁、后续正常帧收发不受影响。
- 失败处置：注入后死锁 → 帧状态机半帧残留清空路径排查（半帧后收到新帧 magic
  必须能重新同步）。

### 9.3 层③ 哨兵模块 runbook（批D1/批D2）

**① esp-rs std 项目骨架**：Cargo.toml 依赖清单（esp-idf-sys / esp-idf-hal /
std 线程，版本与批A' 工具链对表）、`.cargo/config.toml` 要点
（`target = "xtensa-esp32-none-elf"`、runner = espflash）、
sdkconfig.defaults 关键项全文：

```
CONFIG_FREERTOS_HZ=1000
CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192
```

（批D2/S3 迁移追加：`CONFIG_SPIRAM=y` 及 S3 target 相关项，按 esp-idf 实装
对表。）

**② 烧录与监视**：

- 操作步骤：

  ```
  idf.py build flash monitor
  ```

  （或 esp-idf-sys 桥接的 `cargo run` 等价序列；monitor 退出键 `Ctrl+]`。）

- 预期输出：monitor 回显启动横幅 + 哨兵启动日志（含 SURFACE 自述样例行）。
- 判定标准：烧录成功 + monitor 进入且无 panic。
- 失败处置：flash 分区不足 → 分区表裁剪；macOS 驱动 → 装 CP2102 驱动后重插；
  栈溢出 panic（`Guru Meditation` 特征）→ 调 `CONFIG_ESP_MAIN_TASK_STACK_SIZE`。

**③ RAM 实测三点采样**：哨兵启动后 / 注册帧发出后 / round-trip 完成后三点调用
`esp_get_free_heap_size()` 打日志；实测报告按"场景 × 剩余堆"记录，RAM 峰值
估算列必填——RAM 峰值实测数是层③ 验收硬项（梯子表判据）。

**④ D1→D2 触发判据（数字口径）**：实测运行峰值剩余堆 < 20% 总堆（或 std 哨兵
不可起）即触发批D2。S3 迁移差异面清单：`--target esp32s3`、PSRAM 使能
（`CONFIG_SPIRAM`）；批D2 验收同 D1 判据（注册→心跳→round-trip + RAM 实测
报告）。

**⑤ 预期行为**：注册帧发出 → 心跳周期日志（`Rr3Beat` 三态对齐线上字节）→
round-trip 应答；`rr3.ctl.status` 可见哨兵条目在层④ 联调时核验（见 §9.4
步骤 3）。

### 9.4 层④ e2e runbook（批E）

**① rr3-bridge 启动**（参数名随批E 实装对齐，R15 形态）：

- 操作步骤：

  ```
  rr3-bridge --uart /dev/ttyUSB0 --baud 115200 --socket /var/run/rock3-ipc.sock
  ```

- 预期输出：桥日志 UART 链路就绪行样例（形如 `uart link up`）。
- 判定标准：桥进程存活且 UART 设备打开成功。
- 失败处置：设备打开失败 → 回 §9.2 ② 串口准备；socket 路径权限 → 目录与
  umask 核验。

**② rrd 启动**：

- 操作步骤：`rrd --manifest <真模块 manifest 目录>`（哨兵经桥以完整 register
  语义进城，不在 rrd 侧预注册——R15）。
- 预期输出：rrd 启动日志 + 监听 socket 就绪行。
- 判定标准：rrd 存活；两种启动顺序（先桥后 rrd / 先 rrd 后桥）都验——桥应答
  rrd 未起时须重试注册面。
- 失败处置：时序失败 → 桥重试逻辑排查（属批E 缺陷，不属运行豁免）。

**③ e2e 五步**：

1. 桥启动（①）。
2. 哨兵经桥注册 → 桥日志注册行样例。
3. `rrctl status` 观察哨兵在册条目——预期回显：模块列表含哨兵 id、心跳三态
   正常。
4. 总线任一模块 ↔ 哨兵 round-trip：点名主题对（如 `rr3-act/…` RPC → 哨兵回应
   答帧）双方日志样例。
5. 心跳持续与断链恢复：拔 UART → 桥断链日志 → 重插 → 桥重连 → 哨兵再注册 →
   `rrctl status` 回到在册。

- 判定标准：五步全过；断链恢复后注册/心跳/收发全链路自愈。
- 失败处置：注册被拒 → 核哨兵 register 帧 src 与前缀语义（rrd 反伪装校验是
  正确行为，改哨兵不改 rrd）；round-trip 超时 → 主题归属对表（装配单
  bindings）。

**④ 桥零策略断言核对清单**：桥不持主题清单（源码审查项，批E 提交说明附核对
结论）；未注册主题经桥直灌后被 rrd 拒（拒收日志样例入验收记录）。
