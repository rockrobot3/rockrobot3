## 专题一：机制与策略分离核查（结论：成立，零泄漏）

判据：机制核不得出现"按模块名/平台名分支"；策略（阈值/超时/主题/型号/接线）只以数据形式存在于
profiles / 模块 config.toml / contracts / hardware/<形态>/wiring.toml / manifest；Rust 代码读数据、
参数注入，不内嵌现场可调策略。

证据点：
- `tools/periph-mech/src/periph_core.rs`：`rr3_axis_check` / `rr3_servo_gate` 均为纯函数——轴名、
  行程、角度、轨压等级全部由调用方注入，无模块名/平台名分支。
- `base/runtime/rr-mech/src/control.rs`：文件头即声明"控制原语与安全核是纯计算、时钟与输入由
  外部注入、零策略载荷"；`Rr3ReflexCfg` 只存机制参数（循环频率、饱和通告间隔），注释钉死
  "只认参数不认来源"。
- 策略数据面抽样：e2e 夹具把低电阈值/电压曲线/充电周期写在测试 `CONFIG` 数据里而非机制代码；
  装机布局 `manifest.toml`/`bin`/`config.toml` 随装、entry 由 post-build.sh 改写为装机绝对路径
  ——策略数据与机制产物在交付链分离。
- 本轮全扫描未发现策略常量泄漏进机制核或按平台名分支的 Rust 代码。

## 专题二：红项修复 B-12（测试基建确定性）

**现象**：门禁 ① `cargo test --workspace` 红，`e2e_power` 在 `pkill -f <二进制绝对路径>` 处失败
（macOS：`Regular expression evaluation error (illegal byte sequence)`），非被测逻辑失败。

**根因**：pkill 扫全进程表做 regex 匹配——无关进程的非法字节串会让整批匹配报错退出，
夹具断言因此随机变红；外部工具＋全表扫描＋locale 敏感三者叠加，是夹具确定性缺口。

**修复**：从 supervisor 已有的 `spawn <name> pid=<N> entry=…` 日志行取 pid（复用
`rr3_field_from_log`），定点 `kill -TERM <pid>`。附带收益：把"模块必须仍是首实例"从隐含前提
升级为显式断言（pid 失配即红）。

**同类面复核**：`e2e_spawn_restart.rs` / `e2e_depends.rs` 的 `ps -p <pid> -o command=` 是
定点查询、无 regex、失败忽略的"尽力卫生"，与判据解耦——无同类风险，不动。
