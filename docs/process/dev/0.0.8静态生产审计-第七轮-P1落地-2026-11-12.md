# 0.0.8 静态生产审计·第七轮 —— P1 四项落地与验证（2026-11-12）

审计对象：0.0.8 静态生产审计第六轮后遗留的 P1 项（I2S 平台表、decisions 死哈希注记、
质量度量基线、门 a 红账、M6 OTA 写侧）。每件按"事实 → 判据 → 处置 → 验证"四段记录，
验证以 `tools/ci/check.sh` 全量门与专项度量（`tools/ci/metrics.py`）的实跑输出为准。

## 件一 平台表 I2S 裁定（P1-1）

**事实**：板侧确有 I2S0 音频面——经典 ESP32 BCLK=GPIO4 / SD=GPIO27 / WS=GPIO26，
S3 BCLK=GPIO6 / SD=GPIO15 / WS=GPIO7（两处真值点均在
`tools/esp32-periph-base/src/board/pins_classic.rs` / `pins_s3.rs` 引脚真值段，
并各有 `RR3_BIND_I2S_*` 装配对账锚）；但 `contracts/platform/esp32.toml`、
`esp32s3.toml` 的 `[[controller]]` 词表里没有 I2S。

**判据**：平台表的 `kind` 是封闭七值
（`pwm/gpio/i2c/spi/vspi/adc/uart`，单点 `rr-registry/src/platform.rs`
`RR3_PLATFORM_KINDS`），无 `i2s`。平台表承载的是"可分配通道资源"的事实
（③-b 通道上界、④-b 互斥反推、⑧ 构造对账）；I2S 的三条信号脚由 board 侧
esp-idf-hal 具名装配直给（§4.5 生成物表第 3 行），不进装配单 `[[pin]]` 角色域，
既无 role 消费者，也无通道上界与互斥集判据需求。

**处置**：**不登记 I2S**，按契约级变更边界在两表内立明文注记（不扩 `kind` 词域）——
扩词域属"加一类外设 = 同批改多处"的契约级评审（`contracts/roles.toml` 头注），
不属平台表补登记的顺手动作；音频面事实真值点维持在 board 引脚真值段单点，本表
不抄第二份。注记同时写明"何时再进表"：I2S 成为可分配角色（多路音频/编解码器
选型）时，按契约级流程扩 `kind` 词域并落 `[[controller]]` 与 `[[conflict]]`。

**验证**：两表仍是合法 TOML 且形状校验不红——`cargo test -p rr-registry`
（67 单测 + 47 contract 用例，含四张平台表的 parse/形状用例）全过；`check.sh`
③-b/④-b/⑤-a/⑧ 段不红（见件四全量复跑）。注记只增注释行，键集零变动。
一处实证：注记初稿在注释里写了 `[controller_wordform]` 字面量，platform.rs 的
反例用例用字符串替换注入坏键，被注释里的同名文本命中而红——已改成"词形段"表述，
说明"注释也是被扫面的一部分"。

## 件二 decisions 死哈希注记（P1-2）

**事实**：`docs/process/decisions.md` 全文 104 个提交哈希，在当前对象库
`git cat-file -e` **104/104 解析失败**。根因与 status.md 同源：仓库追踪收紧清洗
（`dee5c80`）重写了提交标识；旧树只以标签 `pre-scrub-backup` 保留一个入口，
旧哈希与备份树之间没有可机械换算的映射（实测三个样本均不是备份 tag 祖先）。

**判据**：历史清单是当时的记录，改写即伪造；但读者会把哈希当可复核锚点用，
不注记就是"看起来能查、实际查不到"的假证据。

**处置**：照 status.md 实况锚点先例，在正文前立**统一注记**：说明根因（清洗重写
标识）、存活边界（一律按"历史留痕、不可 `git show` 复核"读）、可复核替代
（只认 status.md 实况锚点与现存 `git log`）。历史清单原文一字不改。

**验证**：文档非空、相对链接全通（`../status.md` 等逐条 `-e` 检查）；
`check.sh` ⑤ 文档门通过（件四全量复跑）。

## 件三 质量度量基线（P1-3）

**事实**：`metrics.py` 实测重复率 1.00%、CC 均值 3.65、单函数最大 14、超长生产
函数名 0；基线文件仍是 `cc_mean_max 3.93 / cc_max_fn 21`。第六轮后各批拆件已把
峰值从 21 降到 14（四个并列 14），基线没跟上。

**判据**："基线只降不升"是机器判据的一半——只拦上涨、不跟低水位，低水位就是空话，
下一批新增一个 20 复杂度的函数也不会红。

**处置**：`metrics-baseline.json` 收到当前低水位（`cc_max_fn 21→14`、
`cc_mean_max 3.93→3.65`）；重复率门槛 3% 与长名 0 不动（未达新低）。

**验证**：`python3 tools/ci/metrics.py` 三项 PASS（均值 3.65 = 基线、max 14 = 基线、
dup 1.00% ≤ 3%）；`check.sh` ⑫ 通过（件四全量复跑）。

## 件四 门 a 红账 21→0（P1-4）

**事实**：`check.sh` ⑨-a 实跑红账 21 = A 13（未覆盖 normal 格）+ B 0 + C 8
（4 个 trait 无 roles.iface 引用 + 4 个 pin 键无 roles.requires 引用）+ D 0。
A 的 13 格分三类：base 内建四族（`bus.publish/subscribe/rpc`、`net.online`、
`power.budget`）、cognition 软件四格（`dialog/asr/llm/tts`）、body 层四格
（`net.wifi`、`audio.capture/playback/vad`）。

**判据（根因）**：
1. 设计原文（`architecture.md` 门 a 行）早已写明"logic 内建格覆盖口径归转红
   收口件另裁"——A 段把 base/cognition 计入分母，与 `roles.toml` 头注
   "logic = 无物理绑定、不进 `[pins]`"直接矛盾：这些格永远没有角色可挂。
2. body 四格是真空缺，但**不能靠"加角色"补**：`rr3_role_gaps` 与
   `surgery_gates` 两用例的硬不变式是"角色必须有 `[[pin]]` 绑定"，
   给无引脚格加 signal 角色会当场把 boot 判降（实测拦下）。
   `roles.toml` 的 `kind = logic` 正是为这类格准备的，但 `rr3_role_gaps`
   没为 logic 角色开口（此前全仓零 logic 角色，这条分支从未被走过）。
3. C 段的 4 个 pin 键按代码自身语义**永远不可能**进 `requires`：`role` 是 pin
   指向角色的自指键、`instance` 只对 `per_instance` 角色必填、`direction` 由
   独立方向判据校验、`mux_group` 明文不归 requires（`profile_checks.rs` 注记：
   互斥组由平台 `conflicts` 表承载）。`Rr3DigitalIn` 是能力面前置件（S-10
   数字输入面未立项），零格位消费者、零 prod 实现。

**处置（两腿同批）**：
1. **真覆盖**：`roles.toml` 10→14，新增 `net.wifi.link`、`audio.capture.mic`、
   `audio.playback.spk`、`audio.vad.gate`，均 `kind = logic`、
   `requires = []` / `derives = []` 显式空，iface 取真实承载面
   （`Rr3Link` / `Rr3AudioSource` / `Rr3AudioSink`；VAD 消费同源采集面）。
   `roles.rs` 把空 requires 的合法性限定在 `kind = logic`（signal/power 留空仍红，
   新增反例用例）；`rr3_role_gaps` 跳过 logic 角色（它们本就不在 `[pins]` 面）。
2. **口径裁定**：A 段分母收为 `layer = body` 的 normal 格；C 段豁免
   `Rr3DigitalIn` 与上述四键，理由逐条写在 `check.sh` ⑨-a 段内。
   红账归零后本门**转执法**：`gate-a-baseline.txt` 降至 0，`count > 0` 即 FAIL。

**验证**：⑨-a 实跑 `A=0 B=0 C=0 D=0 = 0`、`红账 0 = 基线 0（执法态）`；
①b workspace 全量测试 302 + 其余用例全过；`surgery_gates` 两用例（esp32-mini /
pi4b 装载演练）与 `e2e_profile` 的角色数 pin 同批订正后通过；⑩ 门 d 仍
`红账 0 = 上限 0`、`分母 83 = 下限 83`（无连带缩水）。

## 件五 M6 OTA 写侧（P1-5）

**事实**：`rr-ota::bootconf` 只有 extlinux 标签改写（标准序第 3 步）；
`base/ota/partition-layout.md` 的回滚链四变量（bootcount/bootlimit/altbootcmd/
upgrade_available）只有语义落档，写侧零代码。

**判据**：断电安全的回滚链要求"翻标志"这一步可执行且可验，不能停在文档；
写侧必须主机可测（硬件不在手），块设备差异只能落在 I/O 胶水层。

**处置**：新增 `rr-ota/src/bootenv.rs`：
- raw env 载体（`[crc32 LE][k=v\0]…\0`）解析/渲染/改键，CRC 复用
  `rr_ipc::protocol::header::rr3_crc32`（U-Boot `crc32(0, …)` 同形态，单点真值）；
  坏 CRC、截断、重复键、非 UTF-8 一律 fail-closed；
- `/etc/fw_env.config` 解析（`device offset env_size [sector_size num_sectors]`，
  数支持 `0x`），env 位置/容量从板上配置来，工具不猜；
- 回滚链状态迁移：`rr3_rollback_arm(limit, altcmd)` 落第 4 步四变量、
  `rr3_rollback_ok()` 落第 6 步解除；`altbootcmd` 由调用方给（distro boot
  命令随板/构建而变，契约不预造），空落点与 `bootlimit = 0` 当场拒；
- 区读写走 `std::fs`（无 ioctl），板上 Linux 与主机测试面同一份代码。

**验证**：`cargo test -p rr-ota` 24 用例全过（含 unix 真文件读写：16B 前哨 +
128B env 区 + 8B 后哨，验证偏移定位、整区覆盖、区外字节不动、读回逐键等值，
全 0 区被 CRC 拒读）；`cargo clippy -p rr-ota -D warnings` 干净；
`cargo check --target aarch64-unknown-linux-gnu -p rr-ota` 通过（板上目标编译面）；
§13 独立工程门 ④/④b/⑥ 覆盖。文档同批把"写侧未实装"改为"写侧已实装、主机可测"，
板上核对项第 4 条随之改写（不再依赖 `fw_setenv`/`BR2_PACKAGE_UBOOT_TOOLS`，
保留 fw_env.config 布局核对与冗余双副本同步写两条敞口）。
